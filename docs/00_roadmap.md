# MuJoCo × 強化学習 × Sim2Real 学習ロードマップ

作成日: 2026-08-31 / 対象: Python・NumPy は書けるが DL/RL は初めての人

---

## 0. この学習の設計方針

### 方針1: 題材を1つに絞り、最後まで育てる
教材を渡り歩くと「動かしたことはあるが分かっていない」状態になります。ここでは
**1自由度の振り子**から始め、同じ題材を段階的に難しくしていきます。

```
Step 2:  振り子を作る（MJCF）
Step 4:  PD制御 + エネルギー整形でスイングアップ（古典制御）
Step 6:  Gymnasium 環境化
Step 7:  PPO/SAC で学習
Step 9:  報酬設計・観測設計を詰める
Step 11: ドメインランダマイゼーション・遅延・アクチュエータモデル
Step 12: 実機（自作ハード）にデプロイ
```

### 方針2: RL の前に古典制御を通す
RL は「モデルが分からない／設計が難しい問題」のための道具です。
まず PD 制御で振り子を立たせておくと、以下が手に入ります。

- **ベースライン**: RL がこれに勝てなければ RL を使う意味がない
- **sim2real の物差し**: PD 制御は実機でもだいたい動く。RL 方策だけが実機で壊れるなら、原因は方策の過学習である
- **物理の直感**: トルク・慣性・減衰の大きさの感覚が身につく

### 方針3: 「動いた」ではなく「なぜ動いたか」で先に進む
各 Step に**完了条件**を書いています。チェックが全部埋まってから次に進んでください。
埋まらないときは飛ばさずに質問してください。

## 1. 技術スタック（採用と理由）

| 役割 | 採用するもの | 理由 |
|---|---|---|
| 物理シミュレータ | **MuJoCo 3.x**（`pip install mujoco`） | 接触・関節の数値安定性が高く、ロボット RL の事実上の標準。Google DeepMind が開発、Apache-2.0 |
| モデル記述 | **MJCF (XML)** | MuJoCo ネイティブ。URDF より表現力が高く、後で URDF からの変換も学ぶ |
| 環境 API | **Gymnasium** | `reset()` / `step()` の共通規格。RL ライブラリはこれを前提にしている |
| RL アルゴリズム | **Stable-Baselines3 (PPO / SAC)** | 実装が信頼でき、まず「正しく動く実装」を基準に持つため |
| 学習フレームワーク | **PyTorch** | SB3 の中身。Step 8 で自前 PPO を書くときにも使う |
| 実験管理 | **TensorBoard** | 学習曲線を見る癖をつける。RL はログを読めないとデバッグ不能 |
| 高速化（後半） | **MuJoCo MJX + JAX**, **MuJoCo Playground** | GPU 上で数千環境を並列実行。歩行など重い課題で必要になる |

**あえて今使わないもの**: Isaac Lab / Isaac Gym（セットアップが重く、学習の本筋から逸れる）、
RLlib（抽象化が厚く初学者にはブラックボックス）、Unity ML-Agents（対象が違う）。

### ハードウェア前提（あなたの環境）
- Ubuntu 22.04 / Python 3.11.10 (pyenv) / RTX 4050 Laptop 6GB

**重要な事実**: SB3 + MuJoCo の標準的な学習（小さな MLP 方策）では、**GPU はほとんど効きません**。
ボトルネックは物理シミュレーションであり CPU 側です。GPU が本当に効くのは Step 10 の MJX 以降。
「GPU があるのに速くならない」で悩まないでください。それが正常です。

### Step 3: 物理の中身とアクチュエータ（目安 10h）
**ねらい**: シミュレーションが壊れる／実機と合わない原因を、物理エンジン側から理解する。

学ぶこと:
- 運動方程式 `M(q)q̈ + C(q,q̇) = τ` と MuJoCo の解き方（概念レベルで十分）
- `timestep` と積分器（`Euler` / `implicitfast` / `RK4`）— 大きすぎると発散する
- 接触モデル: `solref` / `solimp` / 摩擦係数 — **sim2real 最大の罠のひとつ**
- アクチュエータ: `motor`（トルク）/ `position`（位置サーボ）/ `velocity`
  - **これは実機のモータ制御方式に対応する。ここを間違えると sim2real は絶対に成功しない**
- `gear`、`ctrlrange`、`forcerange`
- センサ: `<sensor>` で取れる量と、実機センサとの対応

あなたが書くもの: `sim/step_experiments.py`（timestep を変えて発散する境界を探す、など）

完了条件:
- [ ] timestep を大きくして発散させ、そのときの現象を説明できる
- [ ] `motor` と `position` アクチュエータの違いを、実機のモータドライバに対応づけて説明できる
- [ ] 摩擦係数を変えて接触挙動が変わることを確認した
- [ ] エネルギー保存を数値的に確認した（減衰ゼロの振り子で）

完了条件:

## Phase B — 強化学習の基礎

### Step 5: MDP と強化学習の言葉（目安 8h・理論中心）
**ねらい**: 論文と実装を読むための語彙を揃える。数式は必要最小限に、意味を優先。

- 方策 `π(a|s)`、決定的 vs 確率的
- ベルマン方程式が「何を言っているだけ」なのか
- 探索と活用、on-policy と off-policy の違い
- 方策勾配定理の直感（うまくいった行動の確率を上げるだけ）

あなたが書くもの: 表形式 Q 学習（`toy/gridworld_q.py`）— **ニューラルネットなしで RL の心臓部を体験する**

完了条件:
- [ ] グリッドワールドで Q 学習が収束するのを見た

- 初期状態のランダム化（学習の頑健性に直結）
- 失敗パターン診断表（学習しない／途中で崩壊する／シミュだけで動く）

## Phase D — Sim2Real

### Step 11: Sim2Real ギャップの理論と対策（目安 12h）
**ねらい**: 「シミュでは完璧、実機で転ぶ」の原因を分類し、対策を打てるようにする。

ギャップの発生源（この分類が Phase D の背骨）:

| 分類 | 具体例 | 主な対策 |
|---|---|---|
| **アクチュエータ** | サーボの応答遅れ、トルク上限、バックラッシュ、減速比の損失 | アクチュエータモデル、Actuator Net、実測同定 |
| **遅延** | センサ読み取り→推論→指令送出のレイテンシ（実機で 5-30ms） | シミュに人工遅延を入れる、観測履歴 |
| **物理パラメータ** | 質量・慣性・重心位置・摩擦係数の誤差 | ドメインランダマイゼーション、システム同定 |
| **接触** | 地面の弾性、滑り、足裏形状 | 接触パラメータのランダム化 |
| **観測** | センサノイズ、バイアス、ドリフト、量子化 | ノイズ注入、フィルタ、非対称 Actor-Critic |
| **未モデル化** | ケーブルの張力、たわみ、発熱によるトルク低下 | 頑健化（DR）、オンライン適応 |

学ぶこと:
- **ドメインランダマイゼーション (DR)**: どのパラメータを、どの範囲で振るか。振りすぎると保守的すぎる方策になる
- **システム同定**: 実機ログからシミュのパラメータを最適化して合わせる
- **アクチュエータネット**: 実機モータの応答を NN で学習してシミュに埋め込む（ANYmal の手法）
- **非対称 Actor-Critic**: Critic には特権情報（真の質量など）を与え、Actor は実機で取れる観測だけ使う
- **観測履歴 / Teacher-Student 蒸留**: 過去数ステップから物理パラメータを暗黙的に推定させる
- **安全のための報酬項**: トルク・関節速度・action rate のペナルティ

あなたが書くもの: DR 付き振り子環境、遅延モデル、同定スクリプト

完了条件:
- [ ] DR ありとなしで方策の頑健性を比較した（テスト時にパラメータをずらす）
- [ ] 遅延を入れると性能が落ちることを確認し、観測履歴で回復させた
- [ ] 非対称 Actor-Critic を実装した
- [ ] 「実機で壊れそうな方策」を、シミュ上のテストで事前に検出できた

### Step 12: 実機を作って載せる（目安 30h+）
**ねらい**: 自作ハードで RL 方策を動かす。ここまでの全部を使う。

**推奨する最初の実機（この順で難易度が上がる）**:

| 候補 | 構成 | 部品費目安 | なぜ良いか |
|---|---|---|---|
| **1. 回転型倒立振子（Furuta pendulum）** | ブラシ付き/BLDC 1個 + エンコーダ2個 + マイコン | 1〜2万円 | 自由度1+1で最小。倒れても壊れない。sim2real ギャップが**摩擦とバックラッシュに集約**され、原因分析が容易 |
| **2. 2輪バランスロボット** | ステッピング/DCモータ2個 + IMU + マイコン | 1〜2万円 | IMU の扱い・センサノイズ・遅延を学べる。転んでも安全 |
| **3. リアクションホイール振子** | BLDC 1個 + FOC ドライバ + IMU | 2〜3万円 | トルク制御が素直で、アクチュエータモデルの学習に最適 |
| **4. 小型ロボットアーム（3-5自由度）** | シリアルバスサーボ（STS3215等）5個 + 3Dプリント | 3〜5万円 | 次の段階。接触とグリッパが絡む |

**この講座での推奨: 1 → 2 の順**。理由は「壊れない・安い・ギャップの原因が特定できる」の3点。

学ぶこと:
- 実機の CAD → MJCF 化（質量・慣性を CAD から取る）
- モータ・エンコーダ・IMU の選定と、それぞれのシミュ上の対応物
- マイコン（ESP32 / Raspberry Pi Pico など）との通信と制御ループの実時間性
- 方策の実機デプロイ: PyTorch → ONNX / TorchScript、あるいは重みを直接 C に埋め込む
- **安全機構**: トルクリミット、非常停止、角度リミット、ウォッチドッグ
- 実機ログ収集 → システム同定 → シミュ更新 → 再学習のループ

完了条件:
- [ ] 実機の MJCF が実測質量・寸法と一致している
- [ ] 実機ログとシミュのログを重ねてプロットし、乖離を定量化した
- [ ] PD 制御が実機で動いた（RL の前に必ずこれ）
- [ ] 学習した方策が実機で動いた
- [ ] DR あり/なしの方策で実機性能を比較した

## 3. 各 Step 共通のルール

1. **完了条件が埋まるまで次に進まない**
2. **数値は必ず理論値・実測値と比較する**（「動いた気がする」を潰す）
3. **失敗を1回は意図的に起こす**（発散させる、報酬ハックさせる、DR なしで壊す）
4. **コードは自分で書く**。スニペットは骨格のみ。写経ではなく、埋めながら理解する
5. **分からない用語はその場で聞く**。用語の霧を残すと Phase D で必ず詰まる
