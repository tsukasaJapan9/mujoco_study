01

式を 1 行ずつ読む

この節のねらい

「分散で割る」という操作の意味を掴みます。 ここが分かると、0 と 1 とマイナスがなぜその意味になるかが 暗記ではなくなります。

新概念 説明された分散 (explained variance)
ひとことで
データのばらつきのうち、何割を予測器が言い当てたかの割合。
なぜ割合か
誤差の大きさ（Var(y − ŷ)）をそのまま見ても良し悪しが判断できないから。 誤差 5 は、収益が ±1000 動く環境なら優秀、±2 の環境なら論外。 「その環境でそもそもどれだけばらついているか」で割って初めて比較できる。
基準となる
ダメな予測器
いつも同じ定数を返す予測器。 これの誤差分散はちょうど Var(y)（分母）になる。 つまり分母＝「何も学習していない予測器」の成績。
だから
EV = 0 は 「定数を返すのと同点」、 EV < 0 は「定数を返すより下手」という意味になる。
EV  =  1  −  Var( y − ŷ ) Var( y )
y = 実際の収益（正解） ŷ = V の予測 分子 = 予測器が残した誤差のばらつき 分母 = そもそも正解がどれだけばらついているか

分数の部分だけ見ると読みやすくなります。 Var(y − ŷ) / Var(y) は 「説明できずに残ったばらつきの割合」です。 これが 0.006 なら、残ったのは 0.6 %。 1 から引いた 0.994 が説明できた割合—— これが explained_variance という名前の由来です。

分散 Var を忘れていたら

Var(x) = mean( (x − mean(x))2 )。 平均からのズレを 2 乗して平均したもの。 重要なのは「平均を引く」ところ—— だから Var は全体が何点ずれていても変わりません。 この性質が §05 の落とし穴に直結します。

02

「正解」とは何か

この節のねらい

式の y を「実際の収益（正解）」と書きましたが、 強化学習に、教師あり学習のような外から与えられる正解は存在しません。 では何を正解として採点しているのか。 ここを曖昧にしたまま EV の数字を読むと、必ず読み違えます。

新概念 本当に欲しいもの — 真の価値 Vπ(s)
定義
Vπ(s) = E[ G | 状態 s から方策 π で動いたとき ]。 5-c でやった価値そのものです。注目すべきは E[ ]——期待値である点。
なぜ期待値か
同じ状態から出発しても、毎回まったく同じ未来にはならないから。 方策が行動をサンプリングし、環境も揺れる。 「起こりうる未来すべての平均」が価値です。
観測
できるか
できません。期待値を直接見る手段はありません。 手に入るのはそこから引いた 1 本のくじだけ。
だから
EV の y は真の正解ではなく、正解の 1 サンプルです。 ラベルではなく、推定値で推定値を採点している。

教師あり学習との違い

教師あり学習強化学習の Critic
正解の出どころ 人間が貼ったラベル。外部の事実 自分が集めたデータから作る。外部の事実はない
正解のばらつき ない（猫の画像は何度見ても猫） ある。同じ状態から引くたび違う収益が出る
正解は動くか 動かない 動く。Vπ は π 次第で、 π は毎イテレーション変わる
満点は取れるか 原理的には取れる 取れないことがある（次の項）

3 番目が特に効きます Vπ は方策 π ごとに違う関数です。 PPO は毎イテレーション π を更新するので、 Critic が追いかけている的そのものが、毎回少し動きます。 EV が学習中に上下するのは、Critic が下手になったのではなく 的が動いた直後だから、ということが普通に起きます。

完璧な Critic でも EV は 1 に届かない

ここが一番大事な帰結です。仮に Critic が真の期待値 Vπ を 完全に言い当てたとしましょう。それでも残差 G − Vπ は 0 になりません。G はくじ引きの結果で、 Vπ はその平均だからです。

EV の天井  =  1  −  E[ Var( G | s ) ] Var( G )
分子 = 状態を知っても消えないばらつき（くじの揺れ） 分母 = 収益全体のばらつき

EV は「収益のばらつきのうち、そもそも状態から予測できる分を、 どれだけ取り切ったか」を測っている——これが正確な言い方です。 予測できない分は、誰にも取れません。

あなたの環境で天井を測る

天井は測れます。同じ状態から何度も分岐させて、収益がどれだけばらつくかを見ればよい。 ppo_semi_long_s0 で実測しました （軌道上の 20 点から分岐、各 24 本、500 ステップ、γ=0.99）。

行動の選び方E[Var(G|s)] Var(G)EV の天井
確率的（学習中はこちら） 4.771983.6 0.9976
決定的（deterministic=True） 0.0001801.4 1.0000

決定的方策でぴったり 0 になる理由 envs/pendulum_env.py の step() に乱数が 1 つもないからです。 MuJoCo の積分は決定的で、ランダムなのは reset() の初期角度だけ。 状態と行動が決まれば未来が完全に決まるので、 G は s の関数になり、原理的に 100 % 説明できます。

だから 0.997 が出た

§08 で測った MC 基準の EV = 0.9962 は、 天井 1.0000 に対する成績です。 学習中（確率的方策）の天井は 0.9976。 どちらの見方でも、この Critic は天井に張り付いています。

そしてこれは「振り子だから」出た数字です。 風が吹く、センサにノイズが載る、相手が動く—— そういう環境では天井が 0.6 や 0.3 まで落ちます。 別の環境で EV が 0.6 でも、天井が 0.62 なら満点です。

実務ルール（2 つ目）

§07 で「設定をまたいで比べるな」と書きました。もう 1 つ—— 環境をまたいでも比べてはいけません。 EV の絶対値に意味があるのは、その環境の天井とセットで見たときだけです。

新しい環境を作ったら、まず天井を測ってください。 同じ状態から N 本分岐させて収益の分散を見る、それだけです。 目標値が分かってから学習を回すのと、分からずに回すのとでは、 デバッグの効率がまったく違います。

03

手計算で 3 例

この節のねらい

5 個だけのデータで実際に数字を出します。 0 とマイナスが「たまたまそうなる」のではなく、 式から必然的にそうなることを確認します。

正解の収益を y = [−10, −6, −2, 2, 6] とします。 平均は −2.0、Var(y) = 32.0（これが全例の分母）。

Critic予測 ŷ残差 y−ŷ Var(残差)EV
まとも [−9, −7, −1, 1, 6] [−1, 1, −1, 1, 0] 0.8 +0.975
平均だけ返す [−4, −4, −4, −4, −4] [−6, −2, 2, 6, 10] 32.0 0.000
逆向き [−1, −3, −5, −7, −9] [−9, −3, 3, 9, 15] 72.0 −1.250

2 行目に注目してください 予測した定数は −4 で、正解の平均 −2 ではありません。 それでも EV はぴったり 0.000 です。 Var が平均を引いてから測るので、 定数なら何を返そうと Var(y − 定数) = Var(y) になるためです。

3 行目の −1.25 も計算で出せます 残差のばらつきが 72.0、正解のばらつきが 32.0 なので 1 − 72/32 = −1.25。 マイナスは「下手」の度合いを線形に表すので、 −0.1 と −3 は全然違う深刻さです。

下限はない

EV の上限は 1 ですが、下限はありません。 予測の符号をすべて反転させた ŷ = −y なら Var(y − (−y)) = Var(2y) = 4 Var(y) なので EV = 1 − 4 = −3。 スケールが 10 倍ずれていれば −81 まで落ちます。

05

EV が見ないもの — R² との違い

この節のねらい

「決定係数 R² と同じでは？」という疑問に決着をつけます。 違います。そして違いが出るのは、まさに Critic が壊れやすい方向です。

EV = 1 − Var( y − ŷ )Var( y )      R² = 1 − Σ( y − ŷ )²Σ( y − ȳ )²
違いは分子だけ: Var は平均を引いてから 2 乗、Σ は引かずに 2 乗

この差は Var(r) = mean(r²) − mean(r)² の 第 2 項ぶんです。つまり R² は残差の平均（＝系統的なズレ）を罰し、EV は罰しない。

実務での意味

V の絶対値が全体的にずれていても EV は気づきません。 報酬のスケールを途中で変えた、VecNormalize の統計がずれている、 といった不具合は EV では検出できないということです。

ただし PPO ではそれでも実害が小さいのがポイントです。 方策の更新に使われるのは A = 収益 − V の相対的な大小で、 しかも A はミニバッチごとに平均 0・分散 1 に正規化されます （normalize_advantage=True が既定）。 EV がバイアスを無視するのは、PPO がバイアスを気にしないからです。 指標の設計が、使われ方と揃っている。

06

SB3 の実装を読む

この節のねらい

ここまでは数学でした。ここからはあなたのログに出ている数字そのものです。 SB3 が「実際の収益」として何を渡しているかを、ソースで確かめます。

指標の定義そのもの

# stable_baselines3/common/utils.py
def explained_variance(y_pred, y_true):
  var_y = np.var(y_true)
  return np.nan if var_y == 0 else float(1 - np.var(y_true - y_pred) / var_y)

式は §01 のとおり。 付け足しは 1 つだけ—— Var(y) == 0 なら nan を返します。 収益がまったくばらつかないとき、この指標は定義できないからです （0 で割ることになる）。 TensorBoard で explained_variance の線が突然消えたら、まずこれを疑ってください。

07

「実際の収益」の正体

この節のねらい

EV = 0.99 でも Critic を褒めきれない理由を示します。 この指標は、自分で自分を採点している部分がある—— それがどれくらいかを数字で見ます。

# stable_baselines3/common/buffers.py  compute_returns_and_advantage()
for step in reversed(range(self.buffer_size)):
  delta = self.rewards[step] + self.gamma * next_values * next_non_terminal - self.values[step]
  last_gae_lam = delta + self.gamma * self.gae_lambda * next_non_terminal * last_gae_lam
  self.advantages[step] = last_gae_lam

self.returns = self.advantages + self.values   # ← ここ

最後の 1 行がすべてです。 returns（＝採点の「正解」）は values（＝採点される「予測」）を足して作られています。 Step 8 で扱う GAE の λ-収益がこれです。

returns − values = advantages   ⇒   EV = 1 − Var( A )Var( returns )
A = アドバンテージ（正規化前、バッファに入っている生の値）

つまり PPO の explained_variance とは 「アドバンテージのばらつきが、λ-収益のばらつきに比べてどれだけ小さいか」 を測った数字に等しい、ということです。定義から導ける恒等式で、近似ではありません。 EV が低い＝ A がばらついている＝方策の更新方向がうるさい。 7-b で「低いと方策の更新方向が信用できない」と書いたのは、この意味です。

何が問題になるのか

λ が小さいほど、正解 returns は r + γV(次の状態) に近づきます—— 正解の中身のほとんどが V 自身になる。 V が下手でも、下手な V を基準に採点すれば当たって見えます。

わざと下手な Critic（真の V を 0.7 倍に縮め、 さらに標準偏差 5 のノイズを載せたもの）を用意し、 Critic は一切変えずに gae_lambda だけ動かして測りました。

gae_lambdaEV正解 returns の中身
0.00+0.698r + γV'。ほぼ V 自身
0.25+0.733—
0.50+0.750—
0.75+0.739—
0.95+0.622SB3 の既定値
1.00+0.477実際の割引収益（モンテカルロ）。V を一切含まない

※ 20 本 × 100 ステップ × 200 試行、γ=0.99、全 λ で同一の乱数系列。 試行間のばらつきは λ=1.0 で標準偏差 0.05、他は 0.01〜0.03。

読み取ること
  • 同じ Critic が、0.477 とも 0.750 とも採点される。 変えたのは gae_lambda だけ
  • λ=1（モンテカルロ）が最も厳しい。 正解に V が混ざらない唯一の設定だから
  • ただし単調ではありません。λ=0 でも 1 ステップ報酬のノイズをまともに受けるため、 この設定では λ=0.5 付近が最も甘くなりました
実務ルール

gae_lambda や gamma が違う実験の EV を横に並べて比べないでください。 採点基準そのものが変わっています。 比べてよいのは、同じ設定の中での時間変化だけです。

では 0.997 は本物か

§07 の話があるので、確かめました。 学習済みモデル ppo_semi_long_s0 を 10 エピソード走らせ、 V を一切使わない本物の割引収益（λ=1 相当）に対して EV を計算した結果が 0.9962（5000 点）。

この環境では、ログの 0.997 は下駄を履いていませんでした。 Critic は本当に当てています。 —— ただしそれは測って初めて言えることです。次の課題でやります。

09

手を動かす

この節のねらい

2 つとも「ログの数字を鵜呑みにしない手段」を自分の手元に作る課題です。 指標を読めるだけでは足りず、指標を検算できる必要があります。

課題 1

本物の収益基準で EV を測る train/ev_check.py

この課題の狙い

SB3 の EV は λ-収益基準でした（§07）。 V を含まない正解を自分で作って比べることで、 Critic の実力と、採点基準の甘さを分離できます。 これは「TensorBoard を疑う」ための道具で、 Step 8 で PPO を自分で実装したあとのデバッグでそのまま使えます。

STEP 1

収益を後ろから積む

まとめ

この教材で分かったこと
  1. EV は「ばらつきの何割を説明したか」。 分母は定数を返すだけの予測器の成績なので、 0＝同点、負＝それ以下、という意味になる
  2. RL に外から与えられる正解はない。 欲しいのは期待値 Vπ、手にあるのはその 1 サンプル。 しかも π が変わるたび正解も動く
  3. 完璧な Critic でも 1 には届かない。 天井は 1 − E[Var(G|s)]/Var(G)。 あなたの振り子は環境が決定的なので天井が高く （確率的方策で 0.9976、決定的方策で 1.0000）、 だから 0.997 が出た。別の環境の 0.6 と比べても意味がない
  4. バイアスを見ない。 ŷ = y + 100 でも EV = 1.000（R² は −98.96）。 PPO はアドバンテージを正規化して使うので、これは欠陥ではなく設計の一致
  5. SB3 の y_pred は収集時の V。 ログの値は更新前の Critic の成績で、1 手遅れている
  6. returns = advantages + values なので EV = 1 − Var(A)/Var(returns)。 低い EV ＝ アドバンテージがうるさい ＝ 更新方向が信用できない
  7. 正解に V 自身が混ざっている。 同じ Critic が gae_lambda 次第で 0.477 とも 0.750 とも採点される。 設定をまたいで横比較してはいけない
  8. 指標には効く区間がある。 あなたのログでは 25 万ステップ以降、EV は 0.995 → 0.997 しか動かないのに 報酬は 189 改善した。そこから先は Actor 側を見る
  9. Var(y) == 0 のとき nan。 線が消えたら、収益がばらついていないことを疑う
Step 8 への接続

8-a で Critic の損失を自分で書くと、 この教材で読んだ returns が、そのまま学習の教師信号として現れます。 value_loss = MSE(V, returns) —— EV はこの損失を「環境ごとに意味のあるスケール」に直したものだと分かります。

そして GAE の λ を自分で実装したとき、 今日見た「正解に V が混ざる」構造を、自分のコードの中に見つけてください。
