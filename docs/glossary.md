## 記号・記法

### `q` — 一般化座標 (generalized coordinates)

ラグランジュ力学の標準記号。**系の姿勢を過不足なく表すのに必要な、最小限の独立変数の組**。

振り子の例:

```
直交座標での記述:  (x, y, z) = 3変数 + 拘束条件2本   ← 冗長
一般化座標での記述: q = [θ]   = 1変数、拘束なし       ← MuJoCo の持ち方
```

棒の先端の位置は 3 つの数で書けるが、「軸から 0.5m」「平面上」という拘束があるため
実際に自由なのは角度 θ だけ。MuJoCo は**関節に沿った変数だけ**を状態として持つので、
拘束を毎回解く必要がなく、速くて数値的に安定する。

### `q` 系と `x` 系

| 記号 | 読み | 中身 | 空間 |
|---|---|---|---|
| `data.qpos` | q | 各関節の角度・変位 | **関節空間** |
| `data.qvel` | q̇ (qdot) | 各関節の角速度・速度 | 関節空間 |
| `data.qacc` | q̈ | 各関節の角加速度 | 関節空間 |
| `data.xpos` | x | 各 body のワールド座標 [m] | **直交座標空間 (Cartesian)** |
| `data.xquat` | — | 各 body の姿勢（クォータニオン） | 直交座標空間 |

```
qpos ──[順運動学 mj_kinematics]──> xpos
「関節がこう曲がっている」        「だから手先はここにある」
```

**`qpos` が原因側の状態、`xpos` はそこから計算された結果。**
`xpos` に代入しても次のステップで上書きされる。動かしたいときは必ず `qpos` を触る。

### 運動方程式の中の q

```
M(q) q̈  +  C(q, q̇)  =  τ
 ↑         ↑            ↑
質量行列    コリオリ・重力  関節トルク
```

`M` が `q` の関数である＝**姿勢によって動かしにくさが変わる**。
アームを伸ばした状態と畳んだ状態では、同じトルクでも回転の速さが違う。

### その他の接頭辞・記号

| 記号 | 意味 |
|---|---|
| `n` 接頭辞 | number of。`nq`, `nv`, `nu`, `njnt`, `nbody` |
| `u` | 制御入力。制御工学の標準記号（`ẋ = Ax + Bu`）。`data.ctrl` の長さが `nu` |
| `frc` | force。`data.qfrc_applied` は関節空間に加える力 |
| `τ` (tau) | 関節トルク [N·m] |
| `adr` | address（配列上の開始位置）。`jnt_qposadr` など |

### `nq ≠ nv` になる場合

`q̇` は `q` の時間微分なので普通は同じ長さだが、**回転姿勢の表現だけが例外**。

| 関節タイプ | qpos | qvel | 中身 |
|---|---|---|---|
| `hinge` | 1 | 1 | 角度 / 角速度 |
| `slide` | 1 | 1 | 変位 / 速度 |
| `ball` | 4 | 3 | クォータニオン / 角速度ベクトル |
| `free` | 7 | 6 | 位置3+クォータニオン4 / 速度3+角速度3 |

姿勢はクォータニオン（4成分＋ノルム1拘束）で持つが、角速度は3成分で足りるため。
四足歩行ロボットの胴体は `free` joint なので、歩行 RL では必ずこのズレに出くわす。

### `nq` / `nv` / `nu` — 次元を表す3つの数

`n` は number of。ただの配列長だが、この3つはロボットの性質そのものを表す。

| 変数 | 正式には | 実質的な意味 |
|---|---|---|
| `nq` | 一般化座標の次元 | 姿勢を表すのに使っている**数値の個数** |
| `nv` | 一般化速度の次元 | **自由度 (DOF)** そのもの。独立に動ける方向の数 |
| `nu` | 制御入力の次元 | **アクチュエータの数**。動かせる方向の数 |

本質的な自由度は `nv`。`nq` は表現の都合で膨らむことがある（クォータニオン）。
「このロボットは何自由度か」の答えは `nv`。質量行列 `M(q)` は `nv × nv` の正方行列になる。

| モデル | 構成 | nq | nv | nu |
|---|---|---|---|---|
| 振り子 | hinge 1 | 1 | 1 | 0 or 1 |
| カートポール | slide 1 + hinge 1 | 2 | 2 | 1 |
| 2リンクアーム | hinge 2 | 2 | 2 | 2 |
| 空中に浮いた箱 | free 1 | 7 | 6 | 0 |
| 四足歩行ロボット | free 1 + hinge 12 | 19 | 18 | 12 |

**ズレは常に free / ball joint の分だけ**発生する。四足の 19 と 18 の差は胴体の free joint による。

### 完全駆動と劣駆動 — `nv` と `nu` の関係

```
nu >= nv  ->  完全駆動 (fully actuated)   全ての自由度を直接動かせる
nu <  nv  ->  劣駆動   (underactuated)    直接動かせない自由度がある  <- 難しい
```

- **カートポール**: `nv=2`（カート位置・棒の角度）に対し `nu=1`（カートを押す力だけ）。
  棒を直接回すモータは無いので、カートを揺すって間接的に角度を制御するしかない。
- **四足歩行**: `nu=12` に対し `nv=18`。差の 6 は胴体の free joint。
  **胴体を直接動かすモータは存在せず**、脚を地面に押しつけた反作用でしか動かせない。
  これが歩行制御の難しさの中心であり、強化学習が使われる理由でもある。

劣駆動系では「制御したい変数」と「動かせる変数」が一致しない。
Step 4 の問い「なぜ PD 制御だけではスイングアップできないか」の答えの入口がこれ。

### RL での現れ方（Step 6 で使う）

```
action_space の次元   = nu
observation の基本形  = qpos (nq) + qvel (nv) をつないだもの
```

自作環境を書くときに真っ先に決めるのがこの2つのサイズ。

```python
print(f"nq={model.nq}  nv={model.nv}  nu={model.nu}")
print(f"qpos.shape={data.qpos.shape}  ctrl.shape={data.ctrl.shape}")
```

Step 1 の振り子は `<actuator>` を書いていないので `nu = 0`、つまり誰も動かせない。
Step 2 で `<motor>` を足して `nu = 1` にするところから制御の話が始まる。

### インデックスと関節の対応を調べる

```python
for j in range(model.njnt):
    name = mujoco.mj_id2name(model, mujoco.mjtObj.mjOBJ_JOINT, j)
```

## MuJoCo の主要オブジェクト

### `MjModel`
コンパイル済みの設計図。**シミュレーション中に変化しない定数**。
質量・慣性・関節の種類と軸・アクチュエータ設定・`opt.timestep`・`opt.gravity` など。
実機で言えば「図面とスペック表」。

### `MjData`
今この瞬間の状態。**`mj_step()` のたびに書き換わる**。
`qpos` / `qvel` / `ctrl` / `time` / `xpos` / `sensordata` など。
実機で言えば「今のセンサ値とモータ指令」。

### `M` — 質量行列（慣性行列）

運動方程式 `M(q)·q̈ + c(q, q̇) = τ` の `M`。
スカラーの `F = ma` の `m` が、多自由度になって行列に化けたもの。
**「ある加速度を出すのにどれだけのトルクが要るか」**を表す。

| | 意味 |
|---|---|
| 対角成分 `M[i,i]` | 関節 i 自身の慣性 |
| 非対角成分 `M[i,j]` | **関節 i と j の干渉**。i を加速すると j が振られる度合い |
| `(q)` が付く理由 | 姿勢によって値が変わるから |

1 自由度の振り子なら 1×1 で、ただのヒンジまわりの慣性モーメント（`0.056743 kg·m²`）。
姿勢を変えても一定。cartpole（`nv=2`）だと非対角成分が出て、ポール角で変化する。

```
pole角=0     M = [[2.78749  +0.23625] [+0.23625  0.09674]]
pole角=pi/2  M = [[2.78749  +0.00000] [+0.00000  0.09674]]   # 水平では干渉が消える
```

### `mj_fullM(model, data, M)` — 疎な M を密行列に展開する

MuJoCo は `M` を**対称性とゼロを省いた疎な形**で保持している。
`cartpole` は `nv=2`（密なら 2×2 = 4 要素）なのに `data.M` は **3 要素**しかない。
そのままでは行列として読めないので、`nv × nv` の普通の配列に書き戻すのがこの関数。

```python
M = np.zeros((model.nv, model.nv))   # 書き込み先を先に用意する
mujoco.mj_fullM(model, data, M)      # 戻り値ではなく M に書き込まれる
print(M[0, 0])
```

`M = mujoco.mj_fullM(...)` と書くと `None` が入る。C の API をそのまま移植しているため。

**MuJoCo 3.12 での変更点**（古い記事のコードは動かない）:

| 古い書き方 | 3.12 |
|---|---|
| `data.qM` | `data.M` |
| `mj_fullM(model, M, data.qM)` | `mj_fullM(model, data, M)` |

`AttributeError: 'MjData' object has no attribute 'qM'` が出たらこれ。

### `mj_step(model, data)`
1 physics step。内部でやっていること:
1. 順運動学（`qpos` → `xpos`）
2. 質量行列 `M(q)`、コリオリ・重力の計算
3. `ctrl` からアクチュエータ力を計算
4. 接触検出と拘束力の求解
5. `q̈` を求め、`timestep` だけ積分して `qpos`, `qvel` を更新
6. `data.time += timestep`

## アクチュエータ

### 3 種は同じ 1 つの式

`motor` / `position` / `velocity` は別々の機能ではなく、**同じ式のパラメータ違い**。

```
力 = gain × ctrl  +  bias₀  +  bias₁ × q  +  bias₂ × q̇
```

| 宣言 | gain | bias (0,1,2) | 結果の式 |
|---|---|---|---|
| `<motor gear="1"/>` | 1 | (0, 0, 0) | `f = ctrl` |
| `<position kp="30" kv="2"/>` | 30 | (0, −30, −2) | `f = 30(ctrl − q) − 2·q̇` |
| `<velocity kv="1.5"/>` | 1.5 | (0, 0, −1.5) | `f = 1.5(ctrl − q̇)` |

`model.actuator_gainprm[i, :3]` と `model.actuator_biasprm[i, :3]` で実測できる。

### `<motor>` — 素の力源

**`ctrl` に書いた数値をそのまま関節トルク [N·m] として加える**、最も素朴なアクチュエータ。
bias 項がすべて 0 なので、`q` にも `q̇` にも依存しない。**フィードバックが一切無い**。

```xml
<motor name="a_motor" joint="j_motor" gear="1" ctrlrange="-2 2"/>
```

| 属性 | 意味 |
|---|---|
| `gear` | `ctrl` に掛かる倍率。そのまま gain になる。減速比を表現するのに使う |
| `ctrlrange` | `ctrl` の上下限。**実機のモータのトルク上限**に対応する |

- `ctrl=1.0` は「1.0 N·m を加え続けろ」の意味。目標角度ではないので、**放っておいても止まらない**
- 重力と釣り合う角度があればそこで静止する。振り子なら `sin θ = ctrl / (m·g·l)` を満たす θ
- 対応する実機は **BLDC + FOC ドライバ**など、電流（≒トルク）を直接指令できるモータ

### なぜ `motor` が重要か

`position` はシミュレータの中に PD 制御器が**埋め込まれている**状態。
制御器を自分で設計したいなら、埋め込み版ではなく `motor` を使い、
毎ステップ `data.ctrl[0] = -kp*(q - q_target) - kd*qvel` のように**自分で計算して書き込む**。

- Step 4（古典制御）で書くのはこれ。`position` の式を Python 側に出す作業
- Step 6 以降、**方策の出力をトルクにするか目標角度にするか**が行動空間の設計そのものになる
- 実機のサーボが目標角度しか受け付けないのに `motor` で学習すると、**指令を送る手段が無い**方策ができる

## 強化学習の概念

### TD 誤差（Temporal Difference error）

```
TD 誤差 = [ r + gamma * max_{a'} Q(s', a') ] - Q(s, a)
            ^^^ 実際にもらった報酬
```

**同じものの 2 つの見積もりを比べている。**

| | 中身 | 性質 |
|---|---|---|
| `Q(s,a)` | 歩く**前**の予想 | 全部が推測 |
| `r + gamma * max Q(s')` | 歩いた**後**の見積もり | **`r` だけは実測値** |

どちらも「`s` で `a` を取ったときの価値」の見積もり。違いは
**後者に実際に起きたこと（`r`）が 1 個混ざっている**点だけ。だから後者のほうがわずかに正しい。

**「正解との差」ではない。** 正解は誰も知らない。知っているのは
「1 歩進んだら、さっきの予想が少しずれていた」という事実だけ。
これを繰り返すと実測の `r` が少しずつ全体に染み渡る（Step 5-d の「波が広がる」絵）。

**注意: 学習途中は `Q(s,a)` も `max Q(s')` も両方とも外れている。**
片方だけ正しいということはない。実際の学習を記録するとこうなる
（gridworld の `(2,0)` で `up` を選んだときの更新）。

```
  ep    Q(s,a)   max Q(s')    r    target      TD誤差
   0   0.00000    0.00000   0.0   0.00000  +0.00000   <- 両方ゼロ。何も起きない
  21   0.02884    0.09735   0.0   0.08761  +0.05878   <- 両方とも正解から遠い
  51   0.37327    0.54655   0.0   0.49190  +0.11863   <- 誤差のピーク
 399   0.65610    0.72900   0.0   0.65610  +0.00000   <- ようやく収束
```

正解は `Q*((2,0),up) = 0.65610`、`max Q*((1,0)) = 0.72900`。**どちらも最後まで動き続ける。**

**`r = 0` の場所では、最初は本当に何も起きない**（ep 0 の行）。
ゴールに入った 1 歩だけ `r = 1.0` が発生し、そこだけは推測が混ざらないので確実に更新される。
その値が隣に、また隣に伝わっていく。

**TD 誤差は単調に減らない。** 情報が届いた瞬間にいったん大きくなり（ep 51）、その後ゼロに向かう。
「誤差が大きい ＝ 悪い」ではなく「学習が進んでいる最中」のこともある
（Step 7-b の `explained_variance` が最初マイナスから 0.91 に急上昇したのと同じ構図）。

**名前の由来**: 時間的に隣り合う 2 つの推定値 — `t` 時点の予想と `t+1` 時点から見た予想 — の差だから。

**符号**: 正なら「思ったより良かった」→ 価値を上げる。負なら下げる。

**終端では `r` だけになる。**

```
ゴールに入る 1 歩:  target = 1.0 + gamma*0 = 1.0    # 未来が無いので推測が混ざらない
```

Step 6-c の `terminated` の場合分けはこのため。
Step 5-d で「ゴールの隣だけは他に頼らず確定できる」と言えたのも同じ理由。

**`V` しか持っていない場合**（PPO がこれ）:

```
Q がある場合:  TD 誤差 = r + gamma*max_{a'} Q(s',a') - Q(s,a)
V だけの場合:  A       = r + gamma*V(s')             - V(s)
```

構造は同じ。後者が**アドバンテージの 1 歩先推定**になる。

### `max_{a'}` の `a'` と SARSA の `a'` は別物

```
Q 学習:  max_{a'} Q(s', a')   # a' はすべての行動を動かす仮の名前。式の外に出ない
SARSA:            Q(s', a')   # a' は実際に次に選ぶ行動。具体的な 1 つの値
```

コードで見れば一目瞭然。

```python
max(Q[s_next])          # Q 学習。添字が無い
Q[s_next][a_next]       # SARSA。a_next という具体的な行動を指定している
```

## 強化学習ライブラリ

### `explained_variance` — 何を測っているか

```
EV = 1 - Var(y_true - y_pred) / Var(y_true)
```

**分母は「いつも同じ定数を返すだけの予測器」の誤差**。だから `0` はその予測器と同点、
負はそれ以下という意味になる。上限は `1`、**下限はない**（符号が逆なら `-3`）。

**分散は平均を引いてから測るので、全体が一律にずれていても値が変わらない。**
`y_pred = y_true + 100` でも `EV = 1.0`（`R²` なら `-98.96`）。
PPO はアドバンテージを正規化して使うので、この鈍さは実害になりにくい。

**「正解」は外から与えられない。** 欲しいのは期待値 `V^π(s) = E[G | s, π]` だが、観測できるのは
そこから引いた 1 サンプルだけ。だから**完璧な Critic でも EV は 1 に届かない**:

```
EV の天井 = 1 - E[Var(G|s)] / Var(G)
```

状態を知っても消えないばらつき（環境と方策の乱数）は、誰にも説明できない。
振り子環境は `step()` に乱数がないので天井が高い（確率的方策 `0.9976` / 決定的方策 `1.0000`）。
**別の環境の `0.6` が悪いとは限らない。天井とセットで見ること。**

**SB3 が渡しているもの**（`ppo.py`）:

```python
explained_variance(rollout_buffer.values,    # 収集時点の V ＝ 更新前の Critic
                   rollout_buffer.returns)   # advantages + values ＝ λ-収益
```

`returns = advantages + values` なので **`EV = 1 - Var(A)/Var(returns)`** が恒等式として成り立つ。
**低い EV ＝ アドバンテージがうるさい ＝ 方策の更新方向が信用できない。**

**注意**: 正解の `returns` に `V` 自身が混ざっているため、`gae_lambda` を変えると
同じ Critic でも値が変わる（実測で `λ=1.0` → `0.477`、`λ=0.5` → `0.750`）。
**設定をまたいだ横比較をしてはいけない。** `Var(y_true) == 0` のときは `nan`。

詳細は補助教材 [explained_variance の中身](explained_variance_explained.html)。

### `VecNormalize` の「統計」とは

観測と収益の **平均** と **分散** のこと。`VecNormalize` が内部に溜め続けている。

```
作った直後      平均 [0. 0. 0.]            分散 [1. 1. 1.]
2550 ステップ後  平均 [0.996 -0.005 0.001]   分散 [0. 0.008 0.223]
```

環境が返す観測を見るたびに更新されるので、**走らせるほど値が変わる**。

**何に使うか**: 正規化の計算そのもの。

```
正規化後 = (生の観測 - 平均) / sqrt(分散)
```

### `venv.training = False` が止めるもの

**新しく見た観測を統計に取り込むのをやめる。** 正規化そのものは続く。

評価時に必ず入れる。理由は 2 つ。

1. **評価のたびに答えが変わる。** 統計が更新され続けると、同じ方策を 2 回測っても
   結果が違う。測定条件を固定しないと比較できない
2. **評価データが学習に混ざる。** テストデータの混入にあたる

併せて `venv.norm_reward = False` も入れる。**報酬を生の値で測らないと基準線と比較できない**から。

```python
venv.save("train/ppo_vecnorm.pkl")     # 忘れると読み込んだ方策が動かない
```

モデルだけ保存して統計を忘れると、ネットが見たことのない桁の入力が来て性能が出ない。
これが `VecNormalize` の導入コストの一部。

## Python の書き方

### `lambda` — その場で名前のない関数を作る

```python
f = lambda x, y: x + y      # ↓ と同じ
def f(x, y): return x + y
```

| 部分 | 意味 |
|---|---|
| `lambda` からコロンまで | 引数リスト |
| コロンの後ろ | 返り値の式。**`return` は書かない** |

**式を 1 つしか書けない。** `if` 文や複数行の処理は入らない。
作られるものは `def` の関数と同じ型で、`__name__` が `<lambda>` になる点だけ違う。

強化学習では「方策 = 状態を受け取って行動を返す関数」を引数として渡す場面で出てくる。

```python
def evaluate(policy):
    ...
    action = policy(env, obs)     # 渡された関数を呼ぶ

evaluate(lambda env, obs: env.action_space.sample())   # ランダム方策
evaluate(expert)                                        # def で書いた制御器
```

**使わない引数も受け取る形にしておく必要がある。** 上の例の `obs` は本文で使われないが、
`evaluate()` が 2 つ渡してくるので省略できない。`lambda env, _: ...` と書いてもよい。

**名前を付けて代入するのは PEP 8 で非推奨。** 名前を付けるなら `def` を使うほうが、
読みやすくトレースバックにも関数名が出る。`lambda` が向くのは、
名前を付けずにその場で渡すとき。

## NumPy イディオム

RL では「ループを書かずに配列全体を一度に処理する」書き方が必須になる。
Step 7 以降、数千ステップ分の観測・報酬・アドバンテージをまとめて計算するようになると、
for ループでは実用にならない速度差が出る。

### 隣り合う要素を比較する — `x[:-1]` と `x[1:]`

```python
q      = [0.9,  0.5, -0.2, -0.7, -0.3,  0.4,  0.8]
q[:-1] = [0.9,  0.5, -0.2, -0.7, -0.3,  0.4]        # 最後を除く = 各点の「今」
q[1:]  = [      0.5, -0.2, -0.7, -0.3,  0.4,  0.8]  # 最初を除く = 各点の「次」
```

1 つずらして重ねると、ループなしで隣接要素をペア比較できる。

### 比較演算はブール配列を返す

```python
q[:-1] > 0                      # [True, True, False, False, False, True]
(q[:-1] > 0) & (q[1:] <= 0)     # 要素ごとの AND
```

`&` は要素ごとの AND（Python の `and` は配列に使えない）。
**演算子の優先順位の都合で各条件を必ず括弧で囲む**こと。

### `np.where` — 2 つの顔を持つ

| 形 | 意味 |
|---|---|
| `np.where(cond)` | **True の位置（インデックス）**を返す。次元ごとのタプルなので `[0]` が要る |
| `np.where(cond, a, b)` | 条件で値を選ぶ。`cond` が True なら `a`、False なら `b` |

```python
idx = np.where(cond)[0]        # タプルの中身を取り出す
idx = np.flatnonzero(cond)     # 同じ結果。こちらは配列が直接返るので素直
```

### `np.argmax` — 最大値の「位置」を返す

`max` が最大の**値**を返すのに対し、`argmax` は最大値がある**インデックス**を返す。
`arg` は「引数」で、数学の `argmax`（最大値を与える引数）から。

```python
q = [0.5905, 0.5905, 0.5314, 0.5314]
np.max(q)     # -> 0.5905   値
np.argmax(q)  # -> 0        位置
```

強化学習では `Q[s]` が `[上, 右, 下, 左]` の並びなので、
**「どれを選ぶか」を知りたいときは位置、「いくら良いか」を知りたいときは値**を使う。

```python
a = int(np.argmax(Q[s]))              # 行動を選ぶ  -> 位置
target = r + gamma * max(Q[s_next])   # 更新式      -> 値
```

**同点なら必ず最初のインデックスを返す**（ランダムではない）。

```python
np.argmax([0.0, 0.0, 0.0, 0.0])  # -> 0
np.argmax([0, 9, 9, 0])          # -> 1
```

Q テーブルが全部 0 の状態で貪欲に選ぶと常に行動 0 を返すため、
`epsilon = 0` だと一度もゴールできず学習が始まらない。Step 5-e の失敗例の正体。

**返り値は `numpy.int64` で Python の `int` ではない。** 辞書のキーやリストの
インデックスに使うと不都合が出ることがあるので `int()` で包む。

**2 次元配列に渡すと平坦化した通し番号を返す。** 行ごとに欲しいなら `axis` を指定する。

```python
a = np.array([[1, 5], [7, 3]])
np.argmax(a)          # -> 2       全体を 1 列に並べた通し番号
np.argmax(a, axis=1)  # -> [1, 0]  行ごと
```

### `np.diff` — 隣接要素の差

```python
np.diff([0.62, 1.87, 3.12])    # -> [1.25, 1.25]
```

### 応用例: 振り子の周期を測る

```python
idx = np.flatnonzero((q[:-1] > 0) & (q[1:] <= 0))   # 下降ゼロ交差の位置
period = np.diff(t[idx]).mean()                      # 交差時刻の間隔の平均
```

「今はプラス、次はマイナス以下」＝角度が上から下へゼロを横切った瞬間。
同じ向きの交差の間隔がちょうど 1 周期になる。

## 報酬・観測の設計（Step 9）

### 報酬ハッキング (reward hacking)

**方策が報酬を高くする方法を見つけたが、それが設計者の意図した振る舞いではない**こと。
学習もコードも正しく、**報酬関数が意図を正確に表していなかった**だけなので、
デバッガでは見つからない。方策の動きを見て初めて気づく。

振り子での実例（9-a、3 シード実測）:

```
-cos(theta) - 0.01*omega**2 - 0.001*torque**2        成功時 +32.11
-cos(theta) + 0.1*abs(omega) - 0.001*torque**2       -632.94  <- 回り続ける
                ^^^^^^^^^^^^ 「振り上げを促す」つもりで足した
```

`+0.1|ω|` 版はランダム方策（−499.50）より悪い。**学習したせいで、何もしないより悪くなった**。

### 動き出す得

報酬を書いた直後に計算する検査値。**「やってほしい動作の 1 歩」−「何もしない 1 歩」**の報酬差。

| 報酬 | 動き出す得 | 結果（3 シード） |
|---|---|---|
| `-cosθ - 0.01ω² - 0.001τ²` | **+0.4125** | 1/3 成功 |
| `0.6exp(-5e²) + 0.3exp(-0.2ω²) + 0.1exp(-11τ²)` | **−0.3934** | 0/3。一度も動かない |
| 上に接近項を足して罰を上限 0 にした版 | **+0.0078** | 0/3。一度も動かない |
| 接近項の幅を 0.7 に広げた版 | **+0.2311** | 1/3 成功 |

**0 以下なら絶対に学習しない。小さすぎても学習しない。** 1 秒で済む検査で、
40 分の学習を守れる。

### 指数型報酬 `exp(-k·e²)` と `e_half`

誤差 `e` を **必ず 0〜1 に収める**報酬の形。単位が何であっても出てくる値は 0〜1 なので、
重みを足して 1 にすれば**重みが純粋な優先順位になる**。

`k` は直接いじらない。**報酬が半分になる誤差 `e_half` から逆算する**。

```
e_half = sqrt(ln2 / k)        k = ln2 / e_half**2      (ln2 = 0.6931)
```

| k | e_half | 角度なら |
|---|---|---|
| 1 | 0.8326 | 47.70 度 |
| 5 | 0.3723 | 21.33 度 |
| 20 | 0.1862 | 10.67 度 |
| 100 | 0.0833 | 4.77 度 |

**弱点**: 遠いところでは傾きが 0 になり、何も教えてくれない。
「そこに到達する」仕事は別の項（`-cosθ` など、幅の広い項）に任せる。

MuJoCo Playground の Go1 も `exp(-e²/0.25) = exp(-4e²)`、
つまり **`e_half` = 0.4163 m/s**（速度誤差 0.42 m/s で報酬が半分）。

### 正則化項は「上限 0 の罰」にする

`exp(-k·ω²)` をそのまま正の報酬として足すと、**何もしないだけで満点がもらえる**。
`exp(-k·ω²) - 1` にすれば上限 0 の罰になり、この罠が消える。

Go1 の報酬 16 項のうち**正は 4 つだけ、残り 12 は罰**。

### ablation（アブレーション）

**部品を 1 つずつ外して、性能がどう変わるかを測る**こと。鉄則は
**採点を常に「全部入り」のものさしで行う**こと（学習に使う報酬は変えてよい）。

振り子での注意点（9-c 実測）:

- **1 シードだときれいな順位が出るが、全部間違っている**
- 結果が**二値**（+30 付近か −400 付近）なので、**平均値に意味がない**
- 成功率 1/3 と 2/3 を見分けるには **約 50 シード**（3 シードでは検出力 27.8%）

### 特権情報 (privileged information)

**シミュレータでは読めるが、実機では測れない量**。摩擦係数、リンクの正確な質量、
外力、地形の高さなど。**Actor（方策）に見せると、実機で入力が無くなって動かない。**

ただし **Critic には見せてよい**。Critic は学習中しか使わず、実機には載らないため。
これを**非対称 Actor-Critic** と呼ぶ。

Playground の Go1:

```python
env.observation_size
# -> {'privileged_state': (123,), 'state': (48,)}
#     Critic 用（特権情報を含む）    Actor 用（実機で取れる量だけ）
```

### 観測の 3 原則

1. **実機で取れるか** — センサで測れない量を入れない
2. **判断に足りるか** — 罰している量が観測から分かるようになっているか
3. **不連続にならないか** — 角度は必ず `cos` と `sin` の組で入れる

`θ` をそのまま入れると、真上のすぐ右（+3.14）と左（−3.14）が **6.28 離れて**見える。
`cos`/`sin` なら 0.004 しか違わない。

**計算できる情報でも、計算済みで渡す。** 観測から `ω` を抜いて
「前回の `cosθ`, `sinθ`」で代用したら、3 シードとも学習しなかった（9-e 実測）。
理論上は差分から速度が出るが、**その取り出し方を学ぶところで詰まる**。

### action rate ペナルティ

`w * (a_t - a_{t-1})**2` を報酬から引く。**行動を急に変えさせない**ための罰。
実機のギアのバックラッシュ・異音・摩耗に効く。

重みの目安は**主目的の 100 分の 1**。Go1 は `tracking_lin_vel` +1.0 に対し
`action_rate` −0.01。罰する量（前回の行動）は**観測にも入れる**こと。

### 符号反転回数

行動の増減が逆転した回数。**報酬にはまったく現れないが、実機では音と摩耗になる**指標。

観測に σ=0.01（1%）のノイズを足すだけで **11.9 → 95.0 回/499 歩**（8 倍）になるのに、
**報酬は −109.77 → −109.72 でまったく変わらない**（9-d 実測）。

```python
s = np.sign(a - prev)
if s != 0 and sign != 0 and s != sign:    # 3 条件とも必要
    n_rev += 1
```

`np.sign(0.0)` は `0.0` なので、これを「符号が違う」と数えると
**止まっている方策が最大の反転回数を記録する**。

### 初期状態のランダム化

学習時だけ初期状態を広げる。**Step 9 で最も効果が大きかった 1 行**（9-e 実測、3 シード）。

| 学習時の初期状態 | 成功 | 標準偏差 |
|---|---|---|
| `±0.1` rad | 1/3 | 218.04 |
| **全周 `±π`** | **3/3** | **42.87** |

**採点は既定（±0.1）のままにする。** ただし成功時の上端時間は 221.1 → 207.5 と
わずかに落ちる（**確実さを買って、尖りを売る**取引）。
Step 11 のドメインランダム化は、ばらけさせる対象が質量・摩擦に変わっただけの同じ発想。

## 高速化（Step 10）

### ボトルネックはどこか

振り子（`nq=1`）での実測:

| | physics-steps/s |
|---|---|
| 物理だけ回す | **704,073** |
| 学習させたとき（最速の設定） | **55,650** |

**92% が Python と PyTorch の事務処理で消えている。**
方策の推論 1 回（35.70 μs）が、**物理 10 歩（17.37 μs）より重い**。
パラメータは 4,547 個しかないのに。

### 並列環境が速い理由

**物理を N コアで並列に回すからではなく、方策の推論を N 体まとめて 1 回で済ませるから。**

| バッチ | 推論 1 回 | 1 環境あたり |
|---|---|---|
| 1 | 35.70 μs | 35.70 μs |
| 64 | 53.23 μs | **0.83 μs**（42.9 倍安い） |

だから `DummyVecEnv`（1 プロセスで順番に回す）でもほぼ同じ効果が出る。
実測では **`DummyVecEnv` の `n_envs=2`（5,347）が、`SubprocVecEnv` の
`n_envs=4`（3,844）より速い**。天井は 5,565 env-steps/s で、1 体の **1.62 倍だけ**。

`SubprocVecEnv` はプロセス間通信のコストがあるので、**環境 1 ステップが重いとき**
（四足歩行など）に初めて正しく効く。

### MJX

MuJoCo を JAX で書き直したもの。**書き換えは機械的**で、違いは 1 点だけ。

| | MuJoCo | MJX |
|---|---|---|
| 1 歩 | `mujoco.mj_step(m, d)` が `d` を書き換える | `dx = mjx.step(mx, dx)` が**新しい dx を返す** |
| 指令 | `d.ctrl[0] = 0.5` | `dx = dx.replace(ctrl=jp.array([0.5]))` |

**戻り値を捨てると何も起きない**のが最頻出のミス。

**1 体だと CPU より遅い**（振り子で CPU の 145 分の 1）。損益分岐点は **128〜192 体**。
16,384 体で 22,716,708 physics-steps/s（CPU 1 体の 32.3 倍、学習同士なら 408 倍）。

衝突は **27 通りしか実装されていない**（`BOX`×`CYLINDER` などは不可）。
接触する geom は `SPHERE` / `CAPSULE` に寄せるのが定番。

### JAX の 5 つの約束

すべて **「値は実行時までわからない」**（トレースして GPU 用に翻訳する）ことから来る。

1. **配列は書き換えない** — `x.at[0].set(99.0)` が新しい配列を返す
2. **`jit` でまとめてコンパイル** — 実測 93 倍。最初の 1 回だけ遅い
3. **`vmap` で 1 体ぶんの関数を N 体に** — 中身は 1 文字も変えない
4. **`if` と可変長 `for` は書けない** — `jp.where` / `lax.cond` / `lax.fori_loop`
5. **乱数は鍵を持ち回す** — `key, subkey = jax.random.split(key)`

速度を測るときは **`block_until_ready()`** を忘れない（JAX の計算は非同期なので、
入れないとありえない速さが出る）。
