ネットワークの形を読む

algos/ppo_min.py の ActorCritic を、 1 行ずつ・1 次元ずつ追いかける。 形を読めるようになると、PyTorch のバグの大半は目で見つかる。

30 分 Step 8-a の補助 PyTorch 2.14.0 で検証
00

この教材について

この教材のねらい

8-a で書いた ActorCritic は 20 行ほどですが、 数字が 6 種類（3・64・1・4・−1・4547）出てきます。 どれが何で、どこから来て、変えられるのはどれか——そこだけを扱います。

PyTorch のバグの多くは「形が合っていないのにエラーが出ない」という形で現れます。 形を読めることが唯一の防御です。

import torch
from torch import nn


class ActorCritic(nn.Module):
  def __init__(self, obs_dim, act_dim, hidden=64):
    super().__init__()
    self.shared = nn.Sequential(
      nn.Linear(obs_dim, hidden),
      nn.Tanh(),
      nn.Linear(hidden, hidden),
      nn.Tanh(),
    )
    self.mu = nn.Linear(hidden, act_dim)   # Actor: 行動の平均
    self.v = nn.Linear(hidden, 1)          # Critic: 価値
    self.log_std = nn.Parameter(torch.zeros(act_dim))

  def forward(self, obs):
    h = self.shared(obs)
    return self.mu(h), self.v(h).squeeze(-1), self.log_std


net = ActorCritic(obs_dim=3, act_dim=1)
obs = torch.randn(4, 3)
mu, v, log_std = net(obs)
01

2 種類の次元 — 変えられるものと、変えられないもの

この節のねらい

最初にいちばん大事な区別を置きます。 ここを取り違えると、以降の説明が全部ずれます。

obs = torch.randn(4, 3) の 4 と 3 は、性格がまったく違います。

43
呼び名バッチ次元特徴次元
意味何個まとめて処理するか1 個が何個の数でできているか
決めるもの都合（速さ・メモリ）タスクの中身（6-a の観測設計）
変えられるか自由に変えられる変えるとエラー
ネットが見るか見ない。素通り見る

3 は 6-a で決めました 観測を [cosθ, sinθ, ω] にしたので 3 です。 この 3 を変えるにはタスクの設計から変える必要があります。

4 は「たまたま」です 動作確認で複数個あればよかったので 4 にしました。 ただし 7-a で n_envs=4 にしていたので、 実際の学習でもこの形は出てきます——環境 4 つが同時に観測を返すので。

実測: バッチは自由

obs=(1, 3)     ->  mu=(1, 1)     v=(1,)
obs=(4, 3)     ->  mu=(4, 1)     v=(4,)
obs=(7, 3)     ->  mu=(7, 1)     v=(7,)
obs=(2048, 3)  ->  mu=(2048, 1)  v=(2048,)

実測: 特徴次元は固定

obs=(4, 2) -> RuntimeError: mat1 and mat2 shapes cannot be multiplied (4x2 and 3x64)
obs=(4, 3) -> OK
obs=(4, 4) -> RuntimeError: mat1 and mat2 shapes cannot be multiplied (4x4 and 3x64)

エラーメッセージの読み方 (4x2 and 3x64) は「4×2 の行列と 3×64 の行列を掛けようとした」という意味。 行列の積は左の列数と右の行数が一致しないと成立しません（2 ≠ 3）。 この形のエラーが出たら、必ず特徴次元の食い違いです。

学習中もバッチサイズは変わり続けます
場面バッチ
データ収集（7-a の n_envs=4）4
更新（PPO の既定 batch_size=64）64
評価（1 環境ずつ）1

同じネットが全部を処理します。 バッチ次元を固定しない設計になっているのはこのためで、 7-a の「PPO は並列化が得意」の実装上の理由でもあります—— 環境を 16 個に増やしても、ネット側は (16, 3) を受け取るだけで何も変わりません。

02

nn.Linear は何をするか

この節のねらい

nn.Linear はこのコードに 4 回出てきます。 この 1 つを理解すれば、形の話は 8 割終わります。

nn.Linear(a, b) は「a 個の数を受け取って b 個の数にする」変換です。

y = x @ W.T + b
形中身
x（入力）(..., a)最後が a ならよい
W（weight）(b, a)(出力, 入力) の順。逆に見えるので注意
b（bias）(b,)出力ごとに 1 個足す
y（出力）(..., b)最後だけが b に変わる

肝心なのは「最後の次元しか見ない」こと

lin = nn.Linear(3, 64)

入力 (3,)       ->  出力 (64,)          # 1 個だけ
入力 (4, 3)     ->  出力 (4, 64)        # 4 個まとめて
入力 (2, 4, 3)  ->  出力 (2, 4, 64)     # 2x4 個まとめて

手前の次元は素通りします (4, 3) を渡すと、4 個それぞれに同じ変換を それぞれ独立に適用して (4, 64) を返す。 4 という数はどこにも記憶されません。 だから次に (7, 3) を渡しても何も問題が起きません。

weight の形が (64, 3) なのはなぜか

nn.Linear(3, 64) と書いたのに weight.shape は (64, 3) です （実測で確認）。

行列の積 x @ W.T で計算するためです。 x が (4, 3)、W.T が (3, 64) なので (4, 3) @ (3, 64) = (4, 64)。 引数の順（入力, 出力）と weight の形（出力, 入力）が逆なのは、 PyTorch でよく引っかかる点です。

Tanh は形を変えません

nn.Tanh() は各要素を tanh に通すだけです。 形は完全にそのまま。(4, 64) は (4, 64) のまま出てきます。

ではなぜ挟むのか これが無いと層を重ねる意味が無くなります。 Linear は線形変換なので、2 つ続けても1 つの線形変換にまとめられてしまう。 間に非線形な関数を挟むことで、初めて「深い」ネットになります。 形の話には関係しないので、以降は無視して構いません。

03

1 行ずつ形を追う

この節のねらい

forward() の 3 行を、1 つずつ形を書きながら追います。 これができれば、この教材の目的は達成です。

def forward(self, obs):          # obs: (4, 3)
    h = self.shared(obs)         # h:   (4, 64)
    return self.mu(h), self.v(h).squeeze(-1), self.log_std
    #      (4, 1)      (4,)                  (1,)

shared の中も展開すると

処理入力出力何をしたか
obs——(4, 3)観測 4 個
Linear(3, 64)(4, 3)(4, 64)3 → 64 に広げた
Tanh()(4, 64)(4, 64)形は変わらない
Linear(64, 64)(4, 64)(4, 64)64 → 64
Tanh()(4, 64)(4, 64)形は変わらない
ここで枝分かれ
mu = Linear(64, 1)(4, 64)(4, 1)行動の平均
v = Linear(64, 1)(4, 64)(4, 1)価値
.squeeze(-1)(4, 1)(4,)最後の 1 を削った
log_std——(1,)obs を通っていない

バッチの 4 は最初から最後まで変わりません どの行でも先頭が 4 のままです。 「観測 4 個を入れたら、結果も 4 個出てくる」——当たり前ですが、 形を追うときはこれが道標になります。

log_std だけ仲間外れです 表の最後の行を見てください。バッチ次元がありません。 obs を一度も通っていないので当然です—— 8-a で書いたとおり、観測に依存しないパラメータだからです。 (1,) の 1 は act_dim であって、バッチではありません。

64 という数字について

hidden=64 は唯一「自由に決めていい」特徴次元です。 観測の 3 も行動の 1 もタスクが決めますが、途中の太さは設計者が決めます。

大きくすると表現力が上がりますが、パラメータが増えて学習が遅くなります。 連続制御では 64 か 256 が定番で、SB3 の既定も 64 です。 振り子のように観測 3 次元の単純なタスクなら 64 で十分です。

05

squeeze(-1) の理由

この節のねらい

v にだけ付いている .squeeze(-1) を扱います。 これを忘れると、エラーを出さずに損失が狂います。実測で見せます。

何をする関数か

サイズが 1 の次元を削除します。-1 は「最後の次元」の意味。

(4, 1)     -> squeeze(-1) -> (4,)        # サイズ 1 なので削られる
(4,)       -> squeeze(-1) -> (4,)        # 何も起きない
(4, 12)    -> squeeze(-1) -> (4, 12)     # サイズ 12 なので削られない
(2, 4, 1)  -> squeeze(-1) -> (2, 4)

なぜ v だけか

形意味12 関節なら
v(4,)状態ごとにスカラー 1 個(4,) のまま
mu(4, 1)行動の次元ごとに 1 個(4, 12)

役割が違います mu は行動の次元を持つべき量なので、 たまたま act_dim=1 でも (4, 1) のまま残します。 ここで squeeze すると、12 関節にしたときだけ形が変わって扱いが揃いません。

v は本質的にスカラーです。 価値は「その状態がどれくらい良いか」を表す 1 個の数で、 行動が何個あろうと 1 個。 だから (4, 1) という余計な次元を持たせません。

忘れるとどうなるか — 実測

価値の損失は (収益 − V)² の平均で計算します。 squeeze を忘れると形が合わないまま計算が通ります。

収益 r = [1.0, 2.0, 3.0, 4.0]            # (4,)
V     = [[0.5], [1.0], [1.5], [2.0]]    # (4, 1)  squeeze 忘れ

(r - V).shape = (4, 4)                  # エラーが出ずに 4x4 の行列に
損失          = 3.125                   # 間違い
正しくは      = 1.875
エラーが出ないのが最悪なところです

(4,) と (4, 1) の引き算は、ブロードキャストという仕組みで (4, 4) に膨らみます。全組み合わせの差が計算されてしまう。

学習は普通に進みます。損失の値が違うだけなので、 「なんか性能が出ないな」で終わります。 Step 6 から何度も出てきた「静かに壊れる」の仲間で、 PyTorch でいちばん多いバグの 1 つです。

防ぎ方

形が気になったら print する。これに尽きます。

print(f"{r.shape=}  {v.shape=}  {(r-v).shape=}")

Python 3.8 以降の f"{x=}" という書き方を使うと、 変数名と値が両方出ます。デバッグのとき便利です。

この節のねらい

8-a で出てきた 4,547 という数の内訳を見ます。 どこが重いかが分かると、設計の勘所が掴めます。

9 割が shared.2 です 64 × 64 = 4096——全体の 90% がこの 1 つの層に集中しています。 観測が 3 次元しかないので入口は軽く、出口も 1 次元なので軽い。 太い層どうしを繋ぐところだけが重いのです。

構成を変えたとき

hidden だけが 2 乗で効きます hidden × hidden の層があるからです。 観測や行動の次元は1 乗でしか効きません。

だから「四足歩行だから大きいネットが要る」とは限りません 観測 48・行動 12 でも 8,153 個——振り子の 1.8 倍です。 タスクの難しさとネットの大きさは、直接は結びつきません。

画像を使うと話が変わります

観測がカメラ画像（64×64×3 = 12,288 次元）になると、 入口の層だけで 12288 × 64 = 786,432 個になります。 そこで畳み込み層が必要になるわけですが、 Phase D まで画像は使いません。

07

よくある形のエラー

この節のねらい

8-b 以降で実際に遭遇するものを先にまとめます。 「ハマる前に書いておく」ためです。

症状原因直し方
mat1 and mat2 shapes cannot be multiplied (4x2 and 3x64) 特徴次元の食い違い。観測が 2 次元なのにネットは 3 次元を期待 obs_dim と実際の観測を揃える
エラーは出ないが損失が変 squeeze(-1) 忘れ。(4,) と (4,1) がブロードキャスト 引き算の前に両方 print
Expected all tensors to be on the same device CPU と GPU が混ざっている 今回は CPU のみなので起きない
expected scalar type Float but found Double NumPy の既定が float64、PyTorch は float32 torch.as_tensor(x, dtype=torch.float32)
too many values to unpack 戻り値の個数が合っていない forward の return を確認
1 次元のバッチで落ちる (3,) を渡した。バッチ次元が無い obs[None] か obs.unsqueeze(0) で (1, 3) にする
float32 の話は 6-a と繋がっています

6-a で観測に dtype=np.float32 を付けたのを覚えていますか。 NumPy の既定は float64 なので、付けないと check_env で弾かれました。

PyTorch 側もfloat32 が既定です。 両方を float32 で揃えておくと、この種のエラーがまとめて消えます—— 6-a であの一手間をかけた理由がここでも効いています。

この教材のまとめ
  1. 次元は 2 種類。バッチ（自由に変わる／ネットは見ない）と 特徴（タスクが決める／合わないとエラー）
  2. nn.Linear(a, b) は最後の次元だけを a から b に変える。 手前は素通り
  3. weight の形は (出力, 入力)。引数の順と逆
  4. Tanh は形を変えない。形の話では無視してよい
  5. v だけ squeeze(-1) するのは本質的にスカラーだから。 忘れるとエラー無しで損失が狂う（3.125 対 1.875）
  6. パラメータの9 割が hidden × hidden の層。 hidden だけが 2 乗で効く
