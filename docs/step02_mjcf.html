01

XML をファイルに分離する

Step 1 では Python の文字列に埋め込んでいた。これを独立したファイルにする。 モデルとコードを分けるのは、単なる整理ではなく 実務上の必然。

  • 同じモデルを複数のスクリプト（可視化・学習・評価）から使い回せる
  • エディタが XML として色分け・補完してくれる
  • git の差分が読める。「モデルを変えたから性能が変わった」を追跡できる
  • Step 12 で CAD から生成した MJCF を差し替えるとき、コードを触らずに済む

モデルを表示するだけの汎用ビューア

モデルを作るたびにスクリプトを書き換えるのは面倒なので、 ファイル名を引数で受け取る汎用ビューアを 1 本用意しておく。 Step 12 まで使い回すことになる、この講座で最も出番の多いツール。

重要: 既定は「物理を進めない」

書いたばかりのモデルを確認したいとき、物理を進めてはいけない。 重力で一瞬にして崩れ落ち、何がどう繋がっているのか観察できないから。
mj_forward だけを呼んで初期姿勢のまま静止表示するのが、 モデルを点検する正しいやり方。動かしたいときだけ --sim を付ける。

# sim/view_model.py — models/ 以下の MJCF を読み込んで表示する
import argparse
import time
from pathlib import Path

import mujoco
import mujoco.viewer

ROOT = Path(__file__).resolve().parent.parent
MODELS = ROOT / "models"

# mjtJoint の並び順（0=free, 1=ball, 2=slide, 3=hinge）
JOINT_TYPES = ("free", "ball", "slide", "hinge")


def load(name):
    path = MODELS / name
    if not path.exists():
        available = [p.name for p in sorted(MODELS.glob("*.xml"))]
        raise SystemExit(f"モデルが見つかりません: {path}\n利用可能: {available}")
    try:
        return mujoco.MjModel.from_xml_path(str(path))
    except Exception as e:
        # MJCF のコンパイルエラーはここに来る。行番号が出るのでそのまま読む
        raise SystemExit(f"MJCF の読み込みに失敗しました:\n{e}")


def summary(model):
    """モデルの構造を表示する。書いた MJCF が意図どおりか確認するために毎回見る。"""
    print(f"nq={model.nq}  nv={model.nv}  nu={model.nu}  "
          f"nbody={model.nbody}  njnt={model.njnt}  nsensordata={model.nsensordata}")

    for j in range(model.njnt):
        name = mujoco.mj_id2name(model, mujoco.mjtObj.mjOBJ_JOINT, j)
        jtype = JOINT_TYPES[model.jnt_type[j]]
        print(f"  joint[{j}] {name:<12} {jtype:<6} "
              f"qposadr={model.jnt_qposadr[j]} dofadr={model.jnt_dofadr[j]}")

    for a in range(model.nu):
        name = mujoco.mj_id2name(model, mujoco.mjtObj.mjOBJ_ACTUATOR, a)
        print(f"  actuator[{a}] {name:<12} ctrlrange={model.actuator_ctrlrange[a]}")


def main():
    parser = argparse.ArgumentParser(description="MJCF を読み込んで表示する")
    parser.add_argument("model", help="models/ 以下のファイル名 (例: cartpole.xml)")
    parser.add_argument("--sim", action="store_true", help="物理を進める（既定は静止表示）")
    parser.add_argument("--speed", type=float, default=1.0, help="再生速度の倍率")
    args = parser.parse_args()

    model = load(args.model)
    data = mujoco.MjData(model)
    summary(model)

    mujoco.mj_forward(model, data)   # 進めずに派生量だけ計算（xpos などを埋める）

    with mujoco.viewer.launch_passive(model, data) as viewer:
        while viewer.is_running():
            t0 = time.time()

            if args.sim:
                mujoco.mj_step(model, data)
                viewer.sync()
                wait = model.opt.timestep / args.speed - (time.time() - t0)
                if wait > 0:
                    time.sleep(wait)
            else:
                viewer.sync()
                time.sleep(1 / 60)       # 静止表示なら 60Hz で十分


if __name__ == "__main__":
    main()

使い方

# 書いたモデルを静止状態で点検する（まずこれ）
uv run python sim/view_model.py pendulum.xml

# 物理を進めて動かす
uv run python sim/view_model.py pendulum.xml --sim

# ゆっくり見る
uv run python sim/view_model.py cartpole.xml --sim --speed 0.25

起動すると、まず構造がコンソールに出る。MJCF を書いたら必ずこれを見ること。 ビューアを眺める前に、数字が意図どおりかを確認するほうが速い。

nq=2  nv=2  nu=1  nbody=3  njnt=2  nsensordata=0
  joint[0] slider       slide  qposadr=0 dofadr=0
  joint[1] hinge        hinge  qposadr=1 dofadr=1
  actuator[0] slide_motor  ctrlrange=[-3.  3.]

モデル点検のチェックポイント

  • nu が 0 なら <actuator> の書き忘れ
  • njnt が想定より少なければ <joint> の書き忘れ。その body は親に溶接されている
  • joint の型が意図と違えば type のタイポ
  • ctrlrange が [0. 0.] なら未指定。実機のトルク上限を反映させること
  • ビューアでは Rendering パネルの Joint を ON にして、関節軸の向きを目視確認する
02

MJCF の全体構造

MJCF ファイルは <mujoco> を根とする木。 トップレベルの要素は役割ごとに分かれていて、書く順番も慣例で決まっている。

03 · 最初の罠

角度の単位はデフォルトで「度」

MJCF の角度はデフォルトで degree（度）。 一方 Python 側の data.qpos は常に radian（ラジアン）。 この不一致が、初学者が最初に踏む地雷になる。

場所単位例
MJCF の euler / axisangle / joint の range degree（デフォルト）range="-90 90"
Python の data.qpos / qvel radian（常に）data.qpos[0] = 1.57

混乱を避けるため、最初の 1 行でラジアンに統一することを強く勧める。

<compiler angle="radian"/>

こう書いておけば XML も Python も全部ラジアンになり、頭を切り替えずに済む。 ロボティクスの論文・ライブラリはほぼラジアンなので、そちらに合わせるほうが後々楽。

他人のモデルを読むとき

MuJoCo 公式のサンプルや配布されているロボットモデルには angle="radian" が書かれていないものも多い。その場合は degree で解釈される。 他人の MJCF を読むときは、まず <compiler> 行を確認する癖をつけること。 ここを見落とすと、関節の可動範囲が 57 倍ずれる。

04 · 核心

body ツリーと親相対座標

MJCF でいちばん重要な概念。すべての pos は親から見た相対位置であり、 ワールド座標ではない。多関節ロボットが破綻なく組めるのはこの仕組みのおかげ。

<worldbody>
  <body name="upper" pos="0 0 1">              <!-- world から見て高さ 1m -->
    <joint name="j1" type="hinge" axis="0 1 0"/>
    <geom type="capsule" fromto="0 0 0  0 0 -0.5" size="0.02"/>

    <body name="lower" pos="0 0 -0.5">         <!-- upper から見て 0.5m 下 -->
      <joint name="j2" type="hinge" axis="0 1 0"/>
      <geom type="capsule" fromto="0 0 0  0 0 -0.4" size="0.02"/>
    </body>
  </body>
</worldbody>

lower の pos="0 0 -0.5" は「ワールドの高さ 0.5m」ではなく 「upper の原点から 0.5m 下」。しかも upper が j1 で回転すれば、 lower は回転した先へ一緒に付いていく。 これが親相対座標の本質で、ロボットアームも脚も、この入れ子で表現される。

動かして確かめる

親フレームの位置と回転、子フレームの相対位置を変えると、 子のワールド座標がどう決まるかを見る。親を回すと子の相対位置がどう効くかに注目。

子のworld座標 = 親のworld座標 + R(親の回転) × 子の相対座標
親の回転行列 R が子の相対位置に掛かる、という一点だけ理解すれば十分。 この計算を全 body について根から順に行うのが順運動学であり、 mj_step が毎回やっている最初の仕事（Step 1 で見た qpos → xpos）。

回転の書き方は 4 通りある

属性形式使いどころ
quatw x y zデフォルト。数値的に安全だが人間には読めない

zaxisx y zz 軸をこの向きに合わせる。円筒形の部品を向けるのに便利
05

joint — 自由度を作る

<joint> は「親 body に対してこの body がどう動けるか」の宣言。 joint を書かなければ、その body は親に溶接されて動かない。

type自由度nqnv実機での例
hinge111回転関節。サーボモータ、蝶番
slide111直動関節。リニアガイド、カートのレール
ball343球関節。肩、ジンバル
free676宙に浮いた物体。四足の胴体、ドローン

主要な属性

属性意味実機との対応
axis回転軸・並進軸の方向（親座標系）モータの取り付け向き
pos関節の位置（body 座標系）軸受けの位置
range可動範囲メカストッパ、サーボの可動域
damping粘性抵抗 τ = -c·q̇グリス粘性、軸受けの抵抗
frictionlossクーロン摩擦（速度によらない一定の抵抗）減速機の摩擦。実機で非常に大きい
armature関節に付加される見かけの慣性モータ回転子の慣性 × 減速比²
stiffnessバネ定数ゴム、板バネ
Step 11 への伏線: armature と frictionloss

この 2 つは今すぐ使わないが、Sim2Real で決定的に効くので名前だけ覚えておくこと。
減速機付きサーボは、モータ回転子が減速比の 2 乗倍の慣性として関節に効く（armature）。 ギヤには速度によらない摩擦がある（frictionloss）。 この 2 つを入れないシミュレーションは実機よりずっと軽やかに動いてしまい、 そこで学習した方策は実機で通用しない。sim2real ギャップの主要因のひとつ。

06

geom — 形と質量

Step 1 で見たとおり、質量と慣性は geom の形状から自動計算される（密度デフォルト 1000 kg/m³）。

size の意味は type ごとに違う

ここが 2 番目の罠。box は「半分の長さ」を指定する。

typesize の意味例
sphere半径size="0.05"
capsule半径（fromto 併用時）size="0.02"
cylinder半径, 半分の高さsize="0.05 0.1"
box各辺の半分の長さ（X,Y,Z）size="0.1 0.1 0.1" → 20cm 立方体
planeX 半幅, Y 半幅, グリッド間隔size="2 2 0.1"

質量を明示したいとき

実機の部品は密度が一様ではない。実測した重さを直接書くほうが正確。

<geom type="box" size="0.1 0.05 0.02" mass="0.35"/>      <!-- 質量を直接指定 -->
<geom type="box" size="0.1 0.05 0.02" density="2700"/>   <!-- アルミの密度 -->

さらに正確を期すなら、慣性テンソルごと明示できる。CAD から取り出した値を入れる用途で、 Step 12 の実機モデリングで使うことになる。

<body name="link">
  <inertial pos="0 0 -0.12" mass="0.42" diaginertia="0.0021 0.0021 0.0003"/>
  <geom type="mesh" mesh="link_mesh"/>   <!-- 見た目だけ。慣性は上で決まる -->
</body>
衝突と見た目を分ける

実務では 1 つの body に「見た目用の精密メッシュ」と「衝突判定用の単純な形」を 別々に持たせる。contype="0" conaffinity="0" を付けた geom は 衝突計算に参加せず、描画だけされる。メッシュ同士の衝突判定は非常に重いので、 衝突用には box や capsule を使う。Step 10 で速度が問題になったとき効いてくる。

07

見た目を整える — 明るいシーンの作り方

MuJoCo の既定の見た目は暗い。これは意図的な控えめ設定で、 モデルが悪いわけではない。描画設定は物理に一切影響しないので、 安心して好きに変えてよい。

なぜ暗いのか

既定値を実際に読み出すと、原因がはっきりする。

headlight.ambient = [0.1 0.1 0.1]     # 環境光がほぼ無い
headlight.diffuse = [0.4 0.4 0.4]     # 主光源も弱い
geom の既定 rgba  = [0.5 0.5 0.5 1]   # 中間グレー = 暗く見える

<light> を 1 つも書かないと、この弱いヘッドライトだけがシーンを照らす。 床も既定の中間グレーなので、全体がくすんで見える。

明るいシーンの一式

下の 3 ブロックを <worldbody> の前に置き、床に material="grid" を付ける。 これで一般的な MuJoCo デモと同等の見た目になる。

<visual>
  <headlight ambient="0.30 0.30 0.30" diffuse="0.35 0.35 0.35" specular="0.05 0.05 0.05"/>
  <rgba haze="0.87 0.90 0.92 1"/>
  <global azimuth="140" elevation="-20"/>
  <quality shadowsize="4096"/>
</visual>

<asset>
  <!-- 空。上から下へのグラデーション -->
  <texture type="skybox" builtin="gradient" rgb1="0.62 0.74 0.86" rgb2="0.94 0.96 0.97" width="512" height="3072"/>

  <!-- 床のチェッカー模様。スケール感が掴めるので必ず入れる -->
  <texture type="2d" name="grid" builtin="checker" mark="edge" rgb1="0.85 0.87 0.86" rgb2="0.55 0.60 0.58" markrgb="0.35 0.38 0.36" width="300" height="300"/>
  <material name="grid" texture="grid" texrepeat="4 4" texuniform="true" reflectance="0.05"/>

  <!-- リンク用のマテリアル。色をここで一元管理できる -->
  <material name="link" rgba="0.25 0.45 0.85 1" specular="0.3" shininess="0.4"/>
</asset>

<worldbody>
  <!-- キーライト: 影を落とす主光源 -->
  <light name="key" pos="1.5 -1.5 3" dir="-0.4 0.4 -1" directional="true" diffuse="0.45 0.45 0.45" specular="0.15 0.15 0.15" castshadow="true"/>

  <!-- フィルライト: 反対側から弱く当てて影を潰しすぎない -->
  <light name="fill" pos="-2 2 2.5" dir="0.5 -0.5 -1" directional="true" diffuse="0.15 0.15 0.15" castshadow="false"/>

  <geom name="floor" type="plane" size="3 3 0.05" material="grid"/>

  <!-- ここから下がロボット本体 -->
</worldbody>
最重要: 光量は足し算になる

MuJoCo の明るさは ヘッドライト ＋ 各 light の合計で決まる。 ヘッドライトを上げたまま <light> を 2 灯足すと合計が 1.0 を大きく超え、 床が真っ白に飛んでチェッカー模様が消える。
上の設定はこのバランスを取ってある。<light> を明示的に置くなら ヘッドライトは 0.3 前後まで下げること。逆にライトを置かないなら ヘッドライトを 0.45 / 0.75 くらいまで上げてよい。

チェッカーが見えないときの診断

白飛びのほかに、2 色の差が小さすぎて見えないケースがある。 rgb1 と rgb2 の差は 0.25 以上取ること。 差が 0.1 程度だと、少し明るくしただけで消える。
テクスチャ自体が適用されているかは Python 側で確認できる。

fid = mujoco.mj_name2id(model, mujoco.mjtObj.mjOBJ_GEOM, "floor")
print("matid   ", model.geom_matid[fid])      # -1 ならマテリアル未適用
print("texid   ", model.mat_texid[model.geom_matid[fid]])
print("texrepeat", model.mat_texrepeat)

matid が -1 なら material="grid" の書き忘れかタイポ。 -1 でないのに見えないなら、原因は光量かコントラスト。

それぞれ何をしているか

要素・属性効果
headlight ambient全方向から当たる環境光。上げると影の中も見えるようになる
headlight diffuseカメラ位置から当たる主光源。全体の明るさ
global azimuth / elevation起動時のカメラ角度。毎回マウスで回さずに済む
quality shadowsize影の解像度。既定は粗いのでギザギザする
texture skybox背景。空があると奥行きが出て姿勢が読み取りやすい
texture checker + material床の格子模様。スケール感と移動量が目で分かる
light directional="true"平行光線（太陽光）。位置ではなく dir の向きだけが効く
castshadow影を落とすか。影があると 3D の奥行きが一気に分かる
material色・光沢の定義。複数 geom で共有でき、色の一元管理ができる
床のチェッカーは実用装備

見栄えの問題ではない。格子があるとロボットがどれだけ移動したか目で測れる。 単色の床では、カメラが動いているのかロボットが動いているのか区別がつかない。 Step 10 で歩行を見るとき、これが無いと進んでいるかどうか判定できない。

カメラを配置する

既定の「フリーカメラ」はマウスで回す軌道カメラで、起動時の距離は 1.5 × model.stat.extent、注視点は model.stat.center で決まる。

<statistic extent="4" center="0 0 0.5"/>    <!-- 計算上のカメラ距離は 6.0 -->
注意: statistic はビューアに効かないことがある

<statistic extent> が変えるのは フリーカメラの初期距離の計算値だけで、 インタラクティブビューア（launch_passive）はこれを初期カメラに反映しないことがある。 実際 mjv_defaultFreeCamera が 6.0 を返していても、ビューアの見た目が変わらない。
XML だけで確実に決めたいなら、次の「固定カメラを起動時カメラにする」を使う。

固定カメラを起動時カメラにする（確実）

<camera> を定義し、<global cameraid> でそれを起動時カメラに指定する。 引き具合はカメラの pos そのものになるので、曖昧さがない。

<visual>
  <global azimuth="140" elevation="-20" cameraid="0"/>   <!-- 0 番のカメラで起動 -->
</visual>

<worldbody>
  <camera name="main" pos="0 -6 1.5" mode="targetbody" target="upper"/>
  ...
</worldbody>
launch_passive は cameraid を自動では見ない

mujoco.viewer.launch_passive は mujoco.MjvCamera() を まっさらな状態で作ってビューアに渡す実装になっており、 model.vis.global_.cameraid を読まない。 つまり XML に cameraid を書いてもフリーカメラのまま起動する。
設定は XML に置いたまま、スクリプト側でそれを反映する 3 行を書けばよい。 この 3 行は汎用なので、以後どのモデルでも XML だけで制御できるようになる。

with mujoco.viewer.launch_passive(model, data) as viewer:
    # XML の <global cameraid="..."> を反映する
    if model.vis.global_.cameraid >= 0:
        viewer.cam.type = mujoco.mjtCamera.mjCAMERA_FIXED
        viewer.cam.fixedcamid = model.vis.global_.cameraid

    while viewer.is_running():
        ...

ビューア左パネルの Camera セレクタに Free / main が並んでいれば、 カメラ定義自体は正しく読まれている。手動で切り替えることもできる。

cameraid は <camera> を定義した順のインデックス（1 台目が 0）。 -1 がフリーカメラで、これが既定。 ビューアの Camera セレクタで Free に戻せば、いつでもマウス操作の軌道カメラに切り替わる。

設定効く対象確実性
<statistic extent>フリーカメラの初期距離ビューアでは反映されないことがある
<camera> + <global cameraid>起動時カメラそのもの確実。ただし launch_passive では上の 3 行で反映が必要
viewer.cam.distance（Python）実行時の上書き確実。ただしスクリプトごと

好きな位置から見たいなら <camera> を置く。何台でも定義でき、 ビューアの Camera セレクタで切り替えられる。

<worldbody>
  <!-- 横から。targetbody なら常に対象を向くので向きの計算が不要 -->
  <camera name="side" pos="0 -3.5 1.2" mode="targetbody" target="upper"/>

  <!-- 正面から。xyaxes で向きを直接指定 -->
  <camera name="front" pos="3.5 0 1.0" xyaxes="0 1 0  0 0 1"/>

  <!-- 真上から -->
  <camera name="top" pos="0 0 4" xyaxes="1 0 0  0 1 0"/>
</worldbody>

xyaxes は「カメラの x 軸と y 軸を world のどの向きに合わせるか」の指定。 カメラは自分の -z 方向を見る。慣れるまでは targetbody のほうが楽。

mode挙動使いどころ
fixed（既定）置いた場所に固定定点観測、動画撮影
targetbody位置は固定、常に対象を向く振り子・アームの観察
track対象と一緒に移動、向きはワールド固定Step 10 の歩行。追いかけカメラ
trackcom重心を追う多リンクの全体を追う

track は追跡したい body の中に置く。歩行ロボットが画面外に出ていかなくなる。

<body name="torso">
  <camera name="follow" pos="0 -3 1" mode="track"/>
  ...
</body>

Python から切り替えるとき、およびオフスクリーン描画のとき:

viewer.cam.type = mujoco.mjtCamera.mjCAMERA_FIXED
viewer.cam.fixedcamid = mujoco.mj_name2id(model, mujoco.mjtObj.mjOBJ_CAMERA, "side")

renderer.update_scene(data, camera="side")     # 動画保存などのオフスクリーン描画
カメラの置き場所は関節軸で決まる

joint が axis="0 1 0"（y 軸まわり）なら、運動は x-z 平面内で起きる。 これを観察するには y 軸上（横）にカメラを置く必要がある。 x 軸上に置くと、曲がっている振り子が真っ直ぐに見えてしまう。
カートポールも同じで、台車が x 方向に動き棒が y 軸まわりに倒れるなら、カメラは -y 側。 関節軸を見れば、どこから見るべきかが決まる。

ワールド原点に 3 軸を表示する

座標軸が見えていると、pos の符号ミスや axis の向き違いが即座に分かる。 方法は 2 つあり、まずは方法 1 で十分。

方法 1: ビューアの Frame 表示（XML 不要・推奨）

ビューア左の Rendering パネル → Frame を World にする。 太い RGB の矢印で原点の 3 軸が出る。Body にすれば全 body の座標系が出るので、 親相対座標がどう積み重なっているかが一目で分かる。

起動時から出しておきたいなら Python から指定する。

with mujoco.viewer.launch_passive(model, data) as viewer:
    with viewer.lock():                                    # UI は別スレッドなのでロックする
        viewer.opt.frame = mujoco.mjtFrame.mjFRAME_WORLD   # 原点の 3 軸
        viewer.opt.flags[mujoco.mjtVisFlag.mjVIS_JOINT] = True   # 関節軸も一緒に
mjtFrame の値表示されるもの
mjFRAME_NONE（既定）なし
mjFRAME_WORLDワールド原点の 3 軸
mjFRAME_BODY全 body の座標系。親相対座標の確認に最適
mjFRAME_GEOM / mjFRAME_SITE各 geom / site の座標系
mjFRAME_CAMERA / mjFRAME_LIGHTカメラ・ライトの向き
mjFRAME_CONTACT接触点の座標系。Step 3 の接触デバッグで使う

方法 2: XML に site で描く

常に出しておきたい、色や長さを自分で決めたいときはこちら。 geom ではなく site を使うこと。

<worldbody>
  <site name="axis_x" type="cylinder" fromto="0 0 0.002  0.4 0 0.002" size="0.008" rgba="0.9 0.15 0.15 1"/>
  <site name="axis_y" type="cylinder" fromto="0 0 0.002  0 0.4 0.002" size="0.008" rgba="0.15 0.7 0.2 1"/>
  <site name="axis_z" type="cylinder" fromto="0 0 0      0 0 0.4"     size="0.008" rgba="0.2 0.35 0.9 1"/>
</worldbody>

色は世界共通の慣習で 赤 = X / 緑 = Y / 青 = Z（RGB = XYZ）。

geomsite
衝突判定するしない
質量・慣性への寄与するしない
用途実体のある物体マーカー、センサ取付点、目標位置

geom で軸を描くと見た目の飾りが物理に混入する （見えない棒に衝突する、質量が増えて周期が変わる）。site なら物理は一切変わらない。

site が見えないときの 3 つの原因

1. group が 3 以上 — MuJoCo の初期表示は group 0-2 のみ （sitegroup = [1,1,1,0,0,0]）。group を書かなければ 0 なので出る。
2. size の桁違い — size は半径。 0.008 = 8mm。0.8 と書くと画面を覆う巨大な円盤になる。
3. 床に埋まっている — X 軸と Y 軸は z=0 の plane と同じ高さなので半分埋まる。 上の例で 0.002 だけ浮かせているのはこのため。

Step 2 で本当に効くのは Joint 表示

原点の軸より重要なのが Rendering パネルの Joint 表示。 axis="0 1 0" と書いた関節が意図した向きに付いているかは、 数字を睨むより見るほうが確実。回転軸を間違えたまま気づかず RL を回す事故は 初期に非常によく起きる。カートポールを組んだら必ず ON にして確認すること。

Python 側から変えることもできる

描画パラメータは MjModel の中にあり、実行時に書き換えられる。

model.vis.headlight.ambient[:] = [0.30, 0.30, 0.30]
model.vis.headlight.diffuse[:] = [0.35, 0.35, 0.35]

model.vis.global_.azimuth = 140      # global は Python の予約語なので global_
model.vis.global_.elevation = -20

fid = mujoco.mj_name2id(model, mujoco.mjtObj.mjOBJ_GEOM, "floor")
model.geom_rgba[fid] = [0.85, 0.87, 0.85, 1]

ビューアのカメラと表示オプションは viewer 側にある。

with mujoco.viewer.launch_passive(model, data) as viewer:
    viewer.cam.distance = 3.0
    viewer.cam.lookat[:] = [0, 0, 0.6]
    viewer.cam.azimuth = 140
    viewer.cam.elevation = -20

    with viewer.lock():          # UI は別スレッドなのでロックしてから触る
        viewer.opt.flags[mujoco.mjtVisFlag.mjVIS_JOINT] = True   # 関節軸を常時表示

どちらに書くべきか

XML に書くPython に書く
向いているものモデル固有の見た目。床、照明、既定カメラ、部品の色 スクリプトごとの都合。デバッグ表示、実行時に切り替えたいもの
適用範囲そのモデルを開く全スクリプトそのスクリプトだけ
gitモデルの差分として残るコードの差分として残る

推奨は XML。 view_model.py・学習スクリプト・評価スクリプトのどれから開いても 同じ見た目になる。Python 側に書くと、スクリプトを増やすたびにコピーすることになる。

Step 11 への伏線: 照明のドメインランダマイゼーション

「描画は物理に影響しない」には例外がある。カメラ画像を観測に使う方策を作る場合、 照明は方策の入力そのものになる。実機の照明環境はシミュと必ず違うので、 学習中に毎エピソード model.light_diffuse や headlight を ランダムに変えて頑健化する。
そのときに使うのが、ここで見た「Python から実行時に書き換えられる」という性質。

08

actuator — ついに動かせるようになる

nu = 0 だった振り子に、モータを 1 つ付ける。

<actuator>
  <motor name="torque" joint="hinge" gear="1" ctrlrange="-2 2"/>
</actuator>
属性意味
jointどの関節を駆動するか
gear制御入力に掛かる係数。実際のトルク = ctrl × gear
ctrlrange入力の許容範囲。実機のトルク上限に対応する

Python 側からはこう使う。

data.ctrl[0] = 0.5          # トルク 0.5 N·m を与える（gear=1 のとき）
mujoco.mj_step(model, data)
ctrlrange は飾りではない

ctrlrange は実機のモータが出せる最大トルクに対応させる。 ここを無限大にしておくと、シミュレーション上では一撃で振り子が立ち上がる方策が学習される。 しかしそのトルクは実機では出せないので、実機に載せた瞬間に破綻する。
Step 4 でスイングアップが「難しい問題」になるのも、この上限があるから。 上限が十分大きければ、力任せに持ち上げるだけの退屈な問題になる。

アクチュエータには motor（トルク指令）以外に position（位置指令）、velocity（速度指令）がある。 この使い分けは実機のモータ制御方式そのもので、 sim2real の成否を分ける重要な選択になる。Step 3 で詳しく扱う。

09

default — 繰り返しをまとめる

脚が 4 本ある、関節が 12 個ある、といったモデルで同じ属性を書き続けるのは苦痛。 <default> は CSS のクラスに近い仕組み。

<default>
  <joint damping="0.05" armature="0.01"/>        <!-- 全 joint の既定値 -->
  <geom rgba="0.2 0.4 0.9 1"/>

  <default class="link">                          <!-- 名前付きクラス -->
    <geom type="capsule" size="0.02"/>
  </default>
</default>

<worldbody>
  <body name="upper" pos="0 0 1">
    <joint type="hinge" axis="0 1 0"/>            <!-- damping=0.05 が自動で入る -->
    <geom class="link" fromto="0 0 0  0 0 -0.5"/> <!-- type と size をクラスから継承 -->
  </body>
</worldbody>

個別に書いた属性はクラスの値を上書きする。この優先順位も CSS と同じ感覚でよい。

10

sensor — 実機センサとの接点

「シミュレーション上で何が測れるか」を宣言する。 実機で測れないものをここに書いてはいけない、という制約意識がここで芽生える。

<sensor>
  <jointpos name="theta" joint="hinge"/>      <!-- 関節角度 = エンコーダ -->
  <jointvel name="omega" joint="hinge"/>      <!-- 関節角速度 -->
</sensor>
print(data.sensordata)      # 定義した順に値が並ぶ
センサ測るもの実機の部品
jointpos / jointvel関節の角度・角速度エンコーダ、ポテンショメータ
framequatbody の姿勢IMU（姿勢推定後）
gyro角速度IMU のジャイロ
accelerometer加速度IMU の加速度計
force / torque力・トルク力覚センサ、電流からの推定
framepossite のワールド座標実機では直接測れない（要モーションキャプチャ）
Step 11 への伏線: 特権情報

表の最後の framepos のように、シミュレーションでは簡単に取れるが実機では取れない量がある。 これを観測に入れて学習すると、シミュ上では高性能なのに実機では全く動かない方策ができる。
ただし Critic（価値関数）にだけ与えるのは有効で、これを非対称 Actor-Critic と呼ぶ。 Step 11 の主要テクニックのひとつ。

課題 3 · 発展（任意）

二重振り子を作ってカオスを見る
