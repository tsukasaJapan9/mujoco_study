古典制御でウォームアップ

強化学習を一切使わずに、振り子を下から振り上げて上端に立てる。 ここで書く制御ループの構造が、そのまま実機の制御ループになる。

00 · 導入

このステップで手に入るもの

Step 3 では <position> が f = kp(ctrl − q) − kv·q̇ という PD 制御そのものであることを見た。この Step ではその式をシミュレータの外に出し、自分の Python コードで毎ステップ計算する。

この Step が答える問い

1. シミュレータに埋め込まれた PD を使わず自分で書くと、何ができるようになるのか？

2. 実機では制御は 100Hz、物理は 1000Hz で動く。この周期の分離はコードのどこに現れ、落とすと何が壊れるのか？

3. なぜ PD 制御だけでは振り子を立てられないのか？ 何を足せば立つのか？

なぜこの順番なのか。 まず §01 で「なぜ RL の前にこれをやるのか」を片付ける。 §02 で PD を Python 側に出し、§03 でその呼び出し頻度を物理から切り離す——ここまでが制御ループの骨格で、Step 6 以降で方策がこの骨格の中に入る。 §04〜§05 は、その骨格を壊す 2 つの要因（トルク上限と制御周期）を順に見る。 §06 で PD の限界を超えるためのエネルギー整形に進み、§07 のスライダで全部を触ってから §08 の課題に入る。

Step 3 との接続

Step 3 の課題 2 で、velocity アクチュエータが kv=1.5 のせいで 1.179 rad で登りきれずに止まったのを見たはず。 あれがトルク飽和で、この Step の主役になる。 今回のモデルはトルク上限を ±0.5 N·m まで絞るので、 重力トルクの最大 1.623 N·m に対して約 1/3 の力しか出せない。 まっすぐ持ち上げるのは物理的に不可能で、そこがこの Step の面白いところ。

01

なぜ RL の前に古典制御を通すのか

この節のねらい

この Step を飛ばしたくなる誘惑への答えを先に置く。 RL が目的なのに、なぜ手で制御器を設計するのか。 到達点は「古典制御は RL の前座ではなく、RL の結果を評価する唯一の物差しだ」と納得すること。

強化学習の実験には、学習が失敗したのか、そもそもタスクが解けないのかを切り分ける手段が要る。 報酬が上がらないとき、原因はアルゴリズムかもしれないし、報酬設計かもしれないし、 単にそのモデルではそのトルクで立たないだけかもしれない。

ここで作るもの後でどう効くか
PD + スイングアップで立つという事実RL が立たないとき「タスクは解ける」と断言できる。原因をアルゴリズム側に絞れる
立つまでの所要時間（今回は約 2.9 秒）学習した方策の速さを比べる基準線。Step 7 で報酬曲線の横に並べる
制御ループの構造Step 6 の Gymnasium 環境で、step() の中身がこれと同じ形になる
トルク上限という物理的な限界Step 9 で「報酬設計が悪い」と「物理的に無理」を混同しなくなる
実機では順序が逆にならない

実機のロボットを作ったとき、最初に書くのは必ず PD 制御。 モータが正しい向きに回るか、エンコーダの符号が合っているか、 ゲインを上げると発振するか——これらはPD を書かないと確かめられない。 Step 12 で実機を組んだとき、あなたが最初に動かすのはこの Step のコードの移植版になる。

02 · 本題

PD 制御を Python 側に出す

この節のねらい

Step 3 で読んだ f = kp(ctrl − q) − kv·q̇ を、 シミュレータの外側に書き写す。やることは式を移すだけだが、 移した瞬間に式を自由に書き換える権利が手に入る。 到達点は、制御則がエンジンの設定ではなく自分のコードの一行になること。 ここが分かれ目で、エネルギー整形も強化学習も、この一行を差し替えることでしか実現できない。

新しい概念PD 制御
何をするもの
今の誤差（P: 比例）と誤差の変化の速さ（D: 微分）だけから出力を決める制御則。 τ = −kp(θ − θ*) − kd·θ̇。 P はバネ、D はダンパに相当する。モデルの知識を一切使わないのが特徴で、 だからこそ質量も慣性も知らない相手に対して動く。
なぜ今出るか
Step 3 で <position> の正体がこの式だと読んだ。 読んで分かることと、自分で書いて動かすことの間には差がある。 特に「どの周期で呼ぶか」は、埋め込み版では触れない。 それを触るためにここで外に出す。
どこに効くか
Step 6 で方策の出力を関節トルクに変換する層がこれと同じ構造になる。 四足歩行の RL では方策が目標角度を出し、その下で PD が回るという 二層構造が標準で、下の層はここで書くものと同一。 Step 12 の実機でも、マイコン側で回るのはこの式。

埋め込み版と自作版の対応

埋め込み版（Step 3）自作版（Step 4）
アクチュエータ<position kp kv/><motor/>
ctrl に書くもの目標角度 [rad]トルク [N·m]
式を評価する頻度毎 physics step（変えられない）自分で決める
式の形固定自由（非線形項も足せる）
ゲインの変更XML を書き換えて再コンパイル変数を書き換えるだけ

骨格

import numpy as np

def wrap(x):
    # 角度差を -pi..pi に畳む。これを忘れると上端付近で符号が反転する
    return (x + np.pi) % (2 * np.pi) - np.pi

def pd(theta, omega, theta_star, kp, kd, tau_max):
    u = -kp * wrap(theta - theta_star) - kd * omega
    return np.clip(u, -tau_max, tau_max)   # 飽和は自分で書く

なぜ wrap が要るのか 上端は θ = π。振り子が θ = 3.10 から θ = 3.20 を通り過ぎるとき、 wrap が無いと誤差は −0.04 → +0.06 と連続に動く——ここまでは良い。 しかし qpos が何周もして θ = 9.5 になったとき、 誤差 9.5 − 3.14 = 6.36 は「6.36 rad 戻せ」という巨大な指令になる。 実際には 0.08 rad ずれているだけなのに。 スイングアップでは振り子が何周もするので、これは必ず起きる。

ハマる前に

np.clip で飽和させても、MuJoCo 側の ctrlrange でもう一度切られる。 両方が効くので、Python 側だけ tau_max を大きくしても出力は増えない。 「ゲインを上げても何も変わらない」と感じたら、 model.actuator_ctrlrange[0] を print してどちらで切られているかを確かめること。 実機でも同じで、ドライバの電流制限とコードの制限が二重にかかる。

03 · 本題

制御周期と物理周期を分ける

この節のねらい

§02 で制御則を外に出した。外に出したからこそ「何ステップに一度呼ぶか」を選べる。 実機ではこれは選択ではなく与えられた制約で、 マイコンの処理能力と通信速度が制御周期を決める。 到達点は、シミュレーションの中に実機の制約を先に持ち込む書き方を身につけること。 これをやらずに学習した方策は、実機に載せた瞬間に別物になる。

新しい概念デシメーション（decimation）
何をするもの
物理を n ステップ進めるあいだ、制御出力を 1 回だけ計算して n ステップ保持すること。 n = 物理周波数 / 制御周波数。 物理 1000Hz・制御 100Hz なら n = 10。 保持するあいだ data.ctrl は書き換えない——これが実機の 「次の指令が来るまでモータは前の指令を出し続ける」状態に対応する。
なぜ今出るか
Step 3 で timestep の下限は物理の安定性で決まると学んだ。 制御周期はそれとはまったく別の理由で決まる量で、混同すると 「発散したから制御を速くする」という的外れな対処に走る。 2 つの周期があると認識するのが先決。
どこに効くか
Step 6 の Gymnasium 環境で、env.step() 1 回が物理の何ステップに当たるかが まさにこの n。方策が考える頻度を決めるので、 学習の難しさにも実機移植の成否にも直結する。 Step 11 では、実機の制御周期とシミュのそれがずれていること自体が Sim2Real ギャップになる。

骨格

ctrl_hz = 100
decimation = round((1 / model.opt.timestep) / ctrl_hz)   # 1000Hz / 100Hz = 10
u = 0.0

for i in range(n_steps):
    if i % decimation == 0:                # ここだけがセンサを読んで考える
        theta = data.qpos[0]
        omega = data.qvel[0]
        u = pd(theta, omega, np.pi, kp, kd, TAU_MAX)
    data.ctrl[0] = u                       # 残りのステップは前の値を保持
    mujoco.mj_step(model, data)

なぜ data.ctrl[0] = u がループの外に出ていないのか if の中に入れても結果は同じに見える（ctrl は勝手に消えない）。 だが毎ステップ書く形にしておくと、後でゼロ次ホールド以外の保持を試せる。 また、外乱やノイズを足す実験をするとき差し込み先がここになる。 実機の構造——「指令は保持され続ける」——をコードの形として見えるようにしておく意味もある。

周波数典型値何が決めるかStep 3 との関係
物理500–2000 Hz硬さ（kp・接触）と積分器。超えると発散Step 3 課題 1 で測ったしきい値
制御50–500 Hzマイコンの処理能力、通信速度、センサの更新レート別物。発散ではなく制御の失敗を招く
実機との対応

シリアルバスサーボ（STS3215 など）は 1Mbps でも 1 指令あたり数百 µs かかる。 12 関節を順に叩けば、それだけで 50–100Hz が上限になる。 「シミュでは 1000Hz で制御していたのに実機は 50Hz しか出ない」は Sim2Real 失敗の典型で、シミュ側を先に 50Hz に落としておくのが正しい対処。 Step 11 でこれをドメインランダマイゼーションの軸として扱う。

04 · 本題

上端は不安定平衡 — 引き込み領域はトルクが決める

この節のねらい

制御ループの骨格ができたので、それを壊す要因の 1 つ目に進む。 上端で振り子を保持するとき、「どれくらい傾いた状態から立て直せるか」には はっきりした限界がある。到達点は、その限界がゲインではなくトルク上限で決まると 計算で言えること。ゲイン調整に時間を溶かす前に、そもそも届くのかを判定できるようになる。

このモデルの実測値（mj_fullM と body_mass から）。

量値意味
質量 m0.661829 kgカプセルの密度既定値 1000 から計算される
重心までの距離 l0.25 m長さ 0.5 m の一様な棒の中点
関節まわりの慣性 I0.056743 kg·m²mj_fullM(m, d, M) の M[0,0]
最大重力トルク m·g·l1.6231 N·m水平のとき最大。これに勝てないと持ち上がらない
トルク上限 τmax0.5 N·mモデルの ctrlrange。重力の 約 1/3
新しい概念不安定平衡と引き込み領域
何をするもの
上端（θ = π）は力の釣り合う点だが、少しずれると倒れる方向に力が働く点。 下端と違って、制御をやめた瞬間に離れていく。 引き込み領域は、そこから制御を始めて上端に戻ってこられる初期状態の範囲。
なぜ今出るか
§06 のエネルギー整形は「上端の近くまで運んで PD に渡す」方式なので、 どこまで近づければ渡せるのかを先に知る必要がある。 この節の数値がそのまま §06 の切り替えしきい値になる。
どこに効くか
Step 9 で、RL が学習した方策の頑健性を測るときの言葉になる。 「初期角度をどこまでランダム化してよいか」は引き込み領域の話。 Step 11 では実機のセンサ遅れがこの領域を狭めることを扱う。

計算で出せる

上端から φ だけ傾いたとき、倒そうとする重力トルクは m·g·l·sinφ。 モータが出せるのは τmax まで。勝てるのは次の範囲だけ。

|φ| < arcsin(τmax / (m·g·l))  =  arcsin(0.5 / 1.6231)  =  0.3131 rad  =  17.9 度
検証済み

二分探索で実測した保持可能な最大初期角は 0.3131 rad。理論値と一致する。 さらに kp を 4 / 8 / 16 / 30 と変えても すべて 0.3131 rad で変わらなかった。 ゲインをいくら上げても境界は動かない——そこでは τ がすでに飽和していて、 制御器は実質的に「全力で押す」しかしていないから。

ここが本質 制御がうまくいかないとき、人はまずゲインを触る。 だがこの境界のようにゲインに一切依存しない限界が存在する。 触る前に「これはゲインの問題か、トルクの問題か」を計算で切り分けられると、 無駄な試行錯誤が消える。実機でモータを選ぶときの計算もこれと同じで、 必要トルクは m·g·l から先に見積もる。

Step 9 への伏線

RL でこの振り子を学習させると、方策はこの境界を勝手に見つける。 報酬を上げようとすれば、物理的に可能な範囲の縁まで攻めるのが最適だから。 学習した方策の挙動が「妙に保守的」あるいは「ギリギリを攻める」と感じたとき、 それが物理の限界なのか報酬設計の副作用なのかを、この計算で判定できる。

05 · 本題

制御周期を落とすと何が壊れるか

この節のねらい

骨格を壊す要因の 2 つ目。§03 で「制御周期は選べる」と言ったが、 落としすぎると何が起きるのかを具体的な数字で押さえる。 到達点は、ゲインを決めたときに必要な制御周期を見積もれること。 実機では逆に、制御周期が先に決まっていて使えるゲインの上限が決まる。

PD の閉ループは、上端まわりで線形化すると次の固有角周波数を持つ。

ωn = sqrt((kp − m·g·l) / I)      # kp > m*g*l でないとそもそも立たない

トルクを飽和させない条件（τmax = 20）で、ゲインごとに 保持できる最低の制御周期を実測した。

505.029.204.6540 Hz8.6x
10010.041.646.6370 Hz10.6x
20020.059.139.41120 Hz12.8x

読み取れること 硬い制御ほど速い制御周期を要求する。 必要な制御周波数はおおよそ閉ループ帯域の 6〜14 倍で、 「制御周期は帯域の 10 倍以上」という経験則がそのまま出ている。 裏を返せば、制御周期が 50Hz しか出ない実機では kp を 100 以上にできない。 シミュで kp = 400 の硬い制御を学習させても、実機には載らない。

今回のモデルでは、この表ほど壊れない

τmax = 0.5 のままだと、制御周期を 10Hz まで落としても倒れない（実測）。 理由は §04 と同じで、常に飽和している制御器は実質的に「倒れる方向と逆に全力」という 符号だけの制御になり、細かい周期の違いが効かないから。 上の表を再現したければ ctrlrange を広げて飽和を外す必要がある。 「飽和がロバスト性を生む」のは実機でもよくある現象で、 性能は落ちるが壊れにくくなる。

06 · 本題

エネルギー整形 — PD が届かない領域へ

この節のねらい

§04 で「上端から 17.9 度以内しか引き込めない」と分かった。 では真下（180 度ずれ）からどうやってそこへ運ぶのか。 到達点は、PD とはまったく違う発想の制御則—— 位置ではなくエネルギーを目標にする——を 1 つ手に入れること。 これは Step 9 で報酬を設計するときの発想にそのままつながる。

まず PD だけで試すとどうなるか

真下から PD で θ* = π を狙うと、立たない。 トルク上限を上げていくと、境界が見える。

τmax [N·m]PD だけで立つか理由
0.5失敗0.32 rad 付近で重力と釣り合って静止する
1.0失敗もう少し上がるが登りきれない
1.230← ここが境界（実測）振れの勢いを借りてぎりぎり越える
1.5成功ほぼ力ずくで持ち上がる
1.623成功m·g·l。ここから上は静的にも持ち上がる

なぜ PD だけでは無理なのか PD は「今いる場所と目標の差」しか見ていない。 真下にいるとき差は最大なので全力で押すが、トルクが足りなければ途中で釣り合って止まる。 「一度逆向きに振ってから勢いをつける」という発想が PD の式には存在しない。 目標に向かって進むことしかできないので、遠回りができない。

新しい概念エネルギー整形（energy shaping）
何をするもの
角度ではなく力学的エネルギーを目標値に合わせにいく制御則。 上端に静止している状態のエネルギー E* = 2·m·g·l を目標にし、 足りなければ注入、多すぎれば抜く。 τ = k·ω·(E* − E) という 1 行で書ける。
なぜ今出るか
§04 で PD の届く範囲が 17.9 度と分かり、 真下からそこへ運ぶ手段が要るから。 PD で解けないタスクに初めて出会ったところで出すのが一番腑に落ちる。
どこに効くか
Step 9 の報酬設計。「上端にいれば +1」という素朴な報酬では 真下から学習できない（報酬が一度も入らない）。 エネルギーを報酬に入れると学習が劇的に速くなる—— これは報酬整形（reward shaping）の代表例で、名前も発想もここから来ている。
もっと詳しく
下の実験室で k を動かすと、 エネルギーが目標に張り付いていく様子を位相平面で見られる。

式

E = 0.5 * I * omega**2 + m_g_l * (1 - cos(theta))   # 真下を 0 とした力学的エネルギー
E_star = 2 * m_g_l                                   # 上端で静止 = 3.2463 J
u = np.clip(k * omega * (E_star - E), -tau_max, tau_max)

なぜ ω が掛かっているのか エネルギーを増やすには動いている向きに力をかけるのが最も効率がよい （仕事率 = τ·ω）。 ω を掛けることで、右に振れているときは右へ、左に振れているときは左へ、 と自動的に符号が切り替わる。ブランコを漕ぐときに体を動かすタイミングと同じ。 そして E が E* に達すると括弧が 0 になり、力を入れるのをやめる。

この式の弱点を先に

ω = 0 のとき τ = 0 になる。 つまり完全に静止した真下から始めると、永遠に動き出さない。 data.qvel[0] = 0.01 のようなわずかな初速を与えるか、 最初の一瞬だけ定トルクを入れる必要がある。 「理論的には正しいのに動かない」の典型例なので、 動かなかったらまず初速を疑うこと。

2 つの制御則を切り替える

if abs(wrap(theta - np.pi)) < SWITCH:
    u = pd(theta, omega, np.pi, kp, kd, TAU_MAX)      # 上端近く: 立たせる
else:
    u = energy(theta, omega, k, TAU_MAX)              # それ以外: 勢いをつける
SWITCH の選び方には答えがある

この段階の狙い すでに上端近くにいる状態から始める。 振り上げは課題 4 まで考えない。 問題を「保持」だけに絞れば、うまくいかないときの原因が PD の中にしかない。

def wrap(x):
    return (x + np.pi) % (2 * np.pi) - np.pi

TAU_MAX = 0.5

確認方法 最終誤差が 1e-4 以下なら保持できている。 ±2.8 付近の値が出たら落ちて下でぶら下がっている。

先に予想すること kp を 1.0 にしたらどうなるか。 実行する前に答えを書いてから試すこと。

答えと解説を見る

落ちる。kp が m·g·l = 1.623 を下回ると、 傾いたときに引き戻す力が重力に負けるので、上端は不安定なまま。 kp = 1.0 では 6 秒後の誤差が −3.05 rad、つまり真下でぶら下がっている。

「ゲインが低いと追従が悪くなる」では足りない kp を下げると整定が遅くなるのは事実で、そこは連続的に悪化する。 だが m·g·l を境に性質そのものが変わる。

崖の正体 kp を下げると ωn → 0、つまり無限に遅くなる。 そして kp < m·g·l でルートの中身が負になり、 ωn が虚数になる——「遅い」ではなく 指数関数的に発散するという意味。

物理的には、倒そうとする重力トルク ≈ m·g·l·φ と 引き戻す制御トルク kp·φ がどちらも φ に比例するから。 傾きの大きさに関係なく同じ比率で負け続けるので、挽回する機会が無い。 kp > m·g·l はゲイン調整ではなく成立条件で、 満たさなければ kd も制御周期も無関係に倒れる。

課題 3 · 壊す

制御周期を落として破綻させる

この課題のねらい

なぜこの課題をやるのか 実機の制約をシミュの中で先に踏むため。 実機に載せてから「50Hz しか出ないので動きません」と気づくのが最悪の順序で、 シミュの段階で壊しておけば設計に織り込める。 あわせて、飽和が効いていると制御周期の影響が隠れるという 紛らわしい現象も見ておく。

やり終えたとき言えること ——ゲインを決めたときに必要な制御周波数を見積もれる。 逆に制御周波数が決まっているとき、使ってよいゲインの上限が言える。 これを知らないと、実機で発振したときに原因を延々と探すことになる。

3-1

まず現状のモデルで落としてみる

この段階の狙い 素直な予想が外れるのを体験する。 「制御周期を落とせば性能が落ちる」は正しいが、 このモデルでは想像よりずっと落ちない。その理由を考えるのが本題。

課題 2-1 の hold() の hz を 100 / 50 / 20 / 10 / 8 / 5 と変える（phi0 = 0.1 で固定）。

先に予想すること 何 Hz で落ちると思うか。紙に書いてから実行する。

答えと解説を見る

8Hz でもまだ保持でき、落ちるのは 5Hz から（実測）。 制御周期 0.125 秒というのは、倒れる時定数 1/sqrt(m·g·l/I) = 1/5.348 = 0.187 秒 と同じオーダーで、 直感的には保つはずがない。

なぜこんなに粘るのか τmax = 0.5 では制御器がほぼ常に飽和していて、 出力は実質「倒れる向きと逆に全力」という符号だけの制御になっている。 符号は 0.125 秒に一度更新すれば十分間に合う。 飽和がロバスト性を生んでいる——性能と引き換えに壊れにくくなる、という現象。

3-2

飽和を外してから落とす

この段階の狙い 3-1 の裏返し。飽和という交絡要因を取り除いて、 制御周期そのものの効果を見る。1 変数だけを振るために邪魔な変数を殺す、という同じ作法。

model.actuator_ctrlrange[0] = [-20, 20] で飽和を外し、 kp = 50, kd = 5 の硬い制御にして 3-1 を繰り返す。

確認方法 40Hz では保持でき、30Hz で落ちる（実測）。 ωn = sqrt((50 − 1.6231)/0.056743) = 29.2 rad/s = 4.65 Hz なので、 帯域のおよそ 8.6 倍が必要だったことになる。

ここから持ち帰るもの kp を上げるほど必要な制御周波数が上がる。 §05 の表を自分で 1 行埋めたことになる。 実機の制御周期が 50Hz なら、kp = 50 あたりが上限という 読み方ができるようになる。

課題 4 · 本題

エネルギー整形でスイングアップする

この課題のねらい

なぜこの課題をやるのか この Step の到達点。PD では原理的に解けないタスクを、 制御則を 1 つ足すだけで解く。 「制御器を自分で書ける」ことの価値が最もはっきり出る場面で、 §02 で式を外に出した理由がここで回収される。

やり終えたとき言えること ——強化学習を使わずにこのタスクが解けると実物で示せる。 これが Step 7 以降で学習結果を評価する基準線になる。 基準線を持たずに RL を始めると、失敗の原因を永遠に特定できない。

4-1

エネルギーを計算して確かめる

この段階の狙い 制御を書く前に測る関数だけを先に作る。 エネルギーが正しく計算できていないと、制御則をいくら直しても動かない。

def energy(theta, omega):
    return 0.5 * I * omega**2 + MGL * (1 - np.cos(theta))

print(energy(0.0, 0.0))        # 真下で静止
print(energy(np.pi, 0.0))      # 上端で静止 = 目標値

確認方法 0.0 と 3.2463 が出れば正しい。 2 つ目が 1.6231 になったら (1 - cos) を cos にしている。

4-2

エネルギー整形だけで回す（PD に切り替えない）

この段階の狙い わざと片方だけで走らせて、何が足りないかを見る。 最初から 2 つを組み合わせると、動かないときにどちらが悪いか分からない。

data.qpos[0] = 0.0
data.qvel[0] = 0.01           # これが無いと永遠に動かない
k = 1.0

for i in range(20000):
    if i % decimation == 0:
        th, om = data.qpos[0], data.qvel[0]
        u = np.clip(k * om * (E_STAR - energy(th, om)), -TAU_MAX, TAU_MAX)
    data.ctrl[0] = u
    mujoco.mj_step(model, data)

先に予想すること 上端に到達するか。到達したらそこで止まるか。

答えと解説を見る

上端の近くまでは行くが、止まらない。 実測では 20 秒間で上端への最接近が 0.161 rad、 一度も上端に静止しない。 最終的なエネルギーは 3.2271 で目標 3.2463 にほぼ一致しているのに、 最終角速度は 10.25 rad/s。

なぜそうなるのか エネルギー整形が制御しているのはエネルギーだけで、 どこにいるかは一切見ていない。 E = 2mgl を満たす状態は「上端に静止」以外にもあり、 「真下を 10.7 rad/s で通過」も同じエネルギーを持つ。 振り子はその等エネルギー線上をぐるぐる回り続ける。 これが PD を足す理由——位置を見る制御が要る。

実験室の位相平面で、灰色の曲線に軌道が張り付いていく様子として見える。

4-3

PD と切り替える

この段階の狙い 2 つの制御則を状態で切り替える構造を書く。 これは有限状態機械の最小形で、 実機のロボットの制御は必ずこの形（起動・待機・歩行・停止…）になる。

SWITCH = ???          # 課題 2 で測った値から決める

if abs(wrap(th - np.pi)) < SWITCH:
    u = np.clip(-kp * wrap(th - np.pi) - kd * om, -TAU_MAX, TAU_MAX)
else:
    u = np.clip(k * om * (E_STAR - energy(th, om)), -TAU_MAX, TAU_MAX)

SWITCH は穴埋め。課題 2-1 で測った 0.3131 rad との関係から決める。

答えと解説を見る

SWITCH = 0.3。 引き込み境界 0.3131 より内側でなければ、 PD が受け取った瞬間に負けて落ちる。

ではなぜ 0.05 のように余裕を取らないのか 狭すぎると通り過ぎる。 上端を通過するときの角速度は大きく、100Hz のサンプリングでは 窓の中でセンサを読めないまま抜けてしまう。 実測では SWITCH = 0.1 は失敗、0.2 以上で成功。 「内側だが狭すぎない」という両側からの制約がある。

確認方法 基準設定（k=1.0, kp=8, kd=1.0, SWITCH=0.3, 100Hz）で 2.89 秒後に PD へ切り替わり、そのまま静止する。 振り返しは 3 回。最大角速度は 10.36 rad/s。
