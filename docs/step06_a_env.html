00

前回までと、今回の問い

前回までで分かっていること
  1. 環境は step(s, a) という関数。遷移 P と報酬 r を実装したもので、学習中は変わらない
  2. 方策が学習されるもの。環境と方策の間を観測と行動が流れる
  3. 壁が 2 つある。A: 遷移を知らない／B: 状態が無限。 振り子では B にぶつかる（角度が連続値なので 14 マスの表が作れない）
この教材が答える問い

1. 振り子の「状態」として、エージェントに何を渡すべきか？

2. 自分の MuJoCo モデルを、RL ライブラリが使える形にするには何を書けばいいのか？

今回の進め方。 宿題の答え合わせから始めます。そのあと Gymnasium という共通規格を紹介し、 5-a のマス目と 1 対 1 で対応させながら最小の環境を作ります。 報酬の設計や学習は出てきません——動く箱を作るところまでが今回です。

先に準備

ライブラリを 1 つ追加します。

uv add gymnasium

検証に使ったのは gymnasium 1.3.0 と mujoco 3.12.0 です。

01

宿題の答え合わせ

この節のねらい

「角度をそのまま渡すと何が困るか」に答えます。 ここを間違えると、あとで学習が進まない原因として跳ね返ってきます。 しかもエラーは出ません。静かに性能が落ちるだけなので、先に潰しておきます。

宿題

振り子の「状態」として何をエージェントに渡しますか。 角度と角速度をそのまま渡すとして、角度には厄介な性質があります。 Step 4 で wrap() を書いたときに一度ぶつかったはずです。何が問題でしょうか。

答え：角度は一周すると元に戻るのに、数字は戻らない。

上端は θ = π = 3.1416 です。 そのわずかに手前と、わずかに行き過ぎたところを比べます。

渡し方θ = +3.13θ = −3.132 点の差
生の角度+3.13−3.136.2600
cos, sin(−1.00, +0.012)(−1.00, −0.012)0.0232

この 2 点は物理的にほぼ同じ状態です どちらも「ほぼ真上、ほんの少しだけ傾いている」。 なのに生の角度で渡すと、数字の上では 6.26 も離れて見えます—— 振り子が取りうる範囲でいちばん遠い 2 点に見えてしまう。

エージェントにとって観測はただの数字の並びです。 近い状態には近い数字、遠い状態には遠い数字が来ることを前提に学習します。 その前提が上端でだけ壊れる。 しかも上端はまさに立たせたい場所です。

何周もする問題もあります

スイングアップでは振り子が何周もします。qpos は畳まれずに増え続けます。

theta =  0.5000  ->  cos, sin = (+0.8776, +0.4794)
theta =  6.7832  ->  cos, sin = (+0.8776, +0.4794)   # 1 周した。同じ値になる
theta = 13.0664  ->  cos, sin = (+0.8776, +0.4794)   # 2 周した。やはり同じ

cos と sin に変換すると自動的に畳まれます 何周していようが、同じ姿勢なら同じ観測になる。 Step 4 で wrap() を手書きしたのと同じ問題を、 関数を書かずに解いています。

いちばん大事な語観測（observation）
何をするもの
環境がエージェントに渡す数字の並び。 状態そのものではなく、状態を「エージェントに見せる形に加工したもの」。 今回は [cosθ, sinθ, ω] の 3 つ。
なぜ「状態」と呼び分けるのか
MuJoCo の中の本当の状態は qpos と qvel です。 そこから何を、どう加工して渡すかは設計者が決めます。 渡さない情報もあれば、今回のように形を変えて渡す情報もある。
どこに効くか
Step 9 の主題そのもの。観測の設計は学習の成否を直接左右します。 Step 11 では「シミュでは取れるが実機では測れない情報」を 観測から外す作業（特権情報の扱い）が出てきます。
角速度はそのままで良いのか

良いです。角速度に周期性はありません—— 10 rad/s と −10 rad/s は本当に違う状態です。 変換が要るのは周期を持つ量だけ。 ロボットの関節角は基本的にこれに該当するので、 四足歩行の論文でも関節角は sin/cos で渡すのが定番です。

02

Gymnasium は共通のお作法

この節のねらい

新しいライブラリが出てきますが、中身は 5-a で書いたものと同じです。 「何が新しくて、何が同じか」をはっきりさせます。

Gymnasium は、環境の書き方を統一する規格です。 ライブラリというより取り決めだと思ってください。

なぜ規格が要るのか。Step 7 で使う学習ライブラリ（SB3）は、 あなたの振り子のことを何も知りません。 それでも学習させられるのは、「環境とはこういう関数を持つもの」という約束が あるからです。

5-a で自分で書いたものGymnasium での名前何が違うか
step(s, a)env.step(action)状態を引数で渡さない。環境が自分で覚えている
s = STARTenv.reset()エピソードの最初に呼ぶ。初期状態を返す
（無かった）observation_space観測の形と範囲の宣言
（無かった）action_space行動の形と範囲の宣言

いちばん大きな違いは「状態を持つ」こと 5-a の step(s, a) は状態を引数で受け取っていました。 Gymnasium の env.step(action) は行動しか受け取りません。 今どこにいるかは環境が内部に持っています（振り子なら self.data）。

これは 5-d の議論と繋がっています 5-d で「ベルマン方程式は step(s, a) と任意の場所を指定できるから使える」と言いました。 Gymnasium の環境では、それができません—— 今いる場所からしか進めない。壁 A がインタフェースの形として現れています。

なぜ空間（space）の宣言が要るのか

SB3 はニューラルネットの入力と出力のサイズを自動で決めます。 そのために「観測は何次元か」「行動は何次元でどの範囲か」を知る必要がある。 observation_space と action_space はそのための申告です。 詳しくは次回 6-b で扱います。

03

reset と step の形

この節のねらい

実際に書く 2 つの関数の戻り値の形を確認します。 ここの個数と順番を間違えるのが最頻出のつまずきなので、先に固めます。

reset() は 2 つ返す

observation, info = env.reset(seed=0)

info はデバッグ用の自由な辞書です。学習には使われません。 必要なければ空の {} を返します。

step() は 5 つ返す

observation, reward, terminated, truncated, info = env.step(action)
戻り値意味5-a では
observation次の観測next_state
rewardその 1 歩の報酬reward
terminatedタスクとして終わったか（ゴール、失敗）done
truncated時間切れで打ち切ったか無かった
infoデバッグ用の辞書無かった
terminated と truncated は必ず分ける

5-a の done が2 つに分かれています。 混同するとエラーを出さずに学習が壊れます。 理由は 5-d で書いた「done のとき未来の価値を足さない」という話に直結しますが、 今回は「2 つある」とだけ覚えて、どちらも False にしておいてください。 正しい使い分けは 6-c でまとめて扱います。

古い記事は 4 つ返しています Gymnasium の前身である gym では obs, reward, done, info の 4 つでした。 ネットのコードをコピーすると個数が合わずに落ちます。 ValueError: not enough values to unpack が出たらこれを疑ってください。

04 · 課題

手を動かす

この課題のねらい

なぜこの課題をやるのか 動く箱を先に作るため。観測の設計も報酬も後回しにして、 まず「reset して step したら値が返ってくる」状態を作ります。 ここが土台になり、6-b 以降はこのファイルに手を入れていきます。

やり終えたとき言えること ——MuJoCo のモデルと RL ライブラリの境界がどこにあるかを指させる。 自作ロボットを RL に繋ぐときに毎回書くのがこのファイルです。

進め方

穴埋めは 段階 2 の 1 箇所だけです。 envs/pendulum_env.py を新規作成してください（envs/ フォルダも）。 モデルは Step 4 で作った models/pendulum_torque.xml をそのまま使います。

段階 1

骨格を書く

この段階ですること クラスの外側だけ作ります。まだ動きません。

from pathlib import Path

import numpy as np
import mujoco
import gymnasium as gym
from gymnasium import spaces

ROOT = Path(__file__).resolve().parent.parent
MODEL_PATH = str(ROOT / "models" / "pendulum_torque.xml")
TAU_MAX = 0.5          # ctrlrange と合わせる
CTRL_HZ = 100          # Step 4 と同じ制御周期


class PendulumEnv(gym.Env):
  metadata = {"render_modes": [], "render_fps": CTRL_HZ}

  def __init__(self):
    self.model = mujoco.MjModel.from_xml_path(MODEL_PATH)
    self.data = mujoco.MjData(self.model)
    self.frame_skip = round((1 / self.model.opt.timestep) / CTRL_HZ)

    self.observation_space = spaces.Box(
      low=np.array([-1.0, -1.0, -20.0], dtype=np.float32),
      high=np.array([1.0, 1.0, 20.0], dtype=np.float32),
      dtype=np.float32,
    )
    self.action_space = spaces.Box(-1.0, 1.0, shape=(1,), dtype=np.float32)

gym.Env を継承します これが「Gymnasium の約束を守ります」という宣言です。 継承しておくと self.np_random という乱数生成器が使えるようになります （段階 3 で使います）。

モデルのパスは __file__ 基準にします "models/pendulum_torque.xml" と相対パスで書くと、 実行時のカレントディレクトリから探しに行くので、 別の場所から実行した途端に見つからなくなります。 sim/view_model.py と同じ書き方に揃えておくと安全です。 Step 7 で SB3 が別プロセスから環境を読み込むとき、ここが効いてきます。

frame_skip は Step 4 の decimation と同じもの 物理 1000Hz・制御 100Hz なので 10 になります。 名前が変わるだけで中身は同じです。

確認用スクリプトの置き場所に注意

下のコードを envs/ の中に置いて直接実行すると失敗します。

$ uv run envs/main.py
ModuleNotFoundError: No module named 'envs'

Python は実行したスクリプトのあるディレクトリを検索パスの先頭に置くので、 envs/ から見ると envs というパッケージは存在しません。 確認用スクリプトはプロジェクトのルートに置いてください （例: try_env.py）。 envs/ は環境の定義だけを置く場所にしておくと、 sim/ や control/ と役割が揃います。

どうしても envs/ の中に置きたい場合は uv run python -m envs.main とモジュールとして実行すれば動きます。

確認方法 ルートに try_env.py を作って実行します。

from envs.pendulum_env import PendulumEnv
env = PendulumEnv()
print("frame_skip =", env.frame_skip)      # -> 10
print(env.observation_space.shape)          # -> (3,)
print(env.action_space.shape)               # -> (1,)
段階 2

観測を作る

この段階ですること §01 の結論をコードにします。 今回の本題はここだけです。

  def _obs(self):
    theta = self.data.qpos[0]
    omega = self.data.qvel[0]
    return np.array(???, dtype=np.float32)      # ← ここだけ考える

§01 で決めたのは 3 つの数字でした。 observation_space の low / high が [-1, -1, -20] と [1, 1, 20] になっているのがヒントです。 最初の 2 つが ±1 に収まる量で、3 つ目だけ範囲が違います。

答えと解説を見る
    return np.array([np.cos(theta), np.sin(theta), omega], dtype=np.float32)

順番は自分で決めて構いません ただし一度決めたら絶対に変えないこと。 observation_space の範囲と対応が崩れますし、 学習済みの方策は並び順まで含めて覚えています。 順番を入れ替えると、学習済みモデルが意味不明な動きをします。

dtype=np.float32 を忘れないでください NumPy の既定は float64 です。 observation_space で float32 と宣言したのに float64 を返すと、6-d の check_env で弾かれます。 SB3 も内部で float32 を前提にしているので、揃えておくのが安全です。

なぜ角速度の範囲を ±20 にしたのか Step 4 でスイングアップを測ったとき、最大角速度は 10.36 rad/s でした。 その倍を取って余裕を見ています。 範囲は「絶対に超えない値」ではなく「だいたいこのくらい」で構いません （超えてもエラーにはなりません）。

段階 3

reset を書く

この段階ですること エピソードの最初に呼ばれる関数です。 写経で構いません。

  def reset(self, *, seed=None, options=None):
    super().reset(seed=seed)                    # 乱数の種を Gymnasium に渡す
    mujoco.mj_resetData(self.model, self.data)  # MuJoCo を初期状態に戻す
    self.data.qpos[0] = self.np_random.uniform(-0.1, 0.1)
    self.data.qvel[0] = self.np_random.uniform(-0.1, 0.1)
    mujoco.mj_forward(self.model, self.data)    # 派生量を埋める
    return self._obs(), {}

super().reset(seed=seed) を必ず呼ぶ これが self.np_random を用意します。 呼ばないと同じ種を渡しても結果が再現しません。 Step 7 で実験を再現するとき、ここが効いてきます。

なぜ初期状態をランダムにするのか 毎回まったく同じ位置から始めると、方策がその 1 通りの手順だけを丸暗記できてしまいます。 少し揺らしておくと、「状況に応じて対処する」方策が育ちます。 これは Step 11 のドメインランダマイゼーションの最も素朴な形です。

mj_forward を忘れると qpos を書き換えただけでは xpos などの派生量が古いままです。 観測に qpos しか使わない今回は実害が出ませんが、 センサ値を観測に入れた途端に前回の値が混ざります。

段階 4

step を書く

この段階ですること 1 歩進める関数です。 報酬は仮置きにして、まず動かすことを優先します。

  def step(self, action):
    torque = float(np.clip(action[0], -1.0, 1.0)) * TAU_MAX
    self.data.ctrl[0] = torque
    for _ in range(self.frame_skip):            # Step 4 の decimation と同じ
      mujoco.mj_step(self.model, self.data)

    reward = 0.0                                # 仮置き。6-d で設計する
    terminated = False                          # 6-c で扱う
    truncated = False
    return self._obs(), reward, terminated, truncated, {}

action は [-1, 1] で来ます TAU_MAX を掛けて実際のトルクに直しています。 なぜ方策に直接 N·m を出させないのかは 6-b の主題です。 いまは「そういう約束」とだけ思ってください。

float() で包む理由 action[0] は NumPy のスカラーです。 data.ctrl[0] への代入は通りますが、 型を明示しておくと後で型エラーに悩まされません （np.argmax を int() で包んだのと同じ話です）。

確認方法 全部つないで動かします。

import numpy as np
from envs.pendulum_env import PendulumEnv

env = PendulumEnv()
obs, info = env.reset(seed=0)
print("初期観測:", obs, obs.dtype)

obs, reward, terminated, truncated, info = env.step(np.array([1.0], dtype=np.float32))
print("1 歩後  :", obs)

次のような出力になれば成功です。

初期観測: [ 0.99962485  0.02738891 -0.04604266] float32
1 歩後  : [0.9996254  0.02737042 0.03426785]

数字を読んでみてください cosθ ≈ 1.0、sinθ ≈ 0.027 なので、 ほぼ真下（θ ≈ 0）にいます。 1 歩（0.01 秒）でトルク最大を入れても、ほとんど動いていません—— ω が −0.046 から +0.034 に変わった程度。 Step 4 で「この振り子は力ずくでは持ち上がらない」と確かめたとおりです。

05

まとめ

今回で分かったこと
  1. 角度をそのまま渡してはいけない。 上端の手前と奥で数字が 6.26 も離れる。cos と sin に直すと 0.023
  2. 観測は状態そのものではなく、状態を見せる形に加工したもの
  3. Gymnasium は環境の書き方の規格。 5-a の step(s,a) との最大の違いは環境が状態を自分で持つこと
  4. reset() は 2 つ、step() は 5 つ返す。 古い gym は 4 つだったので、ネットのコードは大抵合わない
  5. frame_skip は Step 4 の decimation と同じもの。今回は 10
次回（6-b）でやること

observation_space と action_space をきちんと扱います。 今回さらっと書いた action は [-1, 1] で来るという約束が主題です。

先に考えておいてください—— 方策に直接「トルク 0.3 N·m」を出させず、わざわざ [-1, 1] を経由するのはなぜでしょうか。 ヒント: もし関節が 12 個あって、それぞれトルクの上限がバラバラだったら？
