01

宿題の答え合わせ

この節のねらい

「なぜ [-1, 1] を経由するのか」に答えます。 理由は 3 つあり、どれも 1 自由度の振り子では実感しにくいので、 多関節を想像しながら読んでください。

宿題

方策に直接「トルク 0.3 N·m」を出させず、わざわざ [-1, 1] を経由するのはなぜでしょうか。 ヒント: もし関節が 12 個あって、それぞれトルクの上限がバラバラだったら？

理由 1：関節ごとの事情を方策から隠せる

四足歩行ロボットなら関節は 12 個。肩・肘・手首で必要なトルクはまったく違います。 仮に上限が ±0.5 / ±3.0 / ±12.0 だったとして、 方策に生の N·m を出させると関節ごとに出力の桁が違うことになります。

[-1, 1] で受け取って環境側で変換すれば、方策は全関節について同じ範囲を出すだけで済みます。

action = [-1.0, -1.0, -1.0]  ->  トルク [ -0.5,  -3.0, -12.0]
action = [ 0.0,  0.0,  0.0]  ->  トルク [  0.0,   0.0,   0.0]
action = [+1.0, +1.0, +1.0]  ->  トルク [ +0.5,  +3.0, +12.0]

境界がどこにあるかを思い出してください 「関節の上限が何 N·m か」はハードウェアの事情です。 方策が知る必要はありません。環境の側が吸収すべき情報で、 この分担は Step 12 でモータを別の型番に変えたときに効いてきます—— 環境の定数を 1 つ直すだけで、学習済みの方策がそのまま載ります。

理由 2：ニューラルネットの出力は 0 の周りに出る

方策の正体は Step 8 以降ニューラルネットになります。 初期状態のネットは0 を中心に、だいたい ±1 くらいの値を出すように初期化されます。

ここで「±12 を出せ」と要求すると、 学習の最初のうちはまったく力が足りません。 逆に ±0.01 のような小さい範囲だと、少し動いただけで上限に張り付きます。 [-1, 1] はネットが素直に出せる範囲なので、 余計な調整が要らなくなります。

理由 3：探索のノイズの大きさが決められる

5-e の ε-greedy にあたるものが、連続的な行動では 「出力にノイズを足す」という形になります。

そのノイズの大きさをいくつにすればいいかは、行動の範囲が分からないと決まりません。 [-1, 1] という約束があるから、ライブラリ側が 「標準偏差 0.5 くらいから始めよう」と既定値を持てます。 範囲がバラバラだと、探索量も関節ごとに手で決める必要が出てきます。

Gymnasium 自身も推奨しています

action_space を [-2, 2] にして check_env にかけると、 次の警告が出ます（実測）。

WARN: For Box action spaces, we recommend using a symmetric and
      normalized space (range=[-1, 1] or [0, 1] ...)

ただし警告だけで、エラーにはなりません。 [-0.5, 0.5] のように [-1,1] の内側なら警告も出ません。 規格が強制しているのではなく、実務上そうしたほうが得だという話です。

02

Box は「形と範囲」の申告書

この節のねらい

spaces.Box が具体的に何を持っているかを見ます。 触ってみると、思っているより単純なものだと分かります。

6-a で書いた宣言を、そのまま表示してみます。

Box([ -1.  -1. -20.], [ 1.  1. 20.], (3,), float32)
  shape (3,)  dtype float32
  low  [ -1.  -1. -20.]   high [ 1.  1. 20.]

持っているのは 4 つだけです。

項目意味誰が使うか
shape数字が何個並ぶかSB3。ネットの入力層のサイズを決める
dtype型。今回は float32SB3。内部の計算精度
low / high各要素の下限・上限用途によって違う（後述）

Box には便利なメソッドが 2 つあります。

space.sample()                       # 範囲内からランダムに 1 つ作る
space.contains(x)                    # x が範囲に収まっているか True/False

sample() はランダム方策そのものです action_space.sample() と書けば、でたらめな行動が 1 つ手に入ります。 5-a の rng.integers(4) に相当するもので、 動作確認のときのベースラインとして常に使えます。

観測と行動で low / high の意味が違います

行動の low / high は方策への指示です。 SB3 はこの範囲の中に収まる値を出そうとします。

観測の low / high はただの申告です。 環境が範囲外の値を返しても、誰も止めてくれません。 次の節で実測します。

03

申告を守らないとどうなるか

この節のねらい

今回いちばん大事な節です。 観測が宣言した範囲を超えたときの挙動を実測で確かめます。 結論は「チェックのときは弾かれ、実行時は黙って通る」という非対称なもので、 これを知らないと学習が壊れた原因を探せません。

実験：範囲 [-1, 1] の観測に 99.0 を返させる

その 1：check_env にかけると弾かれます

AssertionError: The first element returned by `env.reset()`
                is not within the observation space.

その 2：普通に実行すると、何も起きません

obs, reward, terminated, truncated, info = env.step(action)
print(obs)     # -> [99.  0.]   例外なし。警告もなし

これが厄介な理由 Box は値を切り詰めてくれません。 「範囲は ±20 です」と申告しておいて 50 を返しても、そのまま流れていきます。 学習は動き続け、ただ性能だけが落ちます。 エラーが出ないので、原因を観測の範囲だと疑うまでに時間がかかります。

なぜ性能が落ちるのか

SB3 は観測を正規化する機能を持っており、その計算に申告した範囲を使うことがあります。 申告が ±20 なのに実際は ±200 来ていると、 正規化後の値が想定の 10 倍になり、ネットの入力が暴れます。

また Step 11 で観測にノイズを載せるとき、 ノイズの大きさを範囲から決める実装をすると、そこでも申告値が効いてきます。

覚えておくこと
  1. Box の low / high は強制ではなく申告
  2. 守っているかを調べてくれるのは check_env と contains() だけ
  3. だから環境を書いたら必ず check_env を通す（6-d でやります）
04

観測の範囲はどう決めるか

この節のねらい

§03 で「申告は守るべき」と分かりました。 ではいくつにすればいいのか。実際の決め方を示します。

6-a で書いた宣言を振り返ります。

low  = [-1.0, -1.0, -20.0]
high = [ 1.0,  1.0,  20.0]
要素範囲決め方
cosθ±1.0数学的に決まる。迷う余地がない
sinθ±1.0同上
ω±20.0実測から決める。下で説明

角速度だけ根拠が要ります Step 4 でスイングアップを測ったとき、最大角速度は 10.36 rad/s でした。 その約 2 倍を取って ±20 としています。 「自分で測った値の 2 倍」が実用的な決め方です。

測っていないときは、まず測る

範囲が分からないときは、ランダム方策で回して実際の最大値を記録するのが確実です。 action_space.sample() で 1000 ステップ回し、 各要素の最小・最大を見れば決まります。6-d の課題でこれをやります。

広すぎても狭すぎても困る

狭すぎると §03 の問題が起きます——申告を超えた観測が黙って流れる。

広すぎると、正規化したときに実際の信号が狭い範囲に押し込まれます。 ±10000 と申告して実際は ±10 しか動かないなら、 正規化後の観測は ±0.001 になり、ほとんど変化がない入力に見えます。

だから「実測の 2〜3 倍」あたりが落としどころです。 ±inf と書く実装も見かけますが、 正規化を使わない前提のときに限った書き方です。

段階 2 · 壊す

範囲を狭くして、黙って通ることを見る

この段階ですること §03 の実験を自分の環境で再現します。 ここが今回の核心なので、必ず実行してください。

envs/pendulum_env.py の observation_space で、 角速度の範囲だけを ±20 から ±1 に狭めます。

      low=np.array([-1.0, -1.0, -1.0], dtype=np.float32),    # -20 -> -1
      high=np.array([1.0, 1.0, 1.0], dtype=np.float32),      # 20 -> 1

この状態で角速度を 1 より大きくします。 一定のトルクをかけ続けてもダメです——Step 4 で見たとおり、 0.31 rad で重力と釣り合って止まってしまいます。 振れている向きに押すと、ブランコを漕ぐようにエネルギーが溜まっていきます （Step 4 のエネルギー整形と同じ考え方）。

import numpy as np
from envs.pendulum_env import PendulumEnv

env = PendulumEnv()
obs, info = env.reset(seed=0)

for t in range(300):
    omega = obs[2]
    action = np.array([np.sign(omega) if omega != 0 else 1.0], dtype=np.float32)
    obs, reward, terminated, truncated, info = env.step(action)

print("観測        :", obs)
print("宣言した範囲:", env.observation_space.low, env.observation_space.high)
print("範囲内か    :", env.observation_space.contains(obs))

次のような出力になります。

観測        : [ 0.257283  -0.9663361 11.211819 ]
宣言した範囲: [-1. -1. -1.] [1. 1. 1.]
範囲内か    : False

実行する前に予想してください 角速度が宣言した範囲を超えたとき、step() はどうなりますか。 例外が出る？ 値が切り詰められる？ 警告が出る？

答えと解説を見る

何も起きません。 角速度は 11.2 まで上がり、宣言した ±1 を 10 倍以上超えています。 それでも step() は値をそのまま返し、例外も警告も出ません。 contains() が False を返すだけです。

これが §03 で言った「黙って通る」 学習は普通に動き続けます。ただ性能が落ちるだけ。 エラーが出ないバグは、出るバグより何倍も高くつきます。

確認が済んだら ±20 に戻してください 戻し忘れると 6-d の check_env で弾かれます—— もっとも、それが check_env を通す理由でもあります。

段階 3

多関節でも使えるスケーリングに書き換える

この段階ですること 6-a では action[0] * TAU_MAX と 掛け算 1 つで済ませていました。 §01 の「関節ごとに上限が違う」場合にも通じる一般形に直します。

やりたいのは [-1, 1] を [low, high] に移す変換です。

  def _scale(self, action):
    low, high = self.torque_low, self.torque_high
    return ???                    # ← ここだけ考える

対応させたいのは次の 3 点です。

action出したいトルク
−1.0low
 0.0(low + high) / 2
+1.0high

ヒント: まず action を [0, 1] に移してから、 幅 (high - low) を掛けて low を足します。

答えと解説を見る
    return low + (action + 1.0) * 0.5 * (high - low)

分解して読むと (action + 1.0) * 0.5 が [-1,1] → [0,1] の変換。 そこに幅 (high - low) を掛けて low を足すと、 [low, high] に着地します。

1 自由度・対称なら今までと同じ結果になります low = -0.5, high = 0.5, action = 0.6 で計算すると 0.3。0.6 × 0.5 = 0.3 と一致します。 一般形にしても壊れていないことを確認してください。

関節が増えても同じ式で済みます low と high を配列にすれば、 NumPy が要素ごとに計算してくれます。 low = [-0.5, -3.0, -12.0] のようにしても、コードは 1 行のままです。

確認方法 __init__ に次を足してから試します。

    self.torque_low = np.array([-TAU_MAX], dtype=np.float32)
    self.torque_high = np.array([TAU_MAX], dtype=np.float32)

import numpy as np
from envs.pendulum_env import PendulumEnv

env = PendulumEnv()
for a in (-1.0, -0.5, 0.0, 0.5, 1.0):
    print(f"action={a:+.1f} -> torque={env._scale(np.array([a], dtype=np.float32))}")

次のようになれば正解です。

action=-1.0 -> torque=[-0.5]
action=-0.5 -> torque=[-0.25]
action=+0.0 -> torque=[0.]
action=+0.5 -> torque=[0.25]
action=+1.0 -> torque=[0.5]

step() 側も書き換えてください float(np.clip(action[0], -1.0, 1.0)) * TAU_MAX を self._scale(np.clip(action, -1.0, 1.0))[0] に差し替えます。 clip は残してください—— 方策が範囲外を出してくる可能性がゼロではないので、 環境側で最後の砦を張っておくのが安全です。

06

まとめ

今回で分かったこと
  1. 行動を [-1, 1] にする理由は 3 つ。 関節ごとの事情を方策から隠せる／ ネットが素直に出せる範囲／探索ノイズの大きさを決められる
  2. Box が持つのは shape / dtype / low / high の 4 つだけ
  3. 観測の low/high は申告であって強制ではない。 超えても実行時は黙って通る
  4. 調べてくれるのは check_env と contains() だけ
  5. 範囲は実測値の 2〜3 倍を目安に。広すぎると信号が潰れ、狭すぎると申告違反になる
  6. low + (action + 1) * 0.5 * (high - low) なら関節が何個でも 1 行
次回（6-c）でやること

ずっと False のままにしてきた terminated と truncated を正しく使い分けます。 混同すると、エラーを出さずに学習が壊れる—— 今回の「黙って通る」と同じ種類の厄介さを持った話です。

先に考えておいてください—— 5-d で done のとき未来の価値を足さないようにしました。 では「500 ステップに達したので打ち切った」という場合、未来の価値は足すべきでしょうか、 足さないべきでしょうか。
