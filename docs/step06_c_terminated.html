前回までと、今回の問い

前回までで分かっていること
  1. 行動は [-1, 1] で受け取り、環境側で実際のトルクに直す
  2. Box の low/high は申告であって強制ではない。 破っても実行時は黙って通る
  3. step() の戻り値のうち terminated と truncated を ずっと False のままにしてきた
この教材が答える問い

1. 「時間切れで打ち切った」とき、未来の価値は足すべきか、足さないべきか？

2. 振り子では terminated をいつ True にすべきか？

今回の進め方。 宿題に答えたあと、間違えたときに何が起きるかを最初に見ます。 6-b の「黙って通る」と同じ種類の厄介さですが、 今回は具体的な数字でずれを測れます。

01

宿題の答え合わせ

この節のねらい

宿題に答えます。5-d で書いた 1 行に立ち返るだけで結論が出ます。

宿題

5-d で done のとき未来の価値を足さないようにしました。 では「500 ステップに達したので打ち切った」という場合、 未来の価値は足すべきでしょうか、足さないべきでしょうか。

答え：足すべきです。

5-d の更新式を思い出してください。

target = r + (0.0 if done else gamma * max(Q[s_next]))

なぜ done のとき足さなかったのか その先が存在しないからです。ゴールに着いたら世界が終わる。 未来の報酬は文字通りゼロなので、足すものがありません。

打ち切りは違います 500 ステップで止めたのはこちらの都合であって、 振り子の世界はその先も続いています。 501 ステップ目には報酬が発生するはずだった。 足さないと「そこで世界が終わる」と教えることになります。

terminatedtruncated
意味タスクとして終わったこちらの都合で打ち切った
例ゴール到達、転倒、範囲外に出た時間切れ、ステップ数上限
その先は存在しない存在する
未来の価値足さない足す
決めるのは環境（タスクの定義）実験の設定（学習の都合）

だから 2 つに分かれているのです 古い gym では done ひとつしかありませんでした。 この区別ができないので、多くの実装が静かに間違っていた—— それが Gymnasium で 2 つに分けられた理由です。

02

混同すると何が起きるか

この節のねらい

「間違えると壊れる」とよく言われますが、どれくらい壊れるのかを数字で見ます。 ここを見ておくと、この区別を軽視しなくなります。

いちばん単純な実験

5-b で扱った継続タスク（終わりのないタスク）で試します。 設定はこれ以上ないほど単純です。

  • 状態は 1 つだけ。何をしても報酬 +1
  • タスクとしての終わりは無い
  • ただし T ステップで打ち切る

5-b で計算したとおり、正しい価値は 1/(1−γ) = 10.0 です （γ=0.9）。

打ち切り T正しい実装打ち切りを終端扱いずれ

正しい実装は T に一切依存しません 打ち切りを 5 にしても 500 にしても、きっちり 10.0000 です。 これが正しさの証拠—— 「こちらの都合で区切った長さ」が価値に影響してはいけません。

誤った実装は必ず過小評価します 「そこで世界が終わる」と教えているので、 もらえるはずの未来の報酬を数え落とします。 T を長くすればずれは減りますが、ゼロにはなりません。

エラーは一切出ません

学習は普通に進み、報酬曲線も上がっていきます。 ただ、到達する性能が本来より低いだけ。 比較対象が無ければ「こんなものか」と思って終わります。

6-b の「範囲外の観測が黙って通る」と同じ構造です。 Step 6 で扱う落とし穴は、どれもエラーを出しません。 だからこそ仕組みを知っていること自体が唯一の防御になります。

03

2 つの終わり方の見分け方

この節のねらい

実際に環境を書くとき、どちらにすべきか迷う場面があります。 判断の基準を 1 つ持っておきます。

判断基準

「そこで止めなかったら、その先はあったか？」

あった → truncated。無かった → terminated。

状況どちら理由
ゴールに到達したterminatedタスクが達成された。その先は無い
ロボットが転倒したterminated失敗として定義した。続行しない
台車がレールから外れたterminated物理的に続けられない
500 ステップ経ったtruncated続けられるが、こちらが止めた
学習時間の都合で切り上げたtruncated同上
迷いやすい例: 「倒れたら終わり」は本当に terminated か

倒立振子で「一定角度を超えたら失敗」とする設計はよくあります。 これは terminated です——あなたがタスクをそう定義したから。 物理的には倒れても振り子は動き続けますが、 「失敗したらそこで終わり」というルールにした以上、その先は存在しません。

つまり terminated は物理の話ではなくタスク定義の話です。 同じモデルでも、タスクの決め方次第で変わります。

04

時間切れは自分で書かない

この節のねらい

truncated を自分で管理する必要はありません。 Gymnasium が用意している仕組みを使います。

ステップ数を数えて truncated = True にする処理は、 ラッパー（wrapper）という形で用意されています。 環境を包んで機能を足す仕組みです。

from gymnasium.wrappers import TimeLimit

env = TimeLimit(PendulumEnv(), max_episode_steps=500)

max_episode_steps=5 にして動かすと、こうなります（実測）。

 step  terminated  truncated
    1       False      False
    2       False      False
    3       False      False
    4       False      False
    5       False       True      # ← ラッパーが立てた

環境本体は何も知りません PendulumEnv.step() は truncated=False を返し続けます。 ラッパーがその戻り値を書き換えています。 おかげで環境のコードがタスクの定義だけに集中できます—— 「何ステップで打ち切るか」は実験の設定であって、振り子の性質ではないので。

ラッパーを付け忘れると永遠に終わりません

いまの PendulumEnv は terminated も truncated も 常に False です。実測すると何ステップ回しても終わりません。

学習ループは「エピソードが終わったら reset()」という作りなので、 1 エピソードが永遠に続き、初期状態のランダム化が一度も起きません。 これもエラーは出ません。学習が進まないだけです。

05

振り子ではどうするか

この節のねらい

判断基準を自分の環境に当てはめます。結論は少し意外かもしれません。

振り子のスイングアップで terminated を True にすべき場面はあるでしょうか。

候補判定理由
上端に到達したしない立ち続けることが目標。着いたら終わりではない
倒れたしない倒れてもやり直せる。むしろやり直す過程を学ばせたい
角速度が異常に大きい場合による物理が壊れた兆候なら打ち切る価値はある

結論: terminated は常に False のままで構いません 振り子のスイングアップは継続タスクです。 §02 で 65% のずれを見せた、あの設定そのもの。 だからこそ truncated を正しく扱う必要があります。

倒立振子（cartpole）とは設計が違います

教科書的な倒立振子では「一定角度を超えたら terminated」とします。 あれは「立て続けること」だけが目標で、倒れたら失敗というタスク定義だからです。

今回は下から振り上げるところから含めるので、 「倒れている状態」はむしろ通過点です。 同じ振り子でも、タスクの定義が違えば terminated の設計も変わります。

Step 9 への伏線

「倒れたら terminated」にすると、方策が倒れないことだけを学ぶようになります。 エピソードを早く終わらせれば罰を受けずに済むので、 わざと倒れて終わらせる方策すら出てきます（報酬の付け方次第）。 terminated の設計は報酬設計と不可分で、Step 9 でまとめて扱います。

手を動かす

この課題のねらい

なぜこの課題をやるのか §02 の表を自分の手で作るため。 65% のずれを自分で出しておくと、この区別を二度と軽視しなくなります。

やり終えたとき言えること ——terminated と truncated の使い分けを、 「未来の価値を足すかどうか」の一点で説明できる。

進め方

穴埋めは 段階 1 の 1 箇所だけです。 段階 1 は toy/truncation.py を新規作成、 段階 2・3 は envs/pendulum_env.py と try_env.py に手を入れます。

段階 1

65% のずれを自分で出す

この段階ですること §02 の実験を再現します。 MuJoCo も Gymnasium も使いません—— 状態 1 つだけの、これ以上ないほど単純なタスクです。

GAMMA = 0.9


def run(T, mode, n_ep=20000, alpha=0.05):
    # 状態は 1 つ。何をしても報酬 +1。タスクとしての終わりは無い。
    # T ステップで必ず「打ち切り」になる。
    Q = 0.0
    for ep in range(n_ep):
        for t in range(1, T + 1):
            r = 1.0
            truncated = (t == T)

            if truncated and mode == "wrong":
                target = r                     # 打ち切りを終端扱い（誤り）
            else:
                target = ???                   # ← ここだけ考える

            Q += alpha * (target - Q)
    return Q


true_value = 1 / (1 - GAMMA)
print(f"理論値 = 1/(1-gamma) = {true_value:.4f}")
for T in (5, 10, 20, 50, 100, 500):
    a, b = run(T, "correct"), run(T, "wrong")
    print(f"T={T:<4} 正しい={a:.4f}  誤り={b:.4f}  ずれ={abs(b-true_value)/true_value*100:.1f}%")

§01 で確認した「打ち切りでは未来の価値を足す」を 1 行で書いてください。 未来の価値は Q そのもの（状態が 1 つしかないので）、 割引率は GAMMA です。

答えと解説を見る
                target = r + GAMMA * Q

5-d の更新式そのままです r + gamma * max(Q[s_next]) の max(Q[s_next]) が、 状態が 1 つなので Q に縮んだだけ。 特別なことは何もしていません—— 「終端でないなら足す」という規則を素直に適用しています。

確認方法 こういう出力になります。

2 つのことを読み取ってください ① 正しい実装は T に依存しない。 5 でも 500 でもきっちり 10.0000。 「こちらの都合で区切った長さ」が価値に影響していません。

② 誤った実装は必ず過小評価する。 T を伸ばすとずれは減りますがゼロにはなりません。 「長めに取っておけば大丈夫」という逃げ方はできない、ということです。

段階 2

環境に TimeLimit を付ける

この段階ですること ラッパーを付けて、 エピソードがちゃんと終わることを確かめます。写経で構いません。

import numpy as np
from gymnasium.wrappers import TimeLimit
from envs.pendulum_env import PendulumEnv

env = TimeLimit(PendulumEnv(), max_episode_steps=5)   # 確認用に短く
obs, info = env.reset(seed=0)

for t in range(1, 8):
    obs, reward, terminated, truncated, info = env.step(np.array([0.0], dtype=np.float32))
    print(f"step={t}  terminated={terminated}  truncated={truncated}")
    if terminated or truncated:
        print("エピソード終了")
        break

確認方法 5 ステップ目で truncated=True になります。

段階 3

ラッパー無しだと終わらないことを確かめる

この段階ですること §04 の callout を自分で再現します。 付け忘れたときに何が起きるかを見ておきます。

env = PendulumEnv()          # ラッパー無し
obs, info = env.reset(seed=0)

for t in range(1000):
    obs, reward, terminated, truncated, info = env.step(np.array([0.0], dtype=np.float32))
    if terminated or truncated:
        print(f"{t} ステップで終了")
        break
else:
    print("1000 ステップ回しても終わらない")

確認方法 1000 ステップ回しても終わらない と出ます。

これが起きると何が困るか 学習ループは「エピソードが終わったら reset()」という作りです。 終わらなければ reset() が呼ばれず、 6-a で書いた初期状態のランダム化が一度も起きません。 方策は 1 通りの初期条件しか経験しないまま学習します—— そしてエラーは出ません。

07

まとめ

今回で分かったこと
  1. terminated＝タスクとして終わった（その先は無い）。未来の価値を足さない
  2. truncated＝こちらの都合で打ち切った（その先はあった）。未来の価値を足す
  3. 判断基準は「そこで止めなかったら、その先はあったか？」の一言
  4. 混同すると必ず過小評価になる。打ち切り 5 なら 65%、500 でも 4.9% ずれる。 長く取っても消えない
  5. truncated は TimeLimit ラッパーに任せる。 環境本体はタスクの定義だけに集中させる
  6. 振り子のスイングアップは継続タスクなので、 terminated は常に False でよい
次回（6-d）でやること

Step 6 の最終回です。check_env で環境を自己診断し、 ランダム方策で回してベースラインを測ります。 そして仮置きのままだった報酬を設計します。

先に考えておいてください—— 振り子を上端に立たせたい。報酬をどう定義しますか。 「上端にいたら +1、それ以外は 0」で良いでしょうか。 5-e で ε=0 のとき何も学習できなかった理由を思い出すと、 この案の問題が見えてきます。
