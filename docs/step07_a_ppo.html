00

前回までと、今回の問い

前回までで分かっていること
  1. envs/pendulum_env.py が完成し、check_env を通っている
  2. 報酬は -cosθ - 0.01ω² - 0.001τ²
  3. 基準線が 2 本ある。ランダム −499.50 ／ 古典制御 +28.31（上端滞在 216/500）
この教材が答える問い

1. 学習がうまくいかないとき、何から疑うべきか？

2. なぜ PPO なのか。SAC ではだめなのか？

今回の進め方。 宿題の答え合わせでチェックリストを作ってから学習を回します。 順番が逆に見えるかもしれませんが、回す前に「何を見るか」を決めておくのが 実験の基本です。

先に準備 
uv add stable-baselines3

PyTorch も一緒に入るので、初回は数分かかります。 検証に使ったのは stable-baselines3 2.9.0 / torch 2.14.0 です。 GPU は不要です——この規模なら CPU のほうが速いくらいです（理由は §04）。

01

宿題の答え合わせ

この節のねらい

学習を回す前にチェックする順番を決めます。 ここを決めずに回すと、うまくいかなかったときに手当たり次第に触ることになります。

宿題

学習がうまくいかなかったとき、何から疑いますか。 Step 6 で見た落とし穴を思い出して、チェックする順番を決めておいてください。

答え：環境から疑います。アルゴリズムは最後です。

順疑うもの確かめ方根拠
1報酬の符号真下と真上で reward を print逆でもエラーは出ない（6-d）
2報酬が疎すぎないかランダム方策で報酬が動くか見る疎だと文字通り 0 点（6-d）
3観測の範囲check_env を通す超えても黙って通る（6-b）
4エピソードが終わるかTimeLimit が付いているか終わらないと reset されない（6-c）
5terminated の扱い常に False になっているか混同で最大 65% 過小評価（6-c）
6学習量が足りているかステップ数を 10 倍にしてみる下の §03 参照
7ハイパーパラメータ7-b で扱うここまで潰してから
8アルゴリズムの選択PPO → SAC に変える最後の手段

なぜこの順番なのか 上にあるものほど「静かに壊れる」度合いが高く、確認が安いからです。 報酬の符号は 5 行のコードで確かめられますが、 アルゴリズムの比較には数十分かかります。 安くて致命的なものから潰すのが鉄則です。

Step 6 の落とし穴が 1〜5 を占めています

偶然ではありません。強化学習で「学習しない」原因の大半は環境側にあります。 アルゴリズムは世界中で検証されていますが、 あなたの環境を検証したのはあなただけです。

02

SB3 は 3 行で学習が回る

この節のねらい

まず最小構成を見ます。拍子抜けするほど短いので、 「何が隠れているか」を意識しながら読んでください。

from stable_baselines3 import PPO

model = PPO("MlpPolicy", env, verbose=1)
model.learn(total_timesteps=300_000)

これだけです。Step 5 で 6 本かけて学んだことが、全部この中に入っています。

Step 5 で学んだことSB3 のどこ
収益 G と割引率 γPPO(..., gamma=0.99) の既定値
価値関数 V"MlpPolicy" の中の Critic
方策 π同じく Actor
アドバンテージ A内部で毎回計算されている
on-policy（データ使い捨て）PPO がそう。集めては捨てを繰り返す

"MlpPolicy" が壁 B への答えです 5-d で「状態が無限にあると 14 マスの表が作れない」という壁 B を見ました。 MLP（多層パーセプトロン）＝ニューラルネットで表を近似する——それがこの文字列の意味です。 観測 3 次元を受け取り、行動 1 次元と価値 1 個を出すネットが自動で組まれます。 サイズは observation_space と action_space から決まります （6-b で宣言が必要だった理由がこれです）。

短いことと簡単であることは違います

3 行で回りますが、うまくいかないときに開けるべき蓋が大量にあります。 Step 8 で PPO を自分で実装するのは、その蓋を全部開けるためです。 今は「回る」ことを確認するのが目的で、 中身の理解は Step 8 に置いてあります。

03

なぜ PPO を選ぶのか

この節のねらい

SB3 には 10 種類ほどアルゴリズムがありますが、 連続的な行動を扱う実務では実質 2 つです。 5-f で学んだ on/off-policy が、そのまま選択の軸になります。

PPOSAC
方式on-policyoff-policy
データ集めたら使い捨てリプレイバッファに溜めて再利用
必要なステップ数多い少ない（10 倍近く効率的なことも）
並列化得意。環境を並べれば速くなる苦手。学習側がボトルネック
安定性高い。既定値でだいたい動く調整が要ることがある
向く場面シミュレータがある実機データが貴重

5-f の表がそのまま出ています 「データを使い回せるか」の違いが、必要なステップ数と並列化のしやすさに化けます。 PPO は使い捨てなので大量のデータが要りますが、 大量に作れるなら問題になりません。

今回 PPO を選ぶ理由は 1 つです。 シミュレータがあるから。 振り子は 1 秒間に数千ステップ生成できるので、 データの安さを活かせる PPO が向いています。

GPU が要らない理由

この規模のネット（隠れ層 64 が 2 層）では、GPU に送る手間のほうが計算より高くつきます。 実測すると CPU で 約 3,000 ステップ/秒 出ました。

ボトルネックはネットの計算ではなく MuJoCo の物理計算です。 だから速くしたければ GPU ではなく、環境を並列に増やすのが正解になります（§04）。

実機に移すときは選択が変わるかもしれません

Step 12 で実機の振り子を学習させるなら、1 ステップが実時間 0.01 秒です。 30 万ステップ ＝ 50 分の連続運転。しかも人が初期姿勢に戻す必要があります。 そこでは SAC のデータ効率が効いてきます。

04

環境を 4 つ並べる

この節のねらい

PPO を速くする唯一の現実的な方法を扱います。 コードは 1 行増えるだけですが、考え方は押さえておく価値があります。

PPO は「一定量のデータを集める → それで学習する → 捨てる」を繰り返します。 集める部分は完全に独立なので、環境を複数並べれば同時に走らせられます。

from stable_baselines3.common.env_util import make_vec_env

venv = make_vec_env(make_env, n_envs=4, seed=0)
model = PPO("MlpPolicy", venv, ...)

これを ベクトル化環境 と呼びます 4 つの振り子がそれぞれ別の初期状態から同時に動き、 方策は 4 つ分の観測をまとめて受け取って 4 つ分の行動を返します。 ニューラルネットの計算がまとめて行えるので、そこでも得をします。

何個にすればいいか

目安はCPU の物理コア数です。増やしすぎると プロセス間のやりとりが増えて逆に遅くなります。

なお make_vec_env の既定は DummyVecEnv—— 実は並列ではなく順番に回しています。 本当に並列にするには SubprocVecEnv を指定します。 振り子のように 1 ステップが軽い環境では、 プロセスを分けるコストのほうが高くつくこともありますので、 まずは既定のまま試してください。

エピソードの区切りは自動で処理されます

4 つの環境はバラバラのタイミングで終わります。 ベクトル化環境は終わった環境を自動で reset() し、 truncated のときは正しく未来の価値を足してくれます（6-c の話）。

ただしこれはあなたの環境が正しく truncated を返している前提です。 6-c で TimeLimit を付けたのはこのためでもあります。

05 · 課題

手を動かす

この課題のねらい

なぜこの課題をやるのか 学習を最後まで 1 回通すため。 結果が良いか悪いかは今回は問いません。 回し方と、結果の読み方を固めるのが目的です。

やり終えたとき言えること ——学習した方策を、Step 6 で作った evaluate() で採点し、 2 本の基準線と比べて位置づけられる。

進め方

穴埋めは 段階 2 の 1 箇所だけです。 train/ フォルダを作り、train/train_ppo.py を書きます。 学習には 2 分ほどかかります。

実行方法に注意: 直接実行すると失敗します 
$ uv run train/train_ppo.py
ModuleNotFoundError: No module named 'envs'

6-a で見たのと同じ問題です。Python は実行したスクリプトのあるディレクトリを 検索パスの先頭に置くので、train/ から見ると envs が見つかりません。 モジュールとして実行してください。

uv run python -m train.train_ppo

-m ならカレントディレクトリ（プロジェクトルート）が 検索パスに入るので解決します。

6-a と扱いが違う理由 try_env.py は確認用なのでルートに置きました。 train/train_ppo.py は学習スクリプトという役割を持つファイルなので、 train/ に置いたまま -m で呼ぶのが正しい分担です。

sys.path.insert() で解決しないでください ネットでよく見る解法ですが、7-b 以降で SubprocVecEnv を使うと 子プロセスが生まれます。子プロセスは親の sys.path 操作を 引き継がないことがあり、そこで再発します。 -m なら子プロセスも同じカレントディレクトリを継承するので問題ありません （実測で確認済み）。

段階 1

環境を並べる

この段階ですること まだ学習しません。 ベクトル化環境が作れることだけ確かめます。

import numpy as np
from gymnasium.wrappers import TimeLimit
from stable_baselines3.common.env_util import make_vec_env

from envs.pendulum_env import PendulumEnv


def make_env():
    return TimeLimit(PendulumEnv(), max_episode_steps=500)


venv = make_vec_env(make_env, n_envs=4, seed=0)
print("環境の数:", venv.num_envs)
print("観測の形:", venv.observation_space.shape)
print("行動の形:", venv.action_space.shape)

確認方法 環境の数: 4、観測の形: (3,)、 行動の形: (1,) と出れば成功です。

make_env を関数にしている理由 make_vec_env は環境を 4 個作る必要があるので、 「作り方」を渡します。インスタンスを 1 個渡すと、 4 つが同じオブジェクトを共有してしまいます。

学習を回す

この段階ですること PPO を作って学習させます。

from stable_baselines3 import PPO

model = PPO("MlpPolicy", venv, verbose=1, seed=0, device="cpu")
model.learn(total_timesteps=???)        # ← ここだけ考える
model.save("train/ppo_pendulum")

ステップ数を決めてください。判断材料はこれです。

  • 実測で 約 3,000 ステップ/秒
  • 1 エピソードは 500 ステップ
  • 初回は数分で終わる量にしたい
  • §02 のチェックリストの 6 番「学習量が足りているか」を後で試せるよう、 10 倍にする余地を残したい
答えと解説を見る
model.learn(total_timesteps=300_000)

約 100 秒、600 エピソード分 300,000 / 500 = 600 エピソード。 5-e の gridworld で Q 学習が 500 エピソードで収束したことを思うと妥当に見えますが、 あちらは状態が 14 個、こちらは無限です。比較になりません。

桁の感覚 連続制御のタスクでは 10 万〜1000 万ステップが普通のレンジです。 30 万はその下限あたり——「まず回ることを確かめる」量だと思ってください。

アンダースコアは桁区切りです 300_000 は 300000 と同じ。 桁を数え間違えないための Python の記法で、 ステップ数のように 0 が並ぶ場面で有効です。

確認方法 verbose=1 にしてあるので、学習中に表が流れます。 ep_rew_mean の行だけ見てください—— 1 エピソードあたりの平均報酬です。

段階 3

学習した方策を採点する

この段階ですること Step 6 の evaluate() を再利用します。 採点方法を変えないことが大事です—— そうしないと基準線と比べられません。

from stable_baselines3 import PPO

model = PPO.load("train/ppo_pendulum")


def trained_policy(env, obs):
    action, _ = model.predict(obs, deterministic=True)
    return action


total, up = evaluate(trained_policy)      # try_env.py の関数をそのまま使う
print(f"学習した方策: 合計報酬 {total:.2f}   上端にいたステップ {up:.1f}/500")
print(f"  ランダム方策 : -499.50   (0.0/500)")
print(f"  古典制御     :   28.31   (216.2/500)")

deterministic=True を忘れないでください 学習中の方策は確率的です——5-e の ε-greedy にあたる探索が入っています。 評価のときは探索を切るのが正しい（6-d で「本番では探索を切る」と書いたとおり）。 付け忘れると、本来の実力より低く出ます。

確認方法 3 つの数字が並べば成功です。参考までに、手元の実測はこうなりました。

学習した方策: 合計報酬 -227.51   上端にいたステップ 51.1/500
  ランダム方策 : -499.50   (0.0/500)
  古典制御     :   28.31   (216.2/500)

学習はしています。でも届いていません −499.50 から −227.51 まで上がったので、 方策は確実に何かを学びました。 上端にも 51 ステップ（全体の 10%）は滞在しています。

しかし古典制御の +28.31 / 216 ステップには遠い。 振り上げきれずに途中で落ちている状態です。 これが 7-b の出発点になります。

同じ数字にはなりません

ニューラルネットの初期値、環境の乱数、学習の順序—— 同じ seed を指定しても、環境が違えば結果は変わります。 −200 前後、上端 数十ステップのあたりに来ていれば同じ状況です。

逆に −490 付近から動いていないなら、 §02 のチェックリストを上から確認してください。

06

まとめ

今回で分かったこと
  1. 学習が失敗したら環境から疑う。順番は 報酬の符号 → 疎さ → 観測範囲 → 終了処理 → 学習量 → ハイパラ → アルゴリズム
  2. SB3 の学習は 3 行。"MlpPolicy" が壁 B（状態が無限）への答え
  3. PPO（on-policy）はシミュレータがあるとき、 SAC（off-policy）は実機データが貴重なとき
  4. 速くしたければ GPU ではなく環境を並列に増やす。 ボトルネックは MuJoCo の物理計算
  5. 評価するときは deterministic=True で探索を切る
  6. train/ 配下は uv run python -m train.train_ppo と モジュールとして実行する
次回（7-b）でやること

今回の結果はおそらく古典制御に届いていないはずです。 では何を直せばいいのか——その前に、学習の中で何が起きているかを読めるようになります。

TensorBoard で ep_rew_mean / explained_variance / entropy_loss / approx_kl の 4 つを読みます。 調整より先に診断です——測れないものは直せません。

先に考えておいてください—— 学習曲線（報酬）が上がらないとき、それだけでは原因が分かりません。 方策が悪いのか、価値の見積もりが外れているのか、探索が足りないのか。 この 3 つを切り分けるには、報酬以外に何を見ればいいでしょうか。
