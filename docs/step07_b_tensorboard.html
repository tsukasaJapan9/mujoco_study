01

宿題の答え合わせ

この節のねらい

今回見る 4 つの指標が、それぞれ何を切り分けるためのものかを先に示します。 この対応さえ頭にあれば、あとは個々の読み方だけです。

宿題

学習曲線（報酬）が上がらないとき、それだけでは原因が分かりません。 方策が悪いのか、価値の見積もりが外れているのか、探索が足りないのか。 この 3 つを切り分けるには、報酬以外に何を見ればいいでしょうか。

答え：PPO の部品ごとに 1 つずつ指標があります。

知りたいこと見る指標Step 5 の言葉では
結果は良くなっているかep_rew_mean収益 G の平均
価値の見積もりは当たっているかexplained_varianceV の精度（Critic）
探索はまだ続いているかentropy_loss5-e の ε にあたるもの
更新は適切な大きさかapprox_kl方策がどれだけ変わったか

4 つは Step 5 で学んだ部品にそのまま対応します PPO は方策（Actor）と価値関数（Critic）の 2 つを同時に学習します。 どちらが足を引っ張っているかは、別々の指標を見ないと分かりません。 報酬だけを見るのは、体温だけで病名を当てようとするようなものです。

02

TensorBoard を出す

この節のねらい

記録を取るのは 1 引数です。先に仕組みだけ通します。

先に入れておくもの 
uv add tensorboard

入れずに tensorboard_log を指定すると、 学習が始まる直前に落ちます。

ImportError: Trying to log data to tensorboard but tensorboard is not installed.

SB3 本体には含まれていません。記録を取るときだけ必要なので別扱いになっています。

model = PPO("MlpPolicy", venv, verbose=1, seed=0, device="cpu",
            tensorboard_log="tb_logs")        # ← これだけ

model.learn(total_timesteps=300_000, tb_log_name="ppo")

学習中に tb_logs/ppo_1/ のようなフォルダができます。別の端末で開きます。

uv run tensorboard --logdir tb_logs

ブラウザで http://localhost:6006 を開くとグラフが見られます。 学習中でもリアルタイムに更新されます。

tb_logs を git に入れないでください

実験ごとにフォルダが増え、すぐに数百 MB になります。 .gitignore に追加しておいてください。

tb_logs/

tb_log_name を毎回変えると比較できます "ppo" のままだと ppo_1, ppo_2... と連番になり、 TensorBoard 上で重ねて表示されます。 設定を変えた実験に名前を付けておくと、あとで何を変えたか分かります—— tb_log_name="ppo_lr3e-4" のように。 これが実験管理のいちばん簡単な形です。

03

ep_rew_mean — 成績

この節のねらい

いちばん基本の指標です。ただし単独で見ても情報が少ないことを押さえます。

何を測っているか。 直近 100 エピソードの、1 エピソードあたり合計報酬の平均です。 Step 5 の言葉では収益 G の平均—— 5-b で「強化学習の目的は収益の平均を最大にすること」と言った、まさにその量です。

必ず基準線と一緒に見てください

−300 という数字だけでは良いのか悪いのか分かりません。 Step 6 で 2 本の基準線を作ったのはこのためです。

ep_rew_mean意味
−499 付近から動かない何も学習していない。7-a のチェックリストを上から確認
−499 → −250 あたり学習は進んでいる。振り上げきれていない
+28 を超えた古典制御に並んだ

学習中の値は実力より低く出ます 5-e で見たとおり、学習中の方策は探索しています。 わざと下手に動く分だけ成績が下がるので、 ep_rew_mean と evaluate() の結果は一致しません。 評価は必ず deterministic=True で別に測ってください（7-a 段階 3）。

頭打ちに見えても、まだ伸びることがあります

PPO の学習曲線は長い停滞のあとに急に伸びることがあります。 特にこの振り子のように「振り上げる」という質的な飛躍が要るタスクでは、 できるようになるまで報酬がほとんど動きません。

停滞しているときに「まだ伸びる余地があるか」を判断する材料が、次の 3 つの指標です。

04

explained_variance — Critic の出来

この節のねらい

今回いちばん重要な指標です。 報酬が伸びない原因が Actor 側か Critic 側かを切り分ける、唯一の手がかりです。

何を測っているか。 価値関数 V の予測が、実際の収益をどれだけ説明できているか。 5-c で学んだ V(s) の精度そのものです。

explained_variance = 1 - Var(実際の収益 - V の予測) / Var(実際の収益)
値意味
1.0完璧に予測できている
0.8 〜 0.95健全。ここを目指す
0 付近平均を答えているのと変わらない
マイナス平均を答えるより悪い。何かおかしい

なぜこれが方策に影響するのか

5-c を思い出してください。アドバンテージ A = Q − V は 「その行動が平均よりどれだけ良いか」でした。 PPO はこの A の符号と大きさを見て方策を更新します。

V が外れていると A も外れます V が信用できなければ「平均よりどれだけ良いか」も信用できない。 つまり方策を動かす方向そのものが間違います。 報酬が伸びないとき、原因が Critic 側にあることは珍しくありません。

低いときにどうするか
  • まだ学習の初期なら、低いのは正常。データが足りていないだけ
  • ずっと 0 付近なら、V が学べていない。 報酬のスケールが大きすぎる／小さすぎる可能性（7-c の VecNormalize）
  • マイナスに振れ続けるなら、環境側を疑う。 同じ状態から毎回まったく違う収益が返っていないか—— 6-a で見たマルコフ性の問題（観測に必要な情報が入っていない）が典型
もっと深く

この式の分母がなぜ Var(実際の収益) なのか、 SB3 が「実際の収益」として何を渡しているのか、 0.99 でも Critic を褒めきれない場合があるのはなぜか—— 補助教材「explained_variance の中身」で 式・ソース・ラボまで開けてある。ここを飛ばしても Step 7 は進められる。

Step 8 への伏線

Step 8 で PPO を自分で実装すると、V の学習と方策の学習が 別々の損失関数として並んでいるのが見えます。 explained_variance はそのうち片方だけの成績表です。

05

entropy_loss — 探索の残量

この節のねらい

5-e の ε-greedy にあたるものが、連続的な行動ではどう現れるかを見ます。 探索をやめた方策は、そこから先は伸びません。

何を測っているか。 方策の迷いの大きさです。 連続行動の方策は「平均 μ、ばらつき σ の正規分布」の形をしていて、 σ が大きいほど色々な行動を試します。 エントロピーはその σ の大きさを表す量です。

Step 5 での対応物連続行動では
ε が大きい（よく探索する）エントロピーが大きい（σ が大きい）
ε = 0（探索しない）エントロピーが小さい（σ が小さい）

学習が進むにつれて自然に下がります 最初は手当たり次第に試し、良い行動が分かってくるとそこに集中していく。 これは正常な進み方です。

問題は「早すぎる収束」です

まだ良い方策を見つけていないのに σ が小さくなると、 そこから抜け出せなくなります。 5-e で ε = 0 にしたとき、 Q テーブルが全部 0 のまま動かなかったのと同じ構図です。

症状: 報酬が途中で頭打ちになり、エントロピーも早い段階で下がりきっている。

対処: ent_coef を上げます（既定は 0.0）。 これは「探索をやめるな」という圧力を損失に足すパラメータで、 7-c で実際に触ります。

あわせて train/std も見てください

SB3 は方策の σ そのものも記録しています。 エントロピーより直感的に読めます—— 行動が [-1, 1] なので、 σ が 0.1 を切っていればほぼ探索していないと分かります。

06

approx_kl — 更新の大きさ

この節のねらい

最後の 1 つは学習が壊れていないかの見張り役です。 PPO という手法の名前の由来にも関わります。

何を測っているか。 1 回の更新で方策がどれだけ変わったか。 更新前と更新後の方策の「違いの大きさ」です。

approx_kl意味
0.005 〜 0.02健全な範囲
0.05 以上更新が大きすぎる。学習が不安定になる
0.001 以下更新が小さすぎる。学習が進まない

なぜ大きすぎるとまずいのか

5-f で学んだとおり、PPO は on-policy です。 集めたデータはそのときの方策で集めたものなので、 方策が大きく変わるとデータが古くなります。

これが PPO の P（Proximal ＝ 近接）の意味です 「一度に大きく変えない」——それが手法の名前になっています。 clip_range（既定 0.2）が更新幅に制限をかけており、 approx_kl はその制限が効いているかを見る指標です。

どちらに転んでも対処は learning_rate
  • 大きすぎる（0.05 以上）→ learning_rate を下げる
  • 小さすぎる（0.001 以下）→ learning_rate を上げる

既定は 3e-4 です。2〜3 倍単位で動かすのが普通で、 10% の調整には意味がありません。

あわせて clip_fraction も見てください

更新のうち何割が制限に引っかかったかを表します。 0.1 〜 0.3 くらいが普通で、 0.5 を超えていたら更新が大きすぎます。 approx_kl と同じことを別の角度から見ている指標です。

07 · 課題

手を動かす

この課題のねらい

なぜこの課題をやるのか 自分の学習の指標を、自分の目で読むため。 教材の数字を眺めるのと、自分の実験のグラフを読むのとでは残り方が違います。

やり終えたとき言えること ——報酬が伸びないとき、次にどのパラメータを触るべきかを 指標から根拠づけて言える。7-c の調整はここが土台になります。

進め方

穴埋めはありません。読むことが今回の課題です。 新しい学習は回さず、7-a で回したものに記録を足して回し直すだけです。

段階 1

記録を取りながら学習し直す

この段階ですること 引数を 2 つ足して 7-a と同じ学習を回します。

model = PPO("MlpPolicy", venv, verbose=1, seed=0, device="cpu",
            tensorboard_log="tb_logs")

model.learn(total_timesteps=300_000, tb_log_name="ppo")
model.save("train/ppo_pendulum")

uv add tensorboard          # まだなら先にこれ
uv run python -m train.train_ppo

確認方法 tb_logs/ppo_1/ ができていれば成功です。 .gitignore に tb_logs/ を足しておいてください。

段階 2

TensorBoard を開いて 4 つを見る

この段階ですること 学習中でも構いません。ブラウザで開きます。

uv run tensorboard --logdir tb_logs

http://localhost:6006 を開き、次の 4 つを探してください。

  • rollout/ep_rew_mean
  • train/explained_variance
  • train/entropy_loss
  • train/approx_kl

グラフが階段状に見えたら 右上の Smoothing を 0 にすると生の値が見えます。 既定では平滑化がかかっていて、実際より滑らかに見えています。 異常なスパイクを探すときは必ず 0 にしてください。

段階 3

自分の 4 つの値を書き出す

この段階ですること グラフを眺めるだけでなく、 学習の終わりごろの値を数字で書き出します。 次回この数字と比べることになります。

指標あなたの値判定
ep_rew_mean 上がり続けている？ 頭打ち？
explained_variance 0.9 以上？ 0 付近？
entropy_loss まだ下がり続けている？
approx_kl 0.01 前後に収まっている？

この 4 つから次の一手を決めます §03〜§06 の各節末に「この値ならこうする」を書いてあります。 自分の値がどのケースに当てはまるかを判断してください。 それが 7-c でいじるパラメータになります。

段階 4

上端滞在ステップ数も記録する

この段階ですること 6-d で作った「上端にいたステップ数」を 学習中にも記録します。報酬は合成値なので内訳が見えないためです。

envs/pendulum_env.py の step() で info に入れます。

    upright = float(-np.cos(theta) > 0.95)
    return self._obs(), reward, False, False, {"upright": upright}

info は学習に使われません 6-a で「デバッグ用の自由な辞書」と書いたとおりです。 方策はこれを見ませんが、人間とログは見られます。

なぜこれが要るのか 報酬 −227 という数字からは、 振り上げに失敗しているのか、立ったあと落ちているのかが分かりません。 上端滞在が 0 に近いなら前者、 大きいのに報酬が低いなら後者（暴れて角速度の罰を食っている）。 切り分けに必要な情報です。

TensorBoard に出すにはもう一手間かかります

info に入れただけでは記録されません。 Monitor ラッパーの info_keywords を使うか、 独自の Callback を書く必要があります。 今回は info に入れるところまでで構いません—— 7-d の評価プロトコルでこの値を使います。

08

まとめ

今回で分かったこと
  1. 報酬だけでは「うまくいっていない」しか分からない。 PPO は Actor と Critic を同時に学習しているので、別々の指標が要る
  2. ep_rew_mean＝成績。基準線 2 本と一緒に見る
  3. explained_variance＝Critic の出来。低いと方策の更新方向が信用できない
  4. entropy_loss＝探索の残量。早く下がりきると探索をやめている
  5. approx_kl＝更新の大きさ。大きすぎると壊れ、小さすぎると進まない
  6. 記録は tensorboard_log="tb_logs" の1 引数。 tb_log_name に実験名を付けておくと後で比較できる
次回（7-c）でやること

ようやく調整に入ります。7-a のチェックリストの 6 番（学習量）と 7 番（ハイパーパラメータ）です。

今回読んだ指標が、どれを触るべきかの根拠になります。 定番とされる VecNormalize も試しますが、 効くかどうかは自分の環境で測らないと分かりません—— 実際、今回の振り子では意外な結果が出ます。

先に考えておいてください—— 7-a で 30 万ステップでは届きませんでした。 単にステップ数を 3 倍にしたらどうなると思いますか。 そしてそれを試す前に、指標のどれを見れば「まだ伸びる余地があるか」が分かるでしょうか。
