宿題の答え合わせ

この節のねらい

宿題に答えます。答えはすでに 5-e で書いていました—— 名前が変わっているだけです。

宿題

5-c で A = Q − V と習いましたが、Q は表として持っていません。 持っているのは V と、実際に歩いて得た報酬の列だけ。 そこから A をどう計算すればいいでしょうか。

答え：1 歩あるいた結果で Q を推定します。

Q(s,a) は「s で a を取り、その後は方策に従ったときの収益」でした。 実際に a を取って 1 歩あるけば、報酬 r と次の状態 s' が手に入ります。 その先は V(s') で代用できます。

Q(s,a) ≈ r + γ·V(s')

A(s,a) = Q(s,a) - V(s)
       ≈ r + γ·V(s') - V(s)
この式、5-e で見ています

Q 学習の更新式はこうでした。

target = r + γ·max_{a'} Q(s', a')
TD 誤差 = target - Q(s,a)
この a' は SARSA の a' とは別物です

5-f で SARSA の式を r + γ·Q(s', a') と書きました。 同じ a' という記号が出てきますが、役割がまったく違います。

式a' の正体
Q 学習maxa' Q(s', a') すべての行動を動かすための仮の名前。式の外に出てこない
SARSAQ(s', a') 実際に次に選ぶ行動。具体的な 1 つの値

コードで見れば一目瞭然です。

max(Q[s_next])          # Q 学習。4 つ全部見て最大を取る。添字が無い
Q[s_next][a_next]       # SARSA。a_next という具体的な行動を指定している

だから 5-f の主張が成り立ちます 「Q 学習がでたらめに歩いても学べるのは max のおかげ。 右辺に実際の行動が出てこないから」—— maxa' の a' は実際の行動ではないので、矛盾しません。

形が同じです。「予想していた値」と「1 歩あるいて分かった値」のズレ—— 5-e で TD 誤差 と呼んだものが、そのままアドバンテージの推定値になります。

違いは Q の表を持っているか V だけ持っているかで、 発想は同じです。

学習途中は両側とも外れています

V(s') も V(s) も学習中のネットの出力なので、 片方だけ正しいということはありません。 Q 学習で実際に記録するとこうなります （gridworld の (2,0) で up を選んだときの更新）。

  ep    Q(s,a)   max Q(s')    r    target      TD誤差
   0   0.00000    0.00000   0.0   0.00000  +0.00000   # 両方ゼロ。何も起きない
  21   0.02884    0.09735   0.0   0.08761  +0.05878   # 両方とも正解から遠い
  51   0.37327    0.54655   0.0   0.49190  +0.11863   # 誤差のピーク
 399   0.65610    0.72900   0.0   0.65610  +0.00000   # ようやく収束

それでも target のほうが「わずかに正しい」 r という実測値が 1 個だけ混ざっているからです。 その 1 個の差を頼りに、少しずつ全体が正しくなっていきます。

r = 0 の場所では、最初は本当に何も起きません ep 0 の行を見てください。両方ゼロなので TD 誤差もゼロ、更新しても値が変わらない。 5-e で ε=0 のとき表が動かなかったのと同じ現象です。 学習を始めるのはゴールに入った 1 歩の r = 1.0 だけ—— そこには推測が混ざらないので確実に更新され、隣へ、また隣へと伝わります。 5-d の「波が広がる」絵がこれです。

TD 誤差は単調には減りません ep 51 でいったん大きくなってからゼロに向かっています。 情報が届いた瞬間に修正が始まるためで、 「誤差が大きい ＝ 悪い」とは限りません。 7-b で explained_variance がマイナスから 0.91 へ急上昇したのと同じ構図です。

ただしこの推定は「1 歩先しか見ていません」 r + γV(s') − V(s) は、実際の報酬を 1 個だけ使い、 残りはすべて V の予想に頼っています。 V が外れていれば、その誤差をまるごと引き継ぎます。

逆に、最後まで歩いて収益を測れば V に頼らずに済みますが、 5-c で見たとおりモンテカルロはぶれが大きい。 「どこまで実際の報酬を使い、どこから V に任せるか」—— このつまみが GAE の λ です。次回 8-b の主題になります。

03

Actor-Critic — 1 つのネットで 2 つを出す

この節のねらい

"MlpPolicy" が作っているものの正体を見ます。 2 つの役割が 1 つのネットに同居しているのが要点です。

呼び名役割Step 5 では7-b の指標
Actor（演者）観測を見て行動を決める方策 πentropy_loss
Critic（評論家）観測を見て価値を予想する価値関数 Vexplained_variance

名前のとおりです 演者が動き、評論家が「その場面はどれくらい良いか」を採点する。 採点結果（アドバンテージ）を見て演者が改善します。

構造

観測 (3) ─→ Linear(3,64) ─→ Tanh ─→ Linear(64,64) ─→ Tanh ─┬─→ Linear(64,1) → mu   (行動の平均)
                    共通部分（shared）                      └─→ Linear(64,1) → V    (価値)

                                                  別に持つ: log_std (行動のばらつき)

途中まで同じ計算を使い、最後だけ枝分かれします。

なぜ途中を共有するのか

「今どういう状況か」を読み取る部分は、行動を決めるのにも価値を測るのにも要ります。 別々に持つと同じことを 2 回学ぶことになり、データが余計に必要です。

ただし共有には副作用があります—— Critic の学習が Actor の内部表現を壊すことがあります。 SB3 の既定は実は「共有しない」（net_arch で別々に指定）で、 共有するかどうかはタスク次第です。 8-d では共有版で書きます——短くて、振り子では十分動くので。

実際の大きさ

パラメータ形個数
shared.0.weight / bias(64, 3) / (64,)256
shared.2.weight / bias(64, 64) / (64,)4160
mu.weight / bias(1, 64) / (1,)65
v.weight / bias(1, 64) / (1,)65
log_std(1,)1
合計——4,547

4,547 個です 画像認識のネットが数千万個のパラメータを持つのと比べると桁違いに小さい。 7-a で「GPU が要らない」と書いた理由がこれです。 この規模なら GPU に送る手間のほうが高くつきます。

04

対角ガウス方策 — 連続行動をどう「選ぶ」か

この節のねらい

5-e の ε-greedy にあたるものが、連続行動でどう実装されるかを見ます。 7-b で読んだ entropy_loss と std の正体がここで分かります。

マス目では行動が 4 択だったので、「上 25%、右 25%...」と確率を並べれば方策になりました。 トルクは連続値なので、並べられません。

そこで正規分布を使います。ネットは分布の平均 μ を出し、 ばらつき σ を別に持ち、そこから行動をサンプリングします。

mu     = ネットの出力          # 「だいたいこれくらいが良い」
std    = exp(log_std)          # 「どれくらい散らすか」
action ~ Normal(mu, std)       # そこから 1 つ引く
いちばん大事な語log_std
何をするもの
行動のばらつき σ を、対数で持つパラメータ。 実際に使うときは exp() して σ に戻します。
なぜ対数で持つのか
σ は必ず正でなければなりません（負のばらつきは意味がない）。 直接学習すると負になる危険がありますが、 exp() を通せば何を入れても正になります。 制約を式の形で満たす、という常套手段です。
どこに効くか
7-b で読んだ train/std がこの exp(log_std) です。 30 万ステップ時点で 0.602 でした。 ent_coef はこの値を下がりにくくするパラメータ（7-c）。
log_stdstd意味
0.01.000初期値。行動が [-1,1] なのでかなり広く探索
−0.50.6077-b の 30 万ステップ時点（0.602）がこのあたり
−1.00.368かなり絞られてきた
−3.00.050ほぼ探索していない

「対角」とは何か

行動が複数ある場合（12 関節など）、それぞれ独立した正規分布として扱います。 関節どうしの相関を考えない、という意味で対角（共分散行列が対角）と呼びます。

相関を考えないのは近似です 実際には「肩を上げるなら肘も曲げる」のような相関がありますが、 それは分布ではなくネットワークが学びます—— 観測に応じて μ をまとめて出すので。 分布の形を単純にしておくほうが計算も実装も楽で、実用上ほとんど困りません。

log_prob と entropy が必要になります

8-c の損失計算で使うので、分布から 2 つの量を取り出せることを確認しておきます。

量意味どこで使うか
log_prob(a)その行動を選ぶ確率の対数8-c のクリップ目的関数
entropy()分布の広がりent_coef を掛けて損失に足す

std = 1.0 のときのエントロピーは 1.4189 です （0.5·log(2πe)）。 7-b で学習開始直後の entropy_loss が −1.401 だったのは、 これに符号を付けた値です。

段階 1

ネットワークを書く

この段階ですること §03 の図をコードにします。写経で構いません。

import torch
import torch.nn as nn


class ActorCritic(nn.Module):
  def __init__(self, obs_dim, act_dim, hidden=64):
    super().__init__()
    self.shared = nn.Sequential(
      nn.Linear(obs_dim, hidden), nn.Tanh(),
      nn.Linear(hidden, hidden), nn.Tanh(),
    )
    self.mu = nn.Linear(hidden, act_dim)        # Actor: 行動の平均
    self.v = nn.Linear(hidden, 1)               # Critic: 価値
    self.log_std = nn.Parameter(torch.zeros(act_dim))   # 観測に依存しない

  def forward(self, obs):
    h = self.shared(obs)
    return self.mu(h), self.v(h).squeeze(-1), self.log_std

log_std だけ nn.Parameter です mu は nn.Linear、つまり観測から計算されます （状況に応じて狙う値が変わるので）。 一方 log_std は観測に依存しない、ただの学習される数です。

なぜばらつきは状況に依存しなくていいのか 「上端付近では慎重に、下では大胆に」と変えられれば理想的ですが、 PPO の標準実装では状態非依存にします—— そのほうが学習が安定するからです。 状態依存にする実装もあります（SAC がそう）。

squeeze(-1) の意味 self.v(h) の形は (バッチ, 1) ですが、 価値はスカラー 1 個なので (バッチ,) にします。 この 1 次元の食い違いは、あとで損失計算のときに ブロードキャストの事故を起こします——ここで潰しておきます。

確認方法 形とパラメータ数を出します。

net = ActorCritic(obs_dim=3, act_dim=1)
obs = torch.randn(4, 3)
mu, v, log_std = net(obs)
print("mu:", tuple(mu.shape), " v:", tuple(v.shape), " log_std:", tuple(log_std.shape))
print("パラメータ数:", sum(p.numel() for p in net.parameters()))

mu: (4, 1)  v: (4,)  log_std: (1,)
パラメータ数: 4547
段階 2

行動をサンプリングする

この段階ですること §04 の 3 行をコードにします。 今回の本題はここだけです。

  def dist(self, obs):
    mu, v, log_std = self(obs)
    std = ???                              # ← ここだけ考える
    return torch.distributions.Normal(mu, std), v

  def act(self, obs):
    d, v = self.dist(obs)
    action = d.sample()
    log_prob = d.log_prob(action).sum(-1)
    return action, log_prob, v

§04 で「log_std は対数で持つ」と書きました。 実際に分布に渡すときは何をすればいいでしょうか。

答えと解説を見る
    std = log_std.exp()

これだけです log_std = -0.5 なら std = 0.607。 exp() を通すので、log_std がどんな値でも std は必ず正になります。

なぜ dist() を分けたのか 8-c で分布だけが欲しくなるからです—— すでに選んだ行動の log_prob を、更新後のネットで測り直す場面があります。 そこではサンプリングしたくありません。 dist() を分けておくと、act() と共用できます。

.sum(-1) が付いている理由 log_prob は行動の次元ごとに出ます。 振り子は 1 次元なので違いが見えませんが、12 関節なら 12 個返ります。 §04 で「対角＝各次元が独立」と書いたので、 同時に起きる確率は掛け算——対数なら足し算です。 これを忘れると 12 関節にしたとき静かに壊れます。

確認方法 出てくる値を見ます。

torch.manual_seed(0)
net = ActorCritic(3, 1)
obs = torch.randn(4, 3)
action, log_prob, v = net.act(obs)
print("std     :", net.log_std.exp().detach().numpy())
print("action  :", action.detach().numpy().ravel().round(4))
print("log_prob:", log_prob.detach().numpy().round(4))

std = 1.0 から始まります log_std の初期値が 0 なので。 行動が [-1, 1] の範囲であることを思うと、 標準偏差 1.0 はかなり広い—— 最初はほぼでたらめに動く、ということです。 5-e の ε を 1.0 から始めるのに相当します。

段階 3

7-b の指標と突き合わせる

この段階ですること コードは少しだけです。 7-b で読んだ数字が、いま書いた変数から出ていたことを確認します。

mu, v, log_std = net(obs)
dist = torch.distributions.Normal(mu, log_std.exp())
print("entropy:", dist.entropy().sum(-1).detach().numpy().round(4))

確認方法 1.4189 が 4 つ並びます。

7-b の表を見返してください 16k ステップ時点の entropy_loss が −1.401 でした。 符号を除けばほぼ一致します（1.4189 は std=1.0 ちょうどのとき、 16k 時点では既に少し下がっていたので 1.401）。

なぜ符号が逆なのか SB3 が記録しているのは「損失」だからです。 エントロピーは大きいほど良い（探索が続く）ので、 損失としては符号を反転させます。 7-b で「entropy_loss が下がる＝探索が減る」と読んだのは、 絶対値が小さくなる方向という意味でした。

ここが今回のいちばんの収穫です

7-b では 4 つの指標を「そういうものだ」として読んでいました。 いまは entropy_loss が log_std という 1 個のパラメータから出ていると分かります。

explained_variance も同じで、 self.v という 65 個のパラメータの成績表です。 8-b 以降で残りも同様に開きます。

まとめ

今回で分かったこと
  1. 宿題の答え: A ≈ r + γV(s') − V(s)。 5-e の TD 誤差そのもの。ただし1 歩先しか見ていない
  2. PPO は 5 つの部品。本当に新しいのは4 番（損失）だけ
  3. Actor（行動を決める）と Critic（価値を予想する）が 1 つのネットに同居。合計 4,547 パラメータ
  4. 連続行動は正規分布からサンプリング。 ネットが μ、log_std が σ
  5. log_std を対数で持つのはσ を必ず正にするため
  6. 7-b の entropy_loss は log_std から、 explained_variance は self.v から出ていた
