01

宿題の答え合わせ

この節のねらい

宿題は「なぜ大きく上げてはいけないか」でした。 答えは 5-f にあります。

宿題

アドバンテージが大きい行動の確率を、そのまま大きく上げてはいけないのはなぜでしょうか。 5-f で「PPO は on-policy」と学んだことを思い出してください。

答え：方策が変わると、集めたデータが古くなるからです。

5-f で見たとおり、PPO は on-policy—— いまの方策で集めたデータでしか学習できません。

手順状態
1. 方策 πold で 2048 ステップ集めるデータは πold のもの
2. そのデータで方策を少し更新まだ πold に近い
3. 同じデータでさらに更新（10 エポック繰り返す）方策が離れていく
4. 離れすぎるとデータが方策と合わなくなる

ここが PPO の設計の肝です 本来 on-policy なら1 回更新したらデータを捨てるべきです（5-f）。 しかしそれではデータが高くつきすぎる。 だから PPO は同じデータを 10 回使い回します—— ただし「方策があまり離れない」という条件付きで。

これが名前の由来です

PPO = Proximal Policy Optimization。 Proximal は「近接した」という意味で、 「元の方策の近くに留まりながら最適化する」ことを指します。

7-b で approx_kl を「更新の大きさ」として読みました。 あれは「どれだけ離れたか」を測っていたわけです。

02

ratio — どれだけ変わったか

この節のねらい

「方策が離れた度合い」を測る量を作ります。 8-a で保存しておいた log_prob がここで効いてきます。

ある行動について、更新前と更新後で選ばれやすさがどれだけ変わったかを見ます。

ratio = 新しい方策での確率密度 / 古い方策での確率密度

確率密度は対数で持っているので（density_explained.html）、 引き算して exp すれば比が出ます。

ratio = exp(log_prob_new - log_prob_old)
log_prob の差ratio意味
−0.50.6065選ばれにくくなった
−0.20.8187少し減った
0.01.0000変わっていない
+0.21.2214少し増えた
+0.51.6487選ばれやすくなった

ratio = 1 が「変化なし」の基準です logstd_explained.html で見たとおり、 exp(0) = 1。差がゼロなら比は 1 です。

密度のまま比を取ってよい理由

density_explained.html で「確率 = 密度 × 幅」と書きました。 比を取ると幅が打ち消し合います—— 分子と分母で同じ幅を掛けるはずだったので。 だから密度のままで正しい確率の比が出ます。

これが最も素朴な目的関数です

目的 = ratio × A        # これを大きくしたい

符号で場合分けせずに済みます A > 0（良かった行動）なら ratio を大きくすれば目的が増える → 確率を上げる。 A < 0（悪かった行動）なら ratio を小さくすれば目的が増える → 確率を下げる。 1 つの式で両方が表現できています。

しかしこれには上限がありません A > 0 なら ratio を無限に大きくするのが最善になってしまいます。 §01 で見た「離れすぎる」が起きます。

03

クリップ目的関数

この節のねらい

PPO の中心となる式を出します。2 行です。

a1 = ratio × A
a2 = clamp(ratio, 1-ε, 1+ε) × A     # ε = clip_range = 0.2

目的 = min(a1, a2)

clamp は範囲からはみ出した値を境界に丸める操作です。 ε=0.2 なら ratio を 0.8 〜 1.2 に制限します。

ratioclamp 後

1.01.0
1.51.2
2.01.2

clip_range = 0.2 の意味が見えました 7-c のパラメータ表に出てきた clip_range は、この ε です。 「1 回の更新で、選ばれやすさを ±20% までしか変えさせない」という設定です。

log_prob で言うと

ratio = 1.2 は log_prob の差が 0.1823、 ratio = 0.8 は −0.2231 にあたります（実測）。 7-b で読んだ approx_kl が 0.002〜0.008 だったのを思い出すと、 この制限にはほとんど引っかかっていなかったと分かります。

7-b の clip_fraction（制限に引っかかった割合）が 0.008 → 0.093 だったのも同じ話です。

04

なぜ min を取るのか

この節のねらい

ここが唯一ひねってある部分です。 「クリップするだけ」ではなく「min を取る」理由を、実測の表で確かめます。

A > 0 のとき（良かった行動）

ratioa1 = r×Aa2 = clamp×Amin採用されるのは
0.50.500.800.50a1
1.01.001.001.00a1
1.21.201.201.20a1
1.51.501.201.20a2（頭打ち）
2.02.001.201.20a2（頭打ち）

上げすぎると報われなくなります ratio を 1.2 より大きくしても目的が増えません。 増えないということは勾配がゼロ——それ以上そっちへ動かす理由が消えます。

A < 0 のとき（悪かった行動）

ratioa1a2min採用されるのは
0.5−0.50−0.80−0.80a2（頭打ち）
0.8−0.80−0.80−0.80a1
1.0−1.00−1.00−1.00a1
1.5−1.50−1.20−1.50a1（制限なし）
2.0−2.00−1.20−2.00a1（制限なし）
非対称なのが肝です
上げすぎ（ratio 大）下げすぎ（ratio 小）
A > 0（良い行動）止まる止まらない
A < 0（悪い行動）止まらない止まる

「行きすぎ」だけを止めて、「戻る」は自由にしています。

たとえば A > 0 なのに ratio = 0.5（良い行動なのに確率を下げてしまった）という状態からは、 制限なく戻れます。もし単純にクリップしていたら、 そこでも勾配が消えて間違った状態から抜け出せなくなります。

min は「悲観的に見る」操作です 2 つの候補のうち小さいほうを採るので、 目的関数を控えめに見積もることになります。 結果として「自信のない方向には進まない」という性質が生まれます。

05

損失の全体像

この節のねらい

方策の損失だけでは足りません。 Critic も学習する必要があります。3 つを足して 1 つの損失にします。

loss = policy_loss + vf_coef × value_loss - ent_coef × entropy
       ^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^^^^
       Actor         Critic                   探索を保つ
項中身7-b の指標既定の係数
policy_loss-min(a1, a2) の平均approx_kl1.0
value_loss(V - 収益)² の平均explained_variance0.5
entropy分布の広がりentropy_loss0.0

符号に注意してください policy_loss にマイナスが付くのは、 §04 の min(a1,a2) が大きくしたい量だからです。 学習は損失を小さくする方向に動くので、符号を反転させます。

entropy も大きいほうが良い（探索が続く）ので、 引き算で損失に入れます。 7-b で entropy_loss が負の値だったのはこのためでした（8-a 段階 3）。

アドバンテージは正規化します 
adv = (adv - adv.mean()) / (adv.std() + 1e-8)

論文には目立って書かれていませんが、実装では必須とされる処理です。 報酬のスケールが変わってもこの正規化で吸収されるので、 learning_rate をタスクごとに調整しなくて済みます。

7-c で VecNormalize が効かなかった一因でもあります—— アドバンテージはすでに正規化されているので、 報酬を別途正規化しても得るものが少ない。

detach する場所

8-a の最後で触れた話です。勾配を流したくないものに detach を付けます。

量detach理由
新しい log_probしないここに勾配を流したい
古い log_probする過去の値。更新対象ではない
アドバンテージするCritic 経由で勾配が回り込むのを防ぐ
収益（value の目標）する同上

実装では収集時に torch.no_grad() で囲むので、 古い値は自動的に切り離されています。 明示的な detach() が要らない書き方になります。

段階 2

クリップ目的関数を書く

この段階ですること §03 の 3 行をコードにします。 今回の本題はここだけです。

import torch


def policy_loss(log_prob_new, log_prob_old, adv, clip=0.2):
  ratio = (log_prob_new - log_prob_old).exp()
  a1 = ratio * adv
  a2 = torch.clamp(ratio, 1 - clip, 1 + clip) * adv
  return ???                            # ← ここだけ考える

§03 で「目的 = min(a1, a2)」と決めました。 ただし損失は「小さくしたい量」です（§05 の符号の話）。 バッチ全体で 1 つの数にする必要もあります。

答えと解説を見る
  return -torch.min(a1, a2).mean()

3 つの操作が入っています torch.min(a1, a2) で要素ごとに小さいほうを採り、 .mean() でバッチ全体を 1 つの数にし、 - で「大きくしたい」を「小さくしたい」に反転します。

torch.min は 2 引数だと要素ごとの比較です torch.min(x)（1 引数）は全体の最小値を返しますが、 torch.min(a, b)（2 引数）は同じ位置どうしを比べて小さいほうを返します。 ここで欲しいのは後者です。

.mean() を忘れると 損失がスカラーにならず backward() で落ちます。 これはエラーが出るので気づけます—— 今回は珍しく親切な失敗です。

確認方法 §04 の表を再現します。

for A in (1.0, -1.0):
    print(f"A={A:+.0f}")
    for r in (0.5, 0.8, 1.0, 1.2, 1.5, 2.0):
        lp_old = torch.zeros(1)
        lp_new = torch.full((1,), float(np.log(r)))
        loss = policy_loss(lp_new, lp_old, torch.full((1,), A))
        print(f"  ratio={r:<5} 目的={-loss.item():+.2f}")

段階 3

勾配が消えることを確かめる

この段階ですること 「頭打ち」が本当に学習を止めていることを、 勾配の値で確かめます。写経で構いません。

for r in (1.0, 1.2, 1.5):
    lp_old = torch.zeros(1)
    lp_new = torch.full((1,), float(np.log(r)), requires_grad=True)
    loss = policy_loss(lp_new, lp_old, torch.ones(1))
    loss.backward()
    print(f"ratio={r:<5} 勾配={lp_new.grad.item():+.4f}")

確認方法 ratio=1.5 で勾配が 0.0000 になります。

ratio=1.0   勾配=-1.0000
ratio=1.2   勾配=-0.6000     # 境界上。torch.min がクリップ側を選ぶ
ratio=1.5   勾配=+0.0000     # クリップ領域なので学習が止まる

ratio=1.2 がちょうど半分なのはなぜか ratio=1.2 はクリップの境界ちょうどです。 a1 と a2 の値が等しいので、 torch.min はどちらを選んでもよい状態になります。 PyTorch は同値のとき勾配を両者で分け合うので、半分の -0.6 になります。

実害はありません。 境界ちょうどの値が出る確率はごくわずかで、 大事なのは「境界を越えたら 0 になる」ことです。

「勾配ゼロ」が PPO の制限のかけ方です 値を無理やり押し戻すのではなく、 「そっちへ動かしても損失が減らない」という状態を作るだけ。 結果として更新が自然に止まります。

logstd_explained.html と同じ発想です あちらは「負にならない形に変換する」ことで制約を満たしました。 こちらは「行きすぎると報われない形にする」ことで制約を満たしています。 どちらも「制約を後から押し付けない」という共通の設計です。

07

まとめ

今回で分かったこと
  1. PPO が制限をかけるのは、同じデータを 10 回使い回すから。 方策が離れるとデータが古くなる（5-f の on-policy）
  2. ratio = exp(log_prob_new - log_prob_old)。 1 が「変化なし」
  3. clip_range=0.2 は「選ばれやすさを ±20% までしか変えさせない」
  4. min を取ると非対称になる—— 行きすぎだけ止まり、戻るのは自由
  5. 制限のかけ方は「勾配をゼロにする」。押し戻すのではなく、 そっちへ動かす理由を消す
  6. 損失は 3 つの和。policy_loss + 0.5×value_loss - 0.0×entropy
  7. アドバンテージの正規化は必須。 7-c で VecNormalize が効かなかった一因でもある
次回（8-d）でやること

5 部品を全部つないで動かします。 残るのは部品 2（データ収集）と 5（学習ループ）で、どちらも新しい概念はありません。

そして実際に振り子を立たせます。 SB3 の結果（−254 / 30 万ステップ）と比べて、 自分で書いた PPO がどこまで行くかを見ます。
