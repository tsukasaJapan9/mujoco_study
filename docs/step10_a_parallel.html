この節のねらい

02

環境を並列にする

この節のねらい

Step 7 で何も考えずに n_envs=4 と書きました。 あれが何をしていたのかを理解します。

from stable_baselines3.common.env_util import make_vec_env
from stable_baselines3.common.vec_env import SubprocVecEnv

venv = make_vec_env(make_env, n_envs=4, seed=args.seed,
                    vec_env_cls=SubprocVecEnv)
クラスどう動くか向いている場面
DummyVecEnv 1 つのプロセスで順番に回す。並列ではない 環境が軽いとき。デバッグ
SubprocVecEnv 環境ごとに別プロセスを立てて本当に並列に動かす 環境が重いとき

なぜプロセスを分けるのか Python には GIL という仕組みがあり、 1 プロセスの中では、スレッドを増やしても Python コードは同時に動きません。 本当に並列にするにはプロセスを分けるしかありません。

プロセスを分けると代償があります

観測・行動・報酬をプロセス間でやりとりする必要があります。 これはメモリのコピーと同期待ちを伴います。

環境が軽いと、この通信のほうが高くつきます。 だから n_envs=2 で SubprocVecEnv を使うと、 DummyVecEnv より遅くなることすらあります。

7-a の落とし穴の再確認

SubprocVecEnv は別プロセスで環境を作り直します。 だから if __name__ == "__main__": が無いと スクリプト全体が再実行されます。

Step 7 で実際にこれをやらかしました （tune.py を import したら全実験が走り直した）。 並列にするファイルには必ず書いてください。

03

n_envs を増やすと

この節のねらい

実際に測ります。 期待するほどは速くなりません。その数字を先に見てください。

条件を揃えます

n_steps × n_envs = 8192 に固定しました。 これを揃えないと、更新の回数が変わって比較になりません。

測るのは 40,960 ステップの学習にかかった時間。 8,192 ステップぶん空回ししてから測ります（起動のコストを除くため）。

実測（12 コア、CPU は無負荷）

n_envs方式n_steps env-steps/s1 env あたり
1Dummy8192 3,4333,433基準
2Dummy4096 5,3472,674 いきなり 1.56 倍
4Dummy2048 5,1431,286もう伸びない
2Subproc4096 3,1521,576 1 体より遅い

3,433 → 5,565。 n_envs を 1 から 8 まで増やして、1.62 倍です。

12 コアのマシンで8 倍を期待したくなりますが、なりません。 これが Step 10 で壊したい天井です。

もっと意外なこと — SubprocVecEnv が弱い

n_envs=2 で比べてください。 Dummy 5,347 に対し、Subproc は 3,152。 本物の並列のほうが 1.7 倍遅いのです。

n_envs=4 でも 5,143 対 3,844 で Dummy の勝ち。 Subproc が逆転するのは n_envs=8 からです。

この節でいちばん大事なことDummy でほぼ足りる
数字で言うと
Dummy の n_envs=2 で 5,347。 最速（Subproc 8 体）の 5,565 の 96% です。
なぜそうなるのか
§04 で測りますが、効いているのは「物理の並列化」ではなく 「方策の推論をまとめること」だからです。 Dummy でもまとめて推論します。 プロセスを分ける必要がありません。
Subproc が遅い理由
プロセス間の通信と同期待ちです。 この振り子の 1 ステップは数十マイクロ秒。 通信のほうが高くつきます。
いつ Subproc を使うのか
環境 1 ステップが重いときです。 四足歩行や接触の多い課題なら、通信のコストが相対的に小さくなり、 Subproc が正しく効きます。
Step 7 の設定を見直すと

Step 7 では n_envs=4 + SubprocVecEnv を使いました。 この表で言うと 3,844 —— DummyVecEnv の n_envs=2（5,347）のほうが速かったことになります。

当てずっぽうで「並列にすれば速い」と決めていたわけです。 測って初めて分かりました。

04

なぜ頭打ちになるのか

この節のねらい

並列にすると何が速くなっているのか。 そしてなぜ、どこかで止まるのか。 中身を測ると、意外なものが見えます。

1 env-step の中身を測る

§01 で「物理より事務処理のほうが重い」と書きました。実際に測ります。

やること時間
物理 10 歩（mj_step × frame_skip）17.37 µs
方策の推論 1 回（バッチ 1）35.70 µs
方策の推論が、物理の 2 倍かかっています

このネットワークはパラメータ 4,547 個しかありません。 ResNet-50 の 5,630 分の 1です。

それでも物理シミュレーションより重いのです。 計算そのものではなく、PyTorch を 1 回呼ぶ手続きがこの時間を食っています。

バッチにすると激変します

バッチ推論 1 回の合計 1 環境あたりバッチ 1 との比
135.70 µs35.70 µs1.0x
434.95 µs8.74 µs4.1x
1637.46 µs2.34 µs15.2x
6453.23 µs0.83 µs42.9x

64 体ぶんまとめても、1 体のときの 1.5 倍しかかかりません PyTorch を呼ぶ手続きが 1 回で済むからです。 中の掛け算は 64 倍になっているのに、時間はほぼ変わりません。

いちばん大事な気づき並列環境の本当の効果
思っていたこと
物理シミュレーションを N 個の CPU コアで同時に回すから速い。
実際に効いていること
方策の推論を N 体まとめて 1 回で済ませているから速い。 物理の並列化はおまけです。
数字で見ると
1 env-step に占める推論の割合は バッチ 1 で 67.3%、バッチ 64 で 4.6%。 ここが消えているのが並列化の主な効果です。

では何が天井を作るのか

要因いつ効き始めるか
推論のバッチ効果が飽和 バッチ 16〜64 で推論の割合が 5% を切る。 これ以上減らしても意味がない
CPU コア数 n_envs がコア数を超えると、プロセスが順番待ちになる
プロセス間の通信 n_envs に比例して増える。同期待ちも増える
物理そのもの 最後に残る。CPU で 1 歩 1.74 µs は変えられない

4 つ目が本当の天井です 推論をどれだけ安くしても、物理は CPU で 1 体ずつ動きます。 ここを壊すには、物理ごと GPU に載せるしかありません。 それが 10-c の MJX です。

05

GPU を挿しても速くならない

この節のねらい

「GPU があるのに速くならない」で悩まないための節です。 これは正常です。

よくある期待と、その結末

PPO("MlpPolicy", venv, device="cuda") と書けば速くなる—— なりません。むしろ遅くなることが多いです。

理由 1 — ネットワークが小さすぎる

モデルパラメータ数この方策の何倍
この振り子の方策4,5471x
ResNet-50（画像分類）25,600,0005,630x
GPT-2 small124,000,00027,271x

GPU は「大量の掛け算」を同時にやる装置です 掛け算が 4,547 回しかないなら、 GPU に送って結果を受け取る手間のほうが高くつきます。

理由 2 — 物理は CPU にある

device="cuda" にしても、MuJoCo は CPU で動き続けます。 すると 1 env-step ごとにCPU → GPU → CPU の往復が増えます。

ロードマップにもこう書きました

「ボトルネックは物理シミュレーションであり CPU 側です。 GPU が本当に効くのは Step 10 の MJX 以降。」

MJX が違うのは、物理ごと GPU に載せる点です。 往復が消え、数千体ぶんの物理と推論が GPU の中で完結します。 そこで初めて GPU の形が活きます。

この環境では、そもそも torch から GPU が見えません

いま入っている PyTorch は CUDA 13 向けのビルドで、 このマシンのドライバは 560.35.03（CUDA 12 系）です。

UserWarning: CUDA initialization: The NVIDIA driver on your system is too old

Step 10 では困りません。 MJX は JAX を使い、jax[cuda12] は このドライバで正常に動きます（10-b で確認します）。

手を動かす

この節のねらい

自分のマシンの天井を自分で測ります。 この数字を知らないと、10-c で MJX が速いのかどうか判断できません。

課題 1 — 1 env-step の中身を測る

学習を回さずに、2 つの部品を別々に測ります。

import time, torch, mujoco
torch.set_num_threads(1)

# (a) 物理 10 歩
m = mujoco.MjModel.from_xml_path("models/pendulum_torque.xml")
d = mujoco.MjData(m)
for _ in range(1000):
  mujoco.mj_step(m, d)                 # ウォームアップ
t0 = time.perf_counter()
for _ in range(20000):
  mujoco.mj_step(m, d)
print(f"物理 1 歩: {(time.perf_counter() - t0) / 20000 * 1e6:.2f} us")

# (b) 方策の推論（バッチを変えて）
net = ActorCritic(3, 1).eval()
for B in (1, 4, 16, 64):
  x = torch.randn(B, 3)
  with torch.no_grad():
    for _ in range(200):
      net(x)                           # ウォームアップ
    t0 = time.perf_counter()
    for _ in range(2000):
      net(x)
    per = (time.perf_counter() - t0) / 2000
  print(f"バッチ {B:>3}: {per * 1e6:6.2f} us  (1 環境あたり {???})")   # ← ここだけ考える
答えと解説を見る
  print(f"バッチ {B:>3}: {per * 1e6:6.2f} us  (1 環境あたり {per / B * 1e6:6.2f} us)")

割るのはバッチ数です per はバッチ 1 回ぶんの合計なので、B で割ると1 環境あたりになります。

この割り算が §04 の結論そのものです バッチ 64 で 0.83 µs。バッチ 1 の 35.70 µs と比べて 42.9 倍安い。並列環境の効果はここに出ています。

ウォームアップを必ず入れてください 最初の数回はメモリ確保やキャッシュの準備で遅くなります。 10-b で jit のウォームアップを入れるのと同じ理由です。

答え合わせ（この環境での実測） 
物理 1 歩:   1.74 us   ->  frame_skip 10 で 17.37 us
バッチ   1:  35.70 us  (1 環境あたり 35.70 us)
バッチ   4:  34.95 us  (1 環境あたり  8.74 us)
バッチ  16:  37.46 us  (1 環境あたり  2.34 us)
バッチ  64:  53.23 us  (1 環境あたり  0.83 us)

あなたのマシンでは違う値が出ます。 大事なのは「バッチ 1 のときに推論が物理より重いかどうか」です。

07

まとめ

この教材で分かったこと
  1. 物理だけなら毎秒 704,073 歩、学習中は 55,650 歩。 92% は Python と PyTorch の事務処理（§01）
  2. 並列化の天井は 1.62 倍（3,433 → 5,565 env-steps/s）。 DummyVecEnv の n_envs=2 で 96% は取れる（§03）
  3. 方策の推論（35.70 µs）が物理 10 歩（17.37 µs）より重い。 パラメータ 4,547 個しかないのに（§04）
  4. 並列環境の主な効果は、推論をバッチにまとめること。 バッチ 64 で 1 環境あたり 42.9 倍安くなる（§04）
  5. 最後に残る天井は物理そのもの。 CPU で 1 体ずつ動く限り壊せない（§04）
  6. GPU を挿しても速くならない。これは正常（§05）
いちばん持ち帰ってほしい一文

速くする前に、どこが遅いのかを測る。

「GPU を挿す」「n_envs を増やす」はどちらも当てずっぽうでした。 測ってみたら犯人は 4,547 パラメータのネットワークを呼ぶ手続き。 9-c で報酬の項について言ったことが、そのまま速度にも当てはまります。
