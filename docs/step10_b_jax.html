01

JAX は何をする道具か

この節のねらい

一言で何なのかを掴みます。ここが分かれば残りは細部です。

いちばん大事な一言JAX
何をするか
Python で書いた数値計算の関数を、GPU 用のプログラムに翻訳する道具。
NumPy との関係
jax.numpy はNumPy とほぼ同じ名前・同じ使い方です。 import jax.numpy as jp と書いて jp.sin、jp.array。 見た目はほぼ NumPy です。
ではなぜ難しいのか
翻訳できる書き方に制限があるからです。 JAX は関数を一度「試し実行」して、やった計算を記録し、 それを GPU 用に変換します。 実行するたびに中身が変わる書き方は記録できません。
「試し実行して記録する」= トレース

JAX は関数に本物の数値ではなく「形だけの箱」を流し込みます。 箱が通った道筋を記録して、それを GPU 用にコンパイルします。

だから箱の中身（値）を見る操作は失敗します。 §05 の if が書けない理由がこれです。

これから出てくる 5 つの約束は、全部この 1 点から来ます 「値そのものは、実行時までわからない」。 この一行を覚えておけば、5 つとも理由が分かります。

02

約束 1 — 配列は書き換えない

この節のねらい

NumPy で当たり前にやっていた x[0] = 5 が使えません。 その代わりの書き方を覚えます。

import jax.numpy as jp

x = jp.array([1.0, 2.0, 3.0])
x[0] = 99.0

TypeError: JAX arrays are immutable and do not support in-place item assignment

代わりにこう書きます。

y = x.at[0].set(99.0)

print(y)   # -> [99.  2.  3.]
print(x)   # -> [1. 2. 3.]     元の x は変わらない

「書き換える」ではなく「書き換えた新しい配列を作る」 .at[i].set(v) はコピーを返します。 .add() .mul() なども同じ形です。

コピーだから遅い、とはなりません

コンパイルの段階で不要なコピーは消えます。 .at[].set() を使っても、実際の GPU コードでは直接書き換えになります。

MJX で必ず出会います

MuJoCo では d.ctrl[0] = 0.5 と書いていました。MJX では——

dx = dx.replace(ctrl=jp.array([0.5]))

replace はその項目だけ差し替えた新しい dx を返します。 元の dx は変わりません。戻り値を必ず受け取ってください。

03

約束 2 — jit でコンパイルする

この節のねらい

jax.jit が何をして、どれだけ効くかを実測で見ます。

import jax, jax.numpy as jp, time

def f(x):
  for _ in range(50):
    x = jp.tanh(x) * 1.01
  return x.sum()

fj = jax.jit(f)              # これだけ

a = jp.arange(100000, dtype=jp.float32)
1 回あたり倍率
jit なし5.974 ms1.0x
jit あり0.064 ms93x

なぜこんなに違うのか jit なしだと、jp.tanh 1 回ごとに GPU に命令を送って結果を待つのを 50 回繰り返します。 jit ありなら50 回分をまとめて 1 つの GPU プログラムにしてから送ります。

最初の 1 回だけ遅くなります

コンパイルは最初に呼ばれたときに走ります。 その 1 回は秒単位かかることもあります。

だから速度を測るときは、1 回空打ちしてから測ります。 上の表もそうしています。

形が変わると作り直します

jit は引数の形（shape）ごとにコンパイルします。 (100,) で呼んでから (200,) で呼ぶと、もう一度コンパイルされます。

形をころころ変えるコードは、毎回コンパイルが走って遅くなります。 MJX で並列数を固定するのは、これも理由のひとつです。

結果はすぐには返ってきません

JAX の計算は非同期です。呼んだ瞬間には 「計算を依頼した」だけで、まだ終わっていません。

時間を測るときは jax.block_until_ready(out) か out.block_until_ready() で待ってから止めます。 これを忘れると、ありえない速さが出ます。

04

約束 3 — vmap で N 体にする

この節のねらい

Step 10 の主役です。 vmap があるから、1 体ぶんのコードだけ書けば数千体が動きます。

I, MGL, DT = 0.0567, 1.6231, 0.01

def step_one(state, torque):
  """振り子を 1 歩進める。state = [theta, omega] の 1 体ぶん"""
  theta, omega = state[0], state[1]
  alpha = (torque - MGL * jp.sin(theta)) / I
  omega = omega + alpha * DT
  theta = theta + omega * DT
  return jp.array([theta, omega])

1 体なら問題なく動きます。

step_one(jp.array([0.3, 0.0]), 0.1)
# -> [ 0.29933 -0.06696]

3 体まとめて渡すと壊れます。

batch = jp.array([[0.3, 0.0], [1.0, 0.5], [2.0, -1.0]])   # (3, 2)
tq    = jp.array([0.1, 0.2, 0.0])                          # (3,)

step_one(batch, tq)
# -> TypeError: sub got incompatible shapes for broadcasting: (3,), (2,).

当然です state[0] が「1 体目の theta」ではなく「1 行目まるごと」 になってしまうからです。

Step 10 の主役vmap
何をするか
1 体ぶんに書いた関数を、N 体ぶんに自動で作り変えます。 jax.vmap(step_one) と包むだけ。中身は 1 文字も変えません。
for ループとの違い
for ならN 回順番に実行します。 vmap はN 体を 1 つの大きな計算にまとめます。 GPU は大きな計算 1 個が得意なので、これが効きます。
jax.vmap(step_one)(batch, tq)
# -> [[ 0.29933 -0.06696]
#     [ 1.00294  0.29439]
#     [ 1.9874  -1.2603 ]]

1 体ずつ for で回した答えと完全に一致します vmap は計算を変えません。並べ方を変えるだけです。 疑わしいときは for と突き合わせて確かめられます。

どの軸を並べるかは指定できます

jax.vmap(f, in_axes=(0, None)) のように書くと、 1 つ目の引数だけ N 体ぶん、2 つ目は全員で共有になります。

MJX ではモデル（mx）は全員共通、データ（dx）だけ N 体 なので、この形をよく使います。

05

約束 4 — if と for が書けない

この節のねらい

いちばん引っかかるところです。 §01 の「値は実行時までわからない」がそのまま効いてきます。

def bad(x):
  if x > 0:
    return x * 2
  return x

jax.jit(bad)(jp.array(1.0))
# -> TracerBoolConversionError

理由 jit は形だけの箱を流します。 箱に対して x > 0 はTrue とも False とも決まりません。 どちらの枝を記録すればいいか決められないので、エラーになります。

やりたいこと普通の PythonJAX
条件分岐if cond: a else: b jp.where(cond, a, b)
jax.lax.cond(...)
決まった回数の繰り返しfor i in range(n) jax.lax.fori_loop(0, n, body, init)
条件付きの繰り返しwhile cond jax.lax.while_loop(...)
 
good = jax.jit(lambda x: jax.lax.cond(x > 0,
                                      lambda v: v * 2,   # True のとき
                                      lambda v: v,       # False のとき
                                      x))
good(jp.array( 1.0))   # ->  2.0
good(jp.array(-1.0))   # -> -1.0
形が決まっている for は、実は書けます

for _ in range(50): のように回数が定数なら、 普通の for で書いて大丈夫です（§03 の例がそうでした）。 50 回ぶんが展開されて記録されるだけだからです。

ただし回数が大きいとコンパイルが非常に遅くなります。 数十回までなら for、それ以上は fori_loop が目安です。

MJX でいちばん効いてくる場面

「エピソードが終わったらリセットする」を if done: reset() と書けません。 N 体それぞれで done が違うからです。

代わりに全員ぶんのリセット後の状態を計算しておいて、 jp.where(done, reset_state, state) で選びます。 「やらない計算もやってから捨てる」——GPU ではこれが速いのです。

06

約束 5 — 乱数は鍵を持ち回す

この節のねらい

np.random.randn() のような書き方ができません。 なぜダメで、代わりにどうするか。

import jax

key = jax.random.PRNGKey(0)          # 「鍵」を作る

jax.random.normal(key, (3,))   # -> [ 1.6226422   2.0252647  -0.43359444]
jax.random.normal(key, (3,))   # -> [ 1.6226422   2.0252647  -0.43359444]   同じ！

同じ鍵からは必ず同じ値が出ます JAX の乱数は「内部に状態を持たない」設計です。 key を渡せばいつでも同じ結果。 これは仕様であって、バグではありません。

違う値が欲しいときは、鍵を分けます。

k1, k2 = jax.random.split(key)

jax.random.normal(k1, (3,))   # -> [ 1.0040143  -0.9063372  -0.7481722 ]
jax.random.normal(k2, (3,))   # -> [-2.4424558  -2.0356805   0.20554423]
考え方が変わるところなぜ面倒な設計なのか
NumPy のやり方
ライブラリの中に隠れた状態があり、呼ぶたびに進みます。 呼ぶ順番が変わると結果が変わります。
それが困る理由
vmap で N 体を並列にすると「呼ぶ順番」が存在しません。 jit は計算の順番を勝手に入れ替えます。 隠れた状態とは両立しません。
JAX の答え
状態を引数として明示的に持ち回る。 面倒な代わりに、並列でも再現性が完全に保証されます。
実際の書き方

毎回 split して片方を次に渡すのが定番です。

key = jax.random.PRNGKey(0)
for step in range(100):
  key, subkey = jax.random.split(key)      # key を更新し、使い捨ての subkey を得る
  noise = jax.random.normal(subkey, (4,))
  ...

key を上書きし、subkey を使い捨てる。この形を覚えてください。

課題 1 — 1 体ぶんの振り子を書く

jax_pendulum.py を新しく作ります。

import jax, jax.numpy as jp

I, MGL, DT = 0.0567, 1.6231, 0.01

def step_one(state, torque):
  """state = [theta, omega] の 1 体ぶんを 1 歩進める"""
  theta, omega = state[0], state[1]
  alpha = ___                          # <- ここだけ考える（運動方程式）
  omega = omega + alpha * DT
  theta = theta + omega * DT
  return jp.array([theta, omega])

print(step_one(jp.array([0.3, 0.0]), 0.0))

ヒント Step 4 で使った式です。I·α = τ - mgl·sinθ。 NumPy とまったく同じ書き方で通ります（np が jp になるだけ）。

課題 2 — 100 歩まとめて進める

for ではなく fori_loop で書きます。

@jax.jit
def roll(state, torque, n=100):
  return jax.lax.fori_loop(0, n, ___, state)    # <- ここだけ考える

print(roll(jp.array([0.3, 0.0]), 0.0))
# -> [0.17825 1.31012]

fori_loop に渡す関数の形 (i, 今の状態) -> 次の状態 です。 i を使わなくても、引数には必ず要ります。

確かめ方 素の for で 100 回回した答えと完全に一致するはずです。 一致しなければ書き方が違います。

まとめ

5 つの約束
  1. 配列は書き換えない。.at[i].set(v) で新しい配列を作る（§02）
  2. jit でまとめてコンパイル。実測 93 倍。最初の 1 回だけ遅い（§03）
  3. vmap で 1 体ぶんの関数を N 体に。中身は変えない（§04）
  4. if・可変長 for は書けない。 jp.where / lax.cond / lax.fori_loop（§05）
  5. 乱数は鍵を持ち回す。key, subkey = split(key)（§06）
5 つとも、理由はひとつです

JAX は関数を「試し実行」して計算の道筋を記録し、GPU 用に翻訳する。

だから値そのものは実行時までわからない。 だから if が書けず、隠れた状態が持てず、形が変わると作り直しになります。 迷ったらこの一行に戻ってください。
