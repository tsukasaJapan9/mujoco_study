01

MJX と MuJoCo の対応

この節のねらい

書き換えは機械的です。対応表を 1 つ覚えれば済みます。

MuJoCo（CPU）MJX（GPU）

モデルm = MjModel.from_xml_path(...) mx = mjx.put_model(m)

新しい dx が返る

初期化mujoco.mj_resetData(m, d) dx = mjx.make_data(mx)（作り直す）
違いは 1 点だけです

MuJoCo は d を書き換える。MJX は新しい dx を返す。

10-b §02 の「配列は書き換えない」がそのまま出ています。 mjx.step(mx, dx) の戻り値を捨てると、何も起きません。 MJX でいちばん多いミスです。

XML はそのまま使えます

models/pendulum_torque.xml を1 文字も変えずに MJX で読めます。 mjx.put_model() がCPU 用のモデルを GPU 用に変換してくれます。

ただし使えない機能があります（§05）。 変換できないものがあるとその時点でエラーになります。

02

答えが合うか確かめる

この節のねらい

速度を測る前に、正しさを確かめます。 別の実装なので、まず一致を見るのが先です。

import numpy as np, jax, jax.numpy as jp, mujoco
from mujoco import mjx

m = mujoco.MjModel.from_xml_path("models/pendulum_torque.xml")
d = mujoco.MjData(m)

# --- CPU 版 ---
mujoco.mj_resetData(m, d)
d.qpos[0] = 0.3
d.ctrl[0] = 0.1
mujoco.mj_forward(m, d)
for _ in range(100):
  mujoco.mj_step(m, d)
print(f"CPU: theta={d.qpos[0]:.6f} omega={d.qvel[0]:.6f}")

# --- MJX ---
mx = mjx.put_model(m)
dx = mjx.make_data(mx)
dx = dx.replace(qpos=dx.qpos.at[0].set(0.3),
                ctrl=dx.ctrl.at[0].set(0.1))

@jax.jit
def roll(dx, n=100):
  return jax.lax.fori_loop(0, n, lambda i, s: mjx.step(mx, s), dx)

out = roll(dx)
print(f"MJX: theta={float(out.qpos[0]):.6f} omega={float(out.qvel[0]):.6f}")

CPU: theta=0.267372 omega=-0.627730
MJX: theta=0.267372 omega=-0.627730
差: 4.14e-08
小数点以下 6 桁まで一致しました

差は 4.14e-08。float32 の精度の範囲です。

MJX は MuJoCo の別実装ではなく、同じ計算を GPU 向けに書き直したもの だと確かめられました。

ただし完全一致は保証されません

接触が多い課題では、もっと大きくずれます。 MJX は接触の解き方が CPU 版と違うためです（§05）。

だから自分のモデルでは必ずこの照合をやってください。 振り子のように接触が無ければ、ほぼ一致します。

03

N 体に増やす

この節のねらい

10-b 課題 3 とまったく同じことを、MJX でやります。

B = 5
init = jp.linspace(-0.5, 0.5, B)          # 5 体、別々の初期角度

def make(theta):
  dx = mjx.make_data(mx)
  return dx.replace(qpos=dx.qpos.at[0].set(theta),
                    ctrl=dx.ctrl.at[0].set(0.1))

dxs = jax.vmap(make)(init)                # (5,) -> 5 体ぶんの dx
outs = jax.jit(jax.vmap(roll))(dxs)       # roll は 1 体ぶんのまま

print(np.asarray(outs.qpos[:, 0]).round(5))
# -> [-0.4244  -0.20691  0.00859  0.22409  0.44161]
roll は 1 文字も変えていません

§02 で書いた1 体ぶんの関数を、 jax.vmap で包んだだけです。

mjx.make_data も vmap で包むのがポイント。 これでN 体ぶんの dxが一度にできます。

MJX の書き方の型3 行で終わる
1. 1 体ぶんを書く
mjx.step を使って、普通に 1 体ぶんの処理を書く。
2. vmap で包む
jax.vmap(f)。モデル mx は共通なので、 関数の外で参照するか in_axes=None にする。
3. jit で包む
jax.jit(jax.vmap(f))。この順番です。
frame_skip はどう書くか

あなたの環境は frame_skip = 10 でした （timestep=0.001、制御 100 Hz）。

MJX でも同じです。fori_loop で 10 回まわします。

def env_step(dx, action):
  dx = dx.replace(ctrl=action * 0.5)                    # [-1,1] -> トルク
  dx = jax.lax.fori_loop(0, 10, lambda i, s: mjx.step(mx, s), dx)
  return dx

どれだけ速くなるか

この節のねらい

並列数を変えて測ります。 1 体では CPU に完敗します。そこが出発点です。

これが MJX でいちばん誤解されるところです。 「GPU に載せたのに遅くなった」は正常な結果です。

GPU は1 個の計算を速くする装置ではありません。 1 体ぶんの物理（nq=1 の振り子）は、GPU にとって小さすぎます。

覚えておく数字損益分岐点
この環境では
128 体と 192 体の間。だいたい 150 体です。
それより少ないと
CPU で回したほうが速い。 MJX を使う意味がありません。
何で決まるか
GPU の並列度とモデルの重さです。 モデルが重いほど、少ない並列数で逆転します （1 体あたりの計算量が増えて GPU が埋まりやすくなるため）。 あなたの GPU とモデルで測ってください。
頭打ちになる理由
8,192 を超えると伸びが鈍ります。 GPU の演算器が埋まりきったからです。 これ以上並列数を増やしても、メモリを食うだけです。

学習全体ではもっと差がつきます

上の表は物理だけの比較です。 10-a で見たとおり、実際の学習では Python の事務処理が 9 割を食います。

physics-steps/s内訳
CPU 物理だけ704,073純粋な mj_step
CPU で実際に学習55,650 10-a の最速 5,565 env-steps/s × 10

学習同士で比べると 408 倍です 22,716,708 ÷ 55,650 = 408。 物理だけの比較（32.3 倍）よりずっと大きい。 GPU の並列度そのものより、「Python の往復が消える」効果のほうが大きいのです。

ただし、そのためには方策も GPU に置く必要があります

物理だけ MJX にして、方策が PyTorch のままだと、 毎ステップ GPU と CPU を往復します。意味がありません。

MJX を使うなら、方策も学習ループも JAX で書きます。 自分で書くのは大変なので、 実務では Brax の PPO をそのまま使います（10-d）。

9-c の「43 時間」はどうなるか

4 条件 × 50 シード × 40 万ステップ。 CPU では 約 43 時間でした。

ただし単純に 739 で割ることはできません。 MJX では「50 シードを別々に走らせる」のではなく 「1 回の学習の中で環境を数千体並べる」形になります。 速くなる代わりに、実験のやり方そのものが変わります。

mjx.put_model() の時点で止まります。 実行してから気づくのではないので、その点は親切です。

実務での回避

接触する部分だけ、対応している形状に置き換えます。 四足ロボットの足先ならSPHERE か CAPSULE にするのが定番です。

見た目用の geom と、衝突用の geom を分けます。 MJCF では contype="0" conaffinity="0" にすると 見た目だけで衝突しない geomになります。

models/pendulum_torque.xml は implicitfast、衝突なしなので、何の問題もありません。

手を動かす

この節のねらい

自分の振り子を MJX に載せ、CPU と一致することを確かめ、速度を測ります。

入れる 
uv add mujoco-mjx

jax[cuda12] が入っていればそのまま GPU で動きます。 10-b でやっていない場合は先にそちらを。

課題 1 — CPU と一致することを確かめる

速度を測る前に必ずやります。§02 のコードをそのまま書いてください。

mx = mjx.put_model(m)
dx = mjx.make_data(mx)
dx = dx.replace(qpos=dx.qpos.at[0].set(0.3),
                ctrl=dx.ctrl.at[0].set(0.1))

@jax.jit
def roll(dx, n=100):
  return jax.lax.fori_loop(0, n, ???, dx)      # ← ここだけ考える
答えと解説を見る
  return jax.lax.fori_loop(0, n, lambda i, s: mjx.step(mx, s), dx)

10-b 課題 2 とまったく同じ形です 違うのは step_one が mjx.step になっただけ。自作の運動方程式が MuJoCo の物理エンジンに変わりました。

mx は外から参照します モデルは全ステップで共通なので、ループに渡す必要はありません。N 体に vmap するときも mx は共有です。

戻り値を受け取ってください mjx.step(mx, s) は新しい状態を返します。mjx.step(mx, s) と書いて捨てると、何も進みません（§01）。

合格の目安 CPU 版との差が 1e-6 より小さいこと。 これが合わないまま速度を測っても意味がありません。

課題 2 — 並列数を変えて速度を測る 
import time

STEPS = 100
vroll = jax.jit(jax.vmap(roll))

for B in (1, 64, 128, 256, 1024, 4096, 16384):
  dxs = jax.vmap(lambda _: mjx.make_data(mx))(jp.arange(B))
  out = vroll(dxs)
  jax.block_until_ready(out)                    # <- JIT のウォームアップ

  t0 = time.perf_counter()
  for _ in range(5):
    out = vroll(out)
  jax.block_until_ready(out)                    # <- 忘れると嘘の速度が出る
  dt = time.perf_counter() - t0
  print(f"{B:>6} {B * STEPS * 5 / dt:>15,.0f} physics-steps/s")
答えと解説を見る
     1           4,862 physics-steps/s
    64         299,232
   128         540,610
   256       1,321,885
  1024       4,677,327
  4096      15,664,251
 16384      22,716,708

並列数 1 の値に注目してください 4,862。CPU 1 体の 704,073 と比べて145 分の 1です。「GPU に載せたら遅くなった」は正常な結果です。

16,384 で頭打ちになります 8,192（20,890,867）から 16,384（22,716,708）で8.7% しか伸びません。GPU の演算器が埋まりきったので、これ以上増やしてもメモリを食うだけです。

メモリに注意 RTX 4050 は 6GB。振り子（nq=1）だから 16,384 体が載ります。四足なら 4,096 体でも厳しくなります。

2 つの block_until_ready を忘れないでください 1 つ目はコンパイルを測定に含めないため。 2 つ目は計算の完了を待つため。 どちらが無くても数字が壊れます（10-b §03）。

課題 3 — 損益分岐点を自分の GPU で見つける

CPU 1 体（mujoco.mj_step をループで回す）の速度を測り、 それを超える並列数を探してください。

mujoco.mj_resetData(m, d)
N = 100000
t0 = time.perf_counter()
for _ in range(N):
  mujoco.mj_step(m, d)
cpu = N / (time.perf_counter() - t0)
print(f"CPU 1 体: {cpu:,.0f} physics-steps/s")
答えと解説を見る
CPU 1 体: 704,073 physics-steps/s

     1           4,862   0.007x   <- CPU の 145 分の 1
   128         540,610   0.8x     <- まだ負け
   192         950,752   1.4x     <- ここで逆転
 16384      22,716,708  32.3x

損益分岐点は 128〜192 体でした これより少ない並列数なら、CPU で回したほうが速い。MJX を使う意味がありません。

あなたの環境では違う値になります GPU の並列度とモデルの重さで決まります。モデルが重いほど、少ない並列数で逆転します（1 体あたりの計算量が増え、GPU が埋まりやすくなるため）。

CPU 側は他を止めてから測ってください 学習を裏で回したまま測ったときは 335,590 でした。無負荷の 704,073 の半分以下です。この数字がずれると、損益分岐点もずれます。

この課題のねらい 「GPU だから速い」は嘘だと自分の手で確かめます。 この数字は GPU とモデルによって変わります。 自分の環境の値を知っていることが大事です。

CPU に負荷がかかっていると正しく測れません

9-c の ablation のような学習を裏で回したまま測ると、 CPU 側の数字が半分近くまで落ちます。

速度を測るときは、他を全部止めてください。

07

まとめ

この教材で分かったこと
  1. 書き換えは機械的。違いは「dx を書き換える」ではなく 「新しい dx が返る」の 1 点だけ（§01）
  2. CPU 版と 4.14e-08 まで一致した。 速度を測る前に必ず照合する（§02）
  3. 1 体ぶんを書いて vmap で包む。 mjx.make_data も包む（§03）
  4. 1 体だと CPU より桁違いに遅い。 数百体で逆転する（§04）
  5. 衝突は 27 通りしか計算できない。 接触する geom は SPHERE / CAPSULE に寄せる（§05）
いちばん持ち帰ってほしい一文

GPU は「速い装置」ではなく「たくさん同時にやる装置」です。

1 体だけ速く回したいならCPU のほうが速い。 数千体を同時に回すときだけ、GPU が勝ちます。 この性質が、次の Step の学習アルゴリズムの形まで変えます。

速くなると、やることが変わります

9-c で「まともな ablation には 50 シード = 43 時間」と計算しました。

1 本が数十秒で終わるなら、50 シードは現実的な選択肢になります。 速度は、単に待ち時間が減るだけではありません。 「measure できることの範囲」が変わります。
