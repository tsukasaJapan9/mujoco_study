9-b §05 で学んだ「動かないことに正の点を与えない」が、 ここでは徹底されています。 じっとしていても、正の項からは 1 点ももらえません。

主目的の中身

def _reward_tracking_lin_vel(self, commands, local_vel):
  lin_vel_error = jp.sum(jp.square(commands[:2] - local_vel[:2]))
  return jp.exp(-lin_vel_error / self._config.reward_config.tracking_sigma)
9-b の式そのものです

tracking_sigma = 0.25 なので exp(-e² / 0.25) = exp(-4·e²)。 9-b で書いた exp(-k·e²) の k = 4 です。

9-b の式で e_half を出してみます。 e_half = sqrt(ln2 / k) = sqrt(0.6931 / 4) → 0.4163 m/s。

速度の誤差もらえる点

0.1 m/s0.9608
0.2 m/s0.8521
0.4163 m/s0.5000
1.0 m/s0.0183

この設計者が決めたのは「0.42 m/s ずれたら半分」 tracking_sigma = 0.25 という数字を直接いじったのではなく、 許容できる速度誤差から逆算したと読めます。 9-b §03 でやったことと同じです。

行動の変化への罰

def _cost_action_rate(self, act, last_act, last_last_act):
  return jp.sum(jp.square(act - last_act))

最後の行だけ、原則から外れています

orientation（胴体の傾き）の重みは −5.0。 主目的の 5 倍です。9-a の教えに反しています。

なぜこれでいいのか。 罰の中身が「傾いていないときは 0」だからです。 まっすぐ歩いている限り、この項は一切効きません。 効くのは転びかけたときだけで、そのときは何より優先すべきです。

Step 9 への追加重みの大きさは「いつ効くか」で決まる
9-a で学んだこと
各項が実際に取る値を計算して桁を揃える。
ここで足りていなかった視点

-0.01ω² はうまくいっていても 0 にならない （上端で微小に揺れる）ので、重くできません。 9-a §05 で「失点の 89%」だったのは、まさにこれです。
04

制御周期と行動空間

この節のねらい

報酬以外の設定も、Step 9 の言葉で読めます。

設定Go1あなたの振り子意味
sim_dt0.0040.001物理の刻み（250 Hz / 1000 Hz）
ctrl_dt0.020.01方策が動く周期（50 Hz / 100 Hz）
frame_skip510 1 指令あたりの物理ステップ数
episode_length100050020 秒 / 5 秒
action_scale0.5—行動を関節角のオフセットに変える倍率

方策は 50 Hz でしか動きません 四足歩行というあなたの振り子よりずっと難しい課題なのに、 制御周期は半分です。

それで足りる理由が 9-d §05 です 行動が「目標関節角」だからです。 内部の PD が 250 Hz で補正し続けるので、 方策は 20 ms に 1 回、姿勢の目標を更新するだけで済みます。

action_scale = 0.5 の意味

方策の出力 a（±1）は、そのまま関節角にはなりません。

目標関節角 = 基本姿勢 + action_scale * a

基本姿勢からのズレとして指令します。 a=0 なら立っている姿勢。

これは強力な事前知識です。 学習の最初、方策の出力はほぼ 0 なので、 いきなり「立った姿勢」から始まります。 でたらめなトルクで転げ回るところから始めるのとは、探索の難しさが違います。

06

Phase C のまとめ

この節のねらい

Step 9・10 でやったことを、Phase D で使う形にまとめます。

Step 9 — 設計
  1. 方策は書いた式を最大化する。望んだことではない（9-a）
  2. 学習報酬のグラフでは異常に気づけない。 動きを見る・別のものさしで採点する・内訳をログする（9-a）
  3. 報酬を書いたら「動き出す得」を計算してから学習させる（9-b）
  4. exp(-k·e²)、k = ln2/e_half²。 決めるのは許容誤差（9-b）
  5. 標準偏差より小さい差は差ではない。約 50 シードが相場（9-c）
  6. 二値の結果に平均を使わない。成功率と成功時の点数を分ける（9-c）
  7. 実機で困る量は、実機で困る量として測る。 観測ノイズ 1% で符号反転が 8 倍になっても報酬は動かない（9-d）
  8. ばらつきが大きいなら、比べるより先に減らす（9-c → 9-e）
Step 10 — 速度
  1. CPU 並列はコア数で頭打ち（10-a）
  2. JAX の 5 つの約束。全部「値は実行時までわからない」から来る（10-b）
  3. MJX は 1 体だと CPU より遅い。数百体から逆転する（10-c）
  4. Playground の報酬はStep 9 で導いた原則どおりに書かれている（10-d）
  5. ほとんどの時間 0 になる項は、重みを大きくしてよい（10-d §03）
Phase C でいちばん大事だったこと

測っていないことは、知らないことです。

Phase C では、教材の中で4 回、予想が外れました。

  • 6-d の「ぐるぐる回る」予告 → 起きなかった（9-a）
  • 教科書どおりの指数型報酬 → 2 回とも学習しなかった（9-b）
  • 1 シードのきれいな ablation → 3 シードで順位が逆転（9-c）
  • 「目標角度方式は滑らかになる」 → むしろ荒れた（9-d）

4 回とも、測る前は自信がありました。 Phase D の実機では、外れたときの代償が跳ね上がります。
